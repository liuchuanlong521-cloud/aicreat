核心考点

前言

前面四节，我们从机器学习走到深度学习，再走到 Transformer。如果说 Transformer 是一块强大的"发动机"，那么 大模型（Large Language Model, LLM） 就是装上了这台发动机的"超级跑车"。 2022 年 11 月，ChatGPT 发布，短短两个月用户破亿，成为人类历史上增长最快的消费级应用。它让很多人第一次真切感受到：AI 不再是实验室里的玩具，而是能写诗、写代码、做翻译、回答问题的"超级助手"。 但大模型到底是什么？它为什么突然变得这么厉害？作为 AI PM，你应该如何判断一个业务问题能不能用大模型解决？该选哪个模型？要花多少钱？有哪些坑需要避开？ 本文的目标，就是帮你建立对大模型的系统性认知——不是讲训练细节，而是讲产品直觉。读完之后，你应该能自信地和算法团队讨论大模型选型，能评估一个大模型产品的可行性，知道它的能力边界在哪，以及如何在成本和效果之间做权衡。

# 一、什么是大模型？从"小"到"大"的质变

# （一）一个形象的类比：从"专科生"到"通才博士"

想象你在招聘员工：

小模型（传统 AI 模型）就像"专科生"：

你招了一个专门做情感分析的员工。他读过 10 万条标注好的评论，学会了判断"正面"还是"负面"。但他只会这一件事——你让他写个摘要，他说"我不会"；你让他翻译一段话，他说"我没学过"。

如果你想同时做情感分析、摘要、翻译，你需要招三个专科生，每人训练一次，每人占用一份资源。

大模型就像"通才博士"：

你招了一个读了全人类大部分书籍、论文、网页的"超级学霸"。他没有专门学过"情感分析"这个任务，但你给他几个例子，他马上就能做。你让他翻译，他会。你让他写代码，他也会。你让他分析合同漏洞，他还能说得头头是道。

更神奇的是，这个"通才博士"不是只会"模仿"——他能举一反三、推理演绎，甚至展现出训练时没有被明确教过的能力。

这就是大模型的核心特征：一个模型，通过海量数据预训练，获得通用的语言理解和生成能力，然后通过少量示例或指令就能适配各种下游任务。

# （二）"大"在哪里？三个维度的规模化

大模型的"大"，体现在三个维度：

维度小模型（如 BERT-base）大模型（如 GPT-3）超大模型（如 GPT-4）
参数量1.1 亿1750 亿rumored 1.8 万亿（MoE）
训练数据约 16GB 文本约 45TB 文本未公开，估计数百 TB
训练算力64 个 TPU 训练 4 天数千个 V100 训练数月未公开，估计数千万美元
上下文长度5122048128K

参数量的直觉：

参数量可以理解为模型的"记忆容量"。1.1 亿参数就像能记住一本厚书的内容；1750 亿参数就像能记住一个大型图书馆的内容。

但参数量不只是一个"记忆仓库"——它更像是"神经元连接的数量"。人脑有约 860 亿个神经元、100 万亿个突触连接。GPT-3 的 1750 亿参数，相当于一个"简化版数字大脑"的连接规模。

训练数据的直觉：

GPT-3 的训练数据包括：维基百科、书籍、网页、代码等，总共约 5000 亿个 Token（词片段）。

如果把这些文字全部打印出来，堆叠高度大约是……从地球到月球的一半距离。一个人就算每天读 10 小时，需要读 2 万年才能读完。

训练算力的直觉：

GPT-3 的训练成本约 460 万美元。这相当于：

  • 用 1000 块顶级 GPU（V100）同时工作
  • 连续运行数月
  • 消耗的电费足够一个普通家庭用几百年

# （三）大模型 vs 小模型的核心差异

维度传统小模型大模型
训练方式针对特定任务，用标注数据训练先用海量无标注数据"通识教育"，再针对任务"专项辅导"
任务适配一个模型一个任务一个模型，通过 Prompt/Few-shot 适配无数任务
泛化能力弱，换个场景就要重新训练强，能处理训练时没见过的新任务
数据需求需要大量标注数据预训练不需要标注，微调只需要少量标注
推理成本低（毫秒级）高（秒级到数十秒）
部署方式通常私有化部署API 调用为主，也可私有化
可解释性较低极低（黑箱中的黑箱）
幻觉问题较少常见（会一本正经地胡说八道）

关键洞察：

大模型最大的革命性，不是"更大"，而是从"专用"走向"通用"。

以前，每做一个 AI 功能（情感分析、命名实体识别、文本摘要），都要从头训练一个专用模型。现在，你有一个通用大模型，通过写一段 Prompt 或者给几个例子，它就能做这些事。

这意味着：AI 的产品化成本大幅降低，创新速度大幅提升。

# 二、大模型的发展历程：一场激烈的军备竞赛

# （一）GPT 系列：Decoder-only 路线的胜利

GPT（Generative Pre-trained Transformer）系列是 OpenAI 推出的大模型家族，也是当前最知名的大模型路线。

模型年份参数量关键突破产品意义
GPT-120181.17 亿证明"无监督预训练 + 有监督微调"有效开创了预训练-微调范式
GPT-2201915 亿模型足够大时，零样本能力涌现引发"AI 太危险不敢开源"的争议
GPT-320201750 亿Few-shot 学习能力惊人，不微调就能做事证明了"大力出奇迹"
GPT-3.52022未公开InstructGPT：用 RLHF 对齐人类偏好ChatGPT 的技术基础
GPT-42023未公开（ rumored 1.8T MoE）多模态、推理能力飞跃、支持 128K 上下文当前最强通用模型之一
GPT-4o2024未公开原生多模态、速度更快、成本更低让多模态交互成为常态

GPT 系列的核心洞察：

OpenAI 坚信一个简单但强大的理念：预测下一个词（Next Token Prediction），当规模足够大时，可以解决一切。

这个理念听起来很傻——让模型做"完形填空"，怎么能解决翻译、摘要、推理、代码生成呢？

但事实是：为了准确预测下一个词，模型被迫学会了语法、语义、逻辑、常识、推理，甚至是编程语言的规则。当规模达到某个阈值，这些能力会涌现出来。

# （二）BERT 家族：Encoder-only 的理解之王

BERT（Bidirectional Encoder Representations from Transformers）由 Google 在 2018 年提出，走的是 Encoder-only 路线。

模型改进点适用场景
BERT原始模型，双向 Masked Language Model文本分类、NER、问答
RoBERTa更优训练策略（更大 Batch、更多数据、更长训练）通用理解任务，效果优于 BERT
ALBERT参数共享 + 分解嵌入资源受限场景
DistilBERT知识蒸馏，模型大小减半需要快速推理的场景
ERNIE知识增强，引入实体和知识图谱中文理解任务

BERT vs GPT 的路线之争：

BERT 是"理解型"的——它像一位仔细阅读者，把文章从左到右、从右到左读两遍，深刻理解每个词的含义。适合做分类、抽取、匹配等"理解任务"。

GPT 是"生成型"的——它像一位作家，根据已写的内容，一个字一个字地往下写。适合做写作、对话、翻译等"生成任务"。

在大模型时代，GPT 路线（Decoder-only）成为主流，因为生成能力更通用、扩展性更好。但 BERT 在理解任务上仍然高效且经济，很多工业场景仍在使用。

开源 vs 闭源的对比：

维度闭源（GPT-4/Claude）开源（LLaMA/Qwen）

AI PM 关注点：

对于大多数产品，先闭源 API 验证需求，再考虑开源私有化是最佳路径。

  • 用 GPT-4 API 快速做 MVP，验证用户是否愿意为大模型功能付费
  • 验证成功后，如果调用量大（月消耗 > 10 万元），考虑切换到开源模型私有化部署
  • 如果数据隐私要求极高（金融、医疗、政务），直接私有化部署

AI PM 关注点：

国内大模型的选择，除了技术能力，还要考虑：

  1. 合规性：是否通过网信办备案？（国内上线必须备案）
  2. 价格：不同厂商 API 价格差异很大，DeepSeek 的价格可能是 GPT-4 的 1/50

  4. 服务稳定性：小厂商模型能力强，但服务稳定性可能不如大厂

# 三、大模型的核心技术：从预训练到对齐，再到生成

大模型不是"一下子就变聪明"的。它的训练是一个层层递进的过程——先让模型学会所有知识，再学会遵循人类意图，最后可靠地帮助人类。

核心思想：先让模型获得广博的知识和能力（预训练），再通过人类反馈不断塑造其行为（对齐），使其成为有用、诚实、无害的智能助手。

下面，我们逐个拆解这六个阶段。

# （一）预训练：让模型"博学"

核心目标：学习世界知识——在海量无标注数据上自监督学习，学习语言的通用表示和知识。

训练任务：Next Token Prediction（预测下一个词）

给定"今天天气"，模型预测下一个词最可能是"很好""不错""晴朗"等。 为了准确预测，模型必须学会：

  • 语法规则（"天气"后面通常接形容词）
  • 世界知识（"今天天气"和"晴朗"相关）
  • 上下文逻辑（如果前文提到"出门"，后面可能接"很好"）

预训练数据的来源：

数据源占比说明
书籍约 10%长文本、叙事连贯、知识密集
网页（Common Crawl）60%+互联网网页抓取，数据量大但质量参差不齐
百科（维基百科等）约 5%高质量、结构化知识
代码（GitHub 等）约 10%训练逻辑推理能力
学术论文约 5%专业领域知识
新闻、对话、其他约 10%时效性信息、口语化表达

数据清洗的重要性：

原始互联网数据充斥着垃圾信息、重复内容、低质量文本。数据清洗是预训练中最耗时耗力的工作之一。

好的数据清洗能把"模型能力"提升 20% 以上——这比改架构更有效。

类比：给学生喂教科书 vs 喂垃圾小广告，学习效果天差地别。

预训练 outputs——基础模型（Base Model）：

预训练完成后，我们得到一个"博学但不懂规矩"的基座模型。它知道"量子纠缠"是什么，知道"唐诗宋词"怎么写，知道"Python 代码"怎么编——但你问它"你好"，它可能继续接"今天天气很好，适合出去散步"，而不是回应你的问候。

它像一个读完了全人类书籍的"书呆子"：知识渊博，但不知道如何与人交流。

AI PM 关注点：

如果你在做垂直领域的大模型产品（如法律、医疗、金融），预训练数据的质量比模型架构更重要。

  • 通用大模型 + 领域数据微调，通常比从零训练一个领域模型更经济
  • 领域数据的获取和清洗是最大的壁垒

# （二）监督微调（SFT）：让模型"听懂指令"

核心目标：学会遵循指令——使用高质量的人工标注数据，让模型学会遵循指令、以助手的身份回应用户。

预训练后的基座模型虽然"知识丰富"，但它不懂"对话"。你问它"你好"，它可能继续预测"今天天气很好"，而不是回答"你好！有什么可以帮你的？"

SFT 的数据是什么样子的？

SFT 使用的是高质量指令数据，即"指令 + 回答"的配对：

指令：解释量子纠缠是什么？
回答：量子纠缠是指两个或多个粒子之间...

指令：写一首关于春天的五言绝句。
回答：春风拂面柳丝长，花开大地换新装...

指令：请帮我写一封辞职信。
回答：好的，以下是一封辞职信模板：
尊敬的[领导姓名]：
您好！

SFT 的数据质量要求：

维度要求
多样性覆盖各种任务类型（问答、写作、翻译、代码、推理等）
质量回答要准确、有帮助、格式规范
安全性不能包含有害内容、偏见、错误信息
数量通常 10 万-100 万条高质量对话对

SFT 的直觉：

预训练就像让一个学生读完了全人类的书——他知识渊博，但不知道怎么和人交流。

SFT 就像给他上了"礼仪课"和"沟通课"——教他如何礼貌地回应、如何理解用户的意图、如何组织清晰的回答。更重要的是，教他**"用户问什么，我就答什么"**，而不是继续"预测下一个词"。

SFT outputs——SFT 模型：

SFT 后的模型已经能进行基本的对话了。你问它问题，它会以"助手"的身份回答你。但它的回答质量还不够稳定——有时候很好，有时候一般，有时候可能带有偏见或不安全的内容。

# （三）奖励模型（RM）：让模型"知道好坏"

核心目标：学习人类偏好——通过比较不同回答的质量，训练一个能给回答打分的"裁判模型"。

为什么需要奖励模型？

SFT 的数据量有限，标注人员的回答不一定是"最优"的——可能太啰嗦、可能有偏见、可能对某些群体不友好。

更重要的是，我们需要一个自动化的评分机制，能够在训练过程中实时告诉模型"这个回答好，那个回答不好"。人工标注显然无法在训练时实时进行，所以我们训练一个模型来替代人类做这件事。

奖励模型的训练数据——比较数据（人工标注偏好）：

对于同一个问题，让模型生成多个不同的回答，然后由人类标注员对这些回答进行排序。

例如，对于指令"如何提高学习效率？"

  • 回答 A：制定计划、专注学习、定期复习、保证睡眠...（详细、有条理、可操作）
  • 回答 B：多学习、多做题、时间管理很重要...（简略、泛泛而谈）

人类标注：A 更好。

收集成千上万组这样的"比较数据"，用来训练奖励模型。

奖励模型的作用——RM 模型（打分器）：

奖励模型本质上是一个"打分器"。输入一个问题和一个回答，它输出一个分数——分数越高，表示这个回答越符合人类偏好。

类比：奥运会上的裁判。跳水运动员做完动作，裁判打分。奖励模型就是那个裁判——它学会了人类的评分标准，可以自动给模型的回答"打分"。

AI PM 关注点：

奖励模型的质量直接决定了 RLHF 的效果。如果奖励模型"品味"不行（比如喜欢冗长但空洞的回答），那训练出来的模型也会继承这种"坏品味"。

  • 奖励模型的训练数据需要覆盖多样性场景
  • 标注标准需要统一且清晰
  • 奖励模型本身也可能有偏见，需要持续迭代优化

  • 小狗伸出爪子（生成回答）
  • 你给零食（奖励模型打高分）→ 小狗记住"这样做有好吃的"

  2. 标注偏见：标注员的偏好可能带有文化偏见，模型会学到这些偏见

AI PM 关注点：

RLHF 是模型"人格化"的关键。同一个基座模型，用不同的 RLHF 数据，可以训练出：

  • 一个乐于助人的助手（ChatGPT）
  • 一个谨慎保守的顾问（某些企业版模型）
  • 一个幽默风趣的伙伴（某些娱乐向模型）

如果你在做面向特定用户群体的产品，自定义 RLHF 是差异化竞争的关键。

# （五）对齐后的模型：可靠可用，符合人类期望

对齐后模型的特征：

特征英文说明

对齐的本质：

对齐不是让模型"变得更聪明"——它的知识量在预训练后就基本确定了。对齐是让模型**"学会如何正确地使用它的知识"**。

类比：一个医术高明的医生（预训练），如果态度恶劣、乱开药方、歧视病人，那他对社会的价值甚至是负的。对齐就是给这位医生做"医德培训"——教他如何礼貌地对待病人、如何根据病情合理开药、如何保护病人隐私。

# 补充：DPO——RLHF 的简化替代方案

RLHF 实现复杂，需要单独训练奖励模型 + 强化学习算法。DPO（Direct Preference Optimization）是一种更简单的替代方案。

核心思想：直接把"人类偏好"变成损失函数，跳过奖励模型和强化学习，用偏好数据直接训练模型。

方法复杂度效果适用场景
RLHF（PPO）高（需要奖励模型 + PPO 算法）好资源充足、追求极致效果
DPO低（直接用偏好数据训练）接近 RLHF资源有限、快速迭代
KTO中好只需要二元反馈（好/坏），不需要排序

AI PM 关注点：

对于大多数团队，DPO 是性价比最高的对齐方案——实现简单、效果接近 RLHF、训练稳定。如果你的团队没有专门的强化学习工程师，优先考虑 DPO。

# 四、涌现能力：量变引起质变

# （一）什么是涌现能力？

涌现能力（Emergent Abilities）是大模型最迷人的现象之一：当模型规模超过某个阈值后，会突然出现小模型完全不具备的能力。

类比：

想象你在往一个杯子里倒水：

  • 0-50ml：杯子底部有点湿（小模型能做一些简单任务）
  • 50-80ml：水在杯底聚集，但没什么特别（中等模型效果稍好）
  • 80ml：突然，水开始形成明显的水面，能倒映出周围的景象（涌现！）

水面倒影不是"慢慢变好"的——它是水达到一定量后"突然出现"的性质。

# （二）典型的涌现能力

能力小模型（<10B）大模型（>100B）产品意义
上下文学习（ICL）给例子也没用，还是乱答给几个例子就能学会新任务不用训练就能适配新场景
思维链（CoT）直接给答案，经常错能一步步推理，复杂问题准确率大幅提升数学、逻辑、代码任务
指令遵循听不懂复杂指令能理解多步骤、有约束的指令复杂任务自动化
代码生成语法错误百出能写完整函数、甚至完整项目Copilot、自动化编程
多语言翻译简单句子还行，复杂句不行能处理俚语、文化差异全球化产品
常识推理经常违反常识能做出符合常识的判断对话机器人更自然

上下文学习（In-Context Learning, ICL）的直觉：

你教一个 3 岁小孩认颜色：

  • 小模型：你告诉他"这是红色"，他点点头。你再给他看一个红色的球，他问"这是什么？"——他记不住。
  • 大模型：你告诉他"苹果是红色，香蕉是黄色"，然后他就能立刻判断"草莓是红色，柠檬是黄色"——他通过几个例子就"学会"了颜色的概念。

大模型不需要重新训练，只需要在 Prompt 里给几个示例，就能"现场学会"新任务。

思维链（Chain-of-Thought, CoT）的直觉：

问：一个农场有 35 只鸡和 28 只兔，一共有多少条腿？

  • 小模型：35 + 28 = 63，63 × 4 = 252（错！它以为所有动物都是 4 条腿）
  • 大模型（不加 CoT）：可能也错
  • 大模型（加 CoT）："鸡有 2 条腿，35 只鸡有 35 × 2 = 70 条腿。兔有 4 条腿，28 只兔有 28 × 4 = 112 条腿。总共有 70 + 112 = 182 条腿。"（对！）

关键发现：只要在 Prompt 里加一句"让我们一步步思考"（Let's think step by step），大模型的推理能力就会大幅提升。

涌现能力意味着：模型选型时，规模很重要。

  • 如果你只需要文本分类、情感分析，7B 模型可能就够了
  • 如果你需要复杂推理、代码生成，至少需要 30B 以上
  • 但要注意：不是越大越好——大模型推理成本高，如果小模型能做的事，不要上大模型

# 六、大模型的局限性：知道边界才能做好产品

# （一）幻觉（Hallucination）：一本正经地胡说八道

什么是幻觉？

大模型会生成看似合理、逻辑通顺，但实际错误甚至完全虚构的内容。

例子：

  • 用户："请介绍一下张三教授的研究成果。"
  • 模型："张三教授是清华大学的知名学者，主要研究量子计算，曾获得 2019 年国家自然科学奖一等奖……"
  • 事实：根本没有张三这个人，或者他的研究方向完全不是量子计算。

幻觉的类型：

类型说明例子
事实性幻觉编造不存在的事实虚构人物、虚构论文、虚构数据
忠实性幻觉和输入/上下文不一致摘要时加入原文没有的内容
来源幻觉编造信息来源"根据《Nature》2023 年的研究……"（该论文不存在）

为什么会产生幻觉？

大模型的训练目标是"生成听起来合理的文本"，而不是"生成绝对真实的文本"。

类比：一个读过很多小说的作家，你让他写一段历史。他可能会把小说情节和历史事实混在一起，写得非常精彩——但历史学者看了会皱眉。

降低幻觉的方法：

方法原理效果
RAG（检索增强生成）先检索真实信息，再让模型基于检索结果回答效果显著，推荐首选
事实核查（Fact-checking）生成后用另一个模型核查事实有效，但增加延迟和成本
约束生成限制模型只能输出检索到的内容很有效，但降低灵活性
提示工程让模型"不确定就说不知道"有一定效果
微调用高质量数据训练模型更谨慎效果有限，难以根治

AI PM 的核心判断：

幻觉是大模型产品的头号风险。

  • 做医疗诊断、法律咨询、金融建议的产品，必须做严格的事实核查
  • 做创意写作、头脑风暴的产品，幻觉反而可能是"灵感"
  • 永远不要让大模型单独做高风险决策，必须有人工审核或系统兜底

成本计算示例：

一个客服机器人，每天处理 10 万条用户咨询：

  • 平均每次对话 2000 Token（输入+输出）
  • 用 GPT-4：10 万 × 2000 × $0.045 / 1000 = $9,000/天 = $270,000/月
  • 用 GPT-3.5 Turbo：10 万 × 2000 × $0.001 / 1000 = $2,000/天 = $60,000/月
  • 用 DeepSeek-V2：10 万 × 2000 × $0.0002 / 1000 = $400/天 = $12,000/月

降本策略：

策略说明效果
模型路由简单问题用小模型，复杂问题用大模型成本降 50-80%
缓存相同问题直接返回缓存答案成本降 20-50%
Prompt 压缩减少输入 Token 数直接降低输入成本
输出限制限制最大输出长度直接降低输出成本
量化部署用 8bit/4bit 量化模型推理速度提升，成本降低
混合专家（MoE）每次只激活部分参数如 DeepSeek-V2，成本极低

# （四）对齐税与过度保守

为了让模型"安全"，RLHF 可能让模型变得过于保守：

  • 用户："如何制作炸弹？" → 模型拒绝回答（正确）
  • 用户："请分析一下炸药在采矿中的工业应用" → 模型也拒绝（过度保守）
  • 用户："写一段反派角色制造陷阱的剧情" → 模型可能拒绝（误判为有害）

产品启示：

如果你的产品需要模型处理敏感但合法的内容（如医疗、法律、文学创作），需要：

  • 选择对齐程度适中的模型
  • 设计精细的审核策略，而不是"一刀切"拒绝
  • 考虑私有化部署，自定义安全策略

# （二）Prompt Engineering：不用训练就能优化效果

Prompt Engineering 是在不修改模型的情况下，通过优化输入来提升输出质量。

核心技巧：

技巧说明效果
Zero-shot直接给指令，不给示例基础能力
Few-shot给 2-5 个输入输出示例通常显著提升
Chain-of-Thought让模型"一步步想"数学、推理任务大幅提升
角色扮演"你是一位资深律师……"提升专业性和语气
输出格式约束"请用 JSON 格式输出"提升结构化输出稳定性
Self-Consistency多次采样，选最一致的答案准确率提升
ReAct让模型交替"思考"和"行动"需要调用工具的任务

Prompt 设计原则：

  1. 具体比笼统好："写一篇关于 AI 的文章" → "写一篇 800 字的科普文章，面向高中生，介绍什么是大模型，用类比解释，语言轻松幽默"
  2. 给框架比给自由好：提供结构化的输出模板
  3. 说"做什么"比说"不做什么"好："请用正式语气" 比 "不要用口语" 更有效
  4. Few-shot 示例要典型：示例质量直接决定输出质量

# （三）RAG：大模型 + 知识库 = 减少幻觉的利器

RAG（Retrieval-Augmented Generation，检索增强生成）是当前大模型产品落地的核心技术之一。

RAG 的核心流程：

用户提问
    ↓
检索模块：从知识库中找出最相关的文档片段
    ↓
大模型：基于检索到的内容生成回答
    ↓
用户收到回答

为什么 RAG 有效？

  1. 减少幻觉：模型基于真实检索到的内容回答，而不是"编造"
  2. 知识实时更新：知识库可以随时更新，不需要重新训练模型
  3. 可溯源：能告诉用户"这个回答来自哪份文档"
  4. 成本低：比微调便宜得多

RAG 的关键组件：

组件作用技术选型
文档加载把各种格式的文档读入系统LangChain Document Loaders
文本分块把长文档切成小段按段落、按 Token、按语义
向量化把文本变成向量OpenAI Embedding、BGE、M3E
向量数据库存储和检索向量Milvus、Pinecone、Qdrant、PGVector
重排序对检索结果精排Cross-Encoder、Cohere Rerank
生成基于检索内容生成回答GPT-4 / Claude / 开源模型

AI PM 关注点：

RAG 不是"万能药"：

  • 检索质量决定了回答质量——" garbage in, garbage out"
  • 复杂的多文档推理仍然是挑战
  • 需要精心设计 Prompt，引导模型基于检索内容回答，而不是"自由发挥"

# （四）Function Calling / Tool Use：让大模型"动手"

Function Calling 让大模型能够调用外部函数/API，获取实时数据或执行操作。

典型应用场景：

场景函数示例
查天气get_weather(city="北京", date="今天")
查股票get_stock_price(symbol="AAPL")
查数据库query_database(sql="SELECT * FROM orders WHERE ...")
发邮件send_email(to="user@example.com", subject="...", body="...")
创建日历事件create_calendar_event(title="会议", start_time="...")

工作流程：

用户："帮我查一下明天北京的天气，如果下雨就提醒我带伞"
    ↓
模型分析：需要调用 get_weather 函数
    ↓
模型输出函数调用：{"function": "get_weather", "arguments": {"city": "北京", "date": "明天"}}
    ↓
系统执行函数，返回结果：{"weather": "小雨", "temperature": "15-22℃"}
    ↓
模型基于结果生成回答："明天北京有小雨，气温 15-22℃，记得带伞哦！"

# （五）成本与效果的权衡

做大模型产品，最核心的 PM 能力之一是成本-效果权衡。

案例分析：

你在做一个智能客服产品：

  • 方案 A：全部用 GPT-4，准确率 92%，月成本 ¥50 万
  • 方案 B：简单问题用 GPT-3.5，复杂问题用 GPT-4，准确率 88%，月成本 ¥15 万
  • 方案 C：用开源 13B 模型 + 微调，准确率 82%，月成本 ¥3 万

如何选择？

  • 如果客服的主要价值是"降低人力成本"→ 方案 B 或 C，准确率不需要最高
  • 如果客服涉及高客单价销售转化→ 方案 A 或 B，准确率直接影响收入
  • 如果预算极其有限→ 方案 C 先跑起来，再逐步升级

降本增效的最佳实践：

策略适用场景预期效果
模型路由问题复杂度差异大降本 50-80%，效果损失 < 5%
Prompt 缓存重复性问题多降本 20-40%
流式输出长文本生成提升用户体验，不减成本
批处理非实时任务降低单位成本
模型蒸馏已有大模型效果验证用小模型达到大模型 90% 效果

# 九、小结

# 本节核心要点

  1. 大模型的本质：通过海量数据预训练获得通用能力，一个模型通过 Prompt/Few-shot 适配无数任务，从"专用"走向"通用"。

  2. 三大训练阶段：预训练（学语言规律）→ SFT（学对话方式）→ RLHF（对齐人类偏好）。

  3. 涌现能力：当模型规模超过阈值，会突然出现小模型不具备的能力（ICL、CoT、复杂推理等）。

  4. 选型原则：先闭源 API 验证需求，再考虑开源私有化；简单任务用小模型，复杂任务用大模型；模型路由是降本增效的关键。

  5. 产品化核心工具：Prompt Engineering、RAG、Function Calling。三者组合能解决 80% 的大模型产品需求。

  6. 头号风险是幻觉：必须通过 RAG、事实核查、人工审核等手段控制。高风险场景不能让大模型独自决策。

  7. 成本是核心约束：大模型推理成本高，需要通过模型路由、缓存、量化等手段优化。

  8. Agent 是未来方向：让大模型从"回答问题"走向"执行任务"，但目前仍处于早期，建议从半自动开始。

# 给 AI PM 的一句话

大模型是 AI 产品的"新基建"——它不是一种特定的功能，而是一种通用的能力引擎。作为 AI PM，你不需要会训练大模型，但你需要知道：它能做什么、不能做什么、选哪个模型、花多少钱、以及如何把它安全有效地产品化。大模型的技术迭代极快，今天的前沿技术可能半年后就成了标配。保持好奇心、持续实践、多和算法团队交流，是你在这个快速变化的领域保持竞争力的最好方式。
