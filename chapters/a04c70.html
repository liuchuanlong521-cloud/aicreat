核心考点

前言

在《Token 详解》中，我们已经理解了 Token 是什么——它是大模型的"文字积木"，是模型处理文本的最小单元。

但这一节，我们要换一个视角：Token 不仅是技术概念，更是商业概念。 每一千个 Token 的输入和输出，都对应着真实的账单金额。一次用户请求背后，可能是几分钱的成本，也可能是几块钱的成本。

作为 AI 产品经理，如果你不懂 Token 成本，你会遇到这些困境：

  • 产品上线后，发现每次 API 调用的成本比预期高 10 倍
  • 给用户定价时，根本不知道"一个月 99 元"是赚是亏
  • 技术团队说"换个大模型效果更好了"，你无法判断成本增幅是否合理
  • 投资人问"你们的单位经济模型是什么"，你答不上来

本文将从商业视角，系统讲解 Token 成本的构成、计算方法、优化策略，以及它如何影响你的产品决策。

# 一、Token 成本的构成：你的钱花在哪了？

# （一）API 计费的基本单元

大模型 API 的计费非常简单，只有两个维度：

总成本 = 输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价
1
维度说明示例
输入 Token（Input）你发给模型的所有内容：用户提问 + 系统 Prompt + 上下文历史 + 检索到的知识用户问"总结一下这篇文章"，你附带了一篇 2000 字的文章 → 输入约 1500 Token
输出 Token（Output）模型返回给你的内容模型返回了一段 500 字的总结 → 输出约 400 Token

关键认知：

  • 输出通常比输入贵：因为生成输出需要模型逐个 Token 进行概率计算，计算成本更高
  • 输入单价 ≈ 输出单价的 1/3 到 1/2（大多数模型）
  • 上下文历史也算输入：多轮对话中，之前说的每一句话都会被重复计费

# （二）隐藏的成本杀手

除了显而易见的"输入+输出"，还有一些容易被忽视的成本来源：

# 1. 系统 Prompt 的固定开销

每次请求，你都需要在底层附加一段系统 Prompt（角色设定、格式要求、约束条件）。这段 Prompt 可能长达几百甚至上千 Token，每次请求都要计费。

固定开销占比：如果你的系统 Prompt 有 800 Token，每次请求都要多花这 800 Token 的钱。对于短请求来说，这可能占总成本的 50% 以上。

# 2. 多轮对话的"滚雪球"效应

多轮对话中，每一轮都要把之前的对话历史重新发送给模型：

Round 1：用户问 A → 模型答 A'（计费：输入 100 + 输出 200）
Round 2：用户问 B → 模型答 B'（计费：输入 100+200+100 + 输出 200）
Round 3：用户问 C → 模型答 C'（计费：输入 100+200+100+200+100 + 输出 200）

到第 10 轮对话时，输入 Token 可能已经膨胀到 3000+，而实际新增的用户提问只有 100 Token。

系统 Prompt：800 Token
检索到的文档片段：2000 Token（可能来自 5 篇相关文档）
─────────────────────────────
实际输入：2850 Token

如果 RAG 策略不好，检索到的内容冗余、重复，这部分成本就会被白白浪费。

# 4. 重试和失败请求的沉没成本

模型调用可能因网络、超时、内容审核等原因失败。失败后你通常会重试，失败的请求也可能计费（取决于厂商政策）。

# （二）月度总成本的估算方法

月度总成本 = 单次请求平均成本 × 月均请求次数 × 并发系数
1

案例：AI 写作助手

假设你的产品是一个 AI 写作助手，有 10 万月活用户：

参数估算值说明
月活用户100,000
人均月使用次数20 次每周用 4-5 次
月均总请求数2,000,000
单次平均成本（DeepSeek-V3）¥0.01含输入输出平均
月度 API 成本¥20,000
加上重试/失败（10%）¥22,000
加上高峰期冗余（20%）¥26,400

换算到每个用户的单月成本：

单用户单月成本 = ¥26,400 / 100,000 = ¥0.264（约 2 毛 6）
1

这意味着：如果你给用户定价"每月 9.9 元"，API 成本占比约 2.7%，还有很大的毛利空间。但如果你定价"每月 1 元"，API 成本就占了 26%，加上服务器、人力、运营，大概率亏损。

# 四、降低 Token 成本的 10 个实战策略

# 策略 1：精简系统 Prompt

原理：系统 Prompt 是每次请求的固定开销。

做法：

  • 删除冗余的修饰词和示例
  • 用结构化格式替代自然语言描述
  • 把通用指令移到模型训练或微调中，而不是每次请求都带

效果：系统 Prompt 从 800 Token 压缩到 300 Token，单次成本降低 30-50%。

# 策略 2：多轮对话压缩

原理：对话历史越长，输入 Token 越多。

做法：

  • 对历史对话做摘要，用 200 Token 的摘要替代 2000 Token 的原文
  • 只保留最近 3-5 轮对话，更早的丢弃或归档
  • 显式保留关键约束信息（如用户说过的"预算 1000 元"），其他细节摘要

效果：第 10 轮对话的输入 Token 从 4000+ 降到 1500，成本降低 60%+。

# 策略 3：RAG 结果去重与截断

原理：RAG 检索到的内容经常有冗余。

做法：

  • 对检索结果做语义去重，删除内容高度相似的段落
  • 设置单段最大长度，避免整篇文章被塞进去
  • 按相关度排序后，只取 Top 3-5 段最相关的内容

效果：RAG 检索从 2000 Token 降到 800 Token，成本降低 60%。

# 策略 4：模型分层调度

原理：不是所有任务都需要最强、最贵的模型。

做法：

  • 简单任务（格式化、分类、短回答）→ 轻量模型（Gemini Flash、DeepSeek-V3）
  • 中等任务（文案生成、常规问答）→ 主力模型（GPT-4o、Claude Sonnet）
  • 复杂任务（深度推理、创意策划）→ 旗舰模型（GPT-4o、Claude Opus）

效果：70% 的请求可以用轻量模型处理，整体成本降低 50-70%。

# 策略 5：输出长度控制

原理：输出 Token 通常比输入贵 3-5 倍。

做法：

  • 在 Prompt 中明确要求输出字数/段落数
  • 设置 max_tokens 参数，硬限制输出上限
  • 对长文生成采用"分段生成"策略，而不是一次写完

效果：输出从 1000 Token 控制到 300 Token，成本降低 70%。

# 策略 6：Prompt Caching（缓存复用）

原理：如果多次请求中有一部分上下文是固定的（如系统 Prompt + 知识库），可以缓存这部分，避免重复计费。

做法：

  • 使用支持 Prompt Caching 的厂商（如 Anthropic、OpenAI）
  • 把不变的上下文前置并标记为缓存
  • 缓存后的输入价格通常降低 50-90%

效果：对于高频重复场景（如客服用同一套知识库回答不同用户），成本可降低 40-60%。

# 策略 7：Batch 批处理

原理：把多个请求打包成一批提交，享受批量折扣。

适用场景：

  • 批量生成商品描述
  • 批量处理用户反馈分类
  • 批量数据分析

效果：批量处理通常有 25-50% 的价格折扣。

# 策略 8：本地/私有化部署

原理：对于高频、标准化的任务，自建模型比调用 API 更便宜。

适用场景：

  • 日均调用量超过 100 万次的业务
  • 对数据隐私要求极高的场景（金融、医疗）
  • 效果要求不极端、可用开源模型满足的场景

成本对比：

API 调用成本：¥0.001/次 × 1,000,000 次/天 = ¥1000/天
私有化部署：一次性硬件投入 + 电费运维 ≈ ¥200/天（均摊后）
1
2

# 策略 9：用户输入预处理

原理：用户的原始输入往往冗余、混乱，预处理后再发给模型。

做法：

  • 删除输入中的无意义符号、重复空格
  • 对用户上传的长文档做摘要或分段
  • 对图片/语音输入，先用专用模型提取文字，而不是直接给多模态模型

效果：输入 Token 减少 20-40%。

# 策略 10： Fallback 降级机制

原理：当主力模型不可用时，自动切换到备用模型，避免重试带来的成本浪费。

做法：

  • 主模型超时/失败 → 切换到同厂商的轻量模型
  • 极端情况下 → 切换到缓存的预设回答或规则引擎
  • 避免反复重试同一个失败的请求

# 五、Token 成本如何影响产品决策

# （一）产品功能设计

案例 1：免费试用额度

你想给新用户每天 10 次免费使用额度。

用 GPT-4o：10 次 × ¥0.05 = ¥0.5/人/天，1 万新用户就是 ¥5000/天 用 DeepSeek-V3：10 次 × ¥0.006 = ¥0.06/人/天，1 万新用户就是 ¥600/天

决策：免费额度策略必须绑定轻量模型，或者限制每次请求的上下文长度。

案例 2：功能开关

你的产品有一个"深度分析"功能，需要调用旗舰模型，单次成本 ¥0.5。 普通问答功能单次成本 ¥0.01。

决策："深度分析"不能免费开放，需要放在付费档，或者限制使用次数。

# （二）商业模式选择

商业模式Token 成本影响关键考量
按次付费直接对应每次 API 成本定价要覆盖成本 + 毛利，用户用量不可控
订阅制重度用户可能"用回本"，导致亏损需要设置使用上限或分层权益
免费增值免费用户的成本是沉没成本严格控制免费档的功能和用量
企业定制大客户用量大，议价空间大需要精确估算客户的月均 Token 消耗

# （三）技术方案选型

场景：产品需要做一个"文档智能问答"功能。

方案技术路线单次成本估算适用场景
方案 AGPT-4o + 全文塞进 Prompt¥0.15/次文档很短（< 5000 字），追求极致效果
方案 BDeepSeek-V3 + RAG 检索¥0.015/次文档很长，追求性价比

AI PM 的决策逻辑：

  1. 先定义"效果达标线"——准确率需要达到多少？
  2. 再评估各方案的成本——单用户月均成本是多少？
  3. 最后结合商业模式——这个成本结构能否盈利？

# 六、写在最后

Token 成本是 AI 产品的"原材料成本"。在传统软件中，多服务一个用户的边际成本几乎为零；但在 AI 产品中，每一次用户交互都伴随着真实的 API 费用。

这意味着：

  1. 规模化 ≠ 自动盈利：用户越多，API 账单越大。如果单位经济模型不健康，规模越大亏得越多。
  2. 模型选择是商业决策：不是用最强的模型就好，而是用"足够好且足够便宜"的模型。
  3. 成本优化是持续过程：从系统 Prompt 的 100 个字符，到 RAG 检索策略的阈值调整，每个细节都在影响成本。

核心考点

给 AI PM 的实用建议

上线前：用真实数据跑 1000 次请求，算出平均单次成本，乘以预期月活，得出月度 API 预算。

上线后：监控"单用户单次平均 Token 数"和"单用户月均 API 成本"，设置成本异常告警。

优化时：每次做成本优化前，先 A/B 测试效果变化——省下的钱不能牺牲用户体验。

Token 成本不是技术团队的专属议题。它是 AI 产品经理必须掌握的商业基本功。下一节，我们将探讨另一个商业必谈话题——AI 产品的定价策略。
