核心考点

前言

很多人想转 AI PM，但问的第一个问题是："AI PM 每天都在干什么？" 这个看似简单的问题，答案却比你想象的复杂——因为不同类型的 AI PM，每天干的事完全不同。

应用层的 AI PM 在跑客户、调 Prompt、看 Badcase；技术层的 AI PM 在定义模型能力、设计评测体系；Agent 层的 AI PM 在编排任务流、管理 Skills 库。每一类的工作内容、协作对象、产出物都不一样。

本节的目标：用尽可能真实、详细的描述，让你对每一类 AI PM 的日常工作有具体的体感——不是抽象的概念，而是"今天早上我做了什么、下午开了什么会、晚上在看什么数据"的真实画面。

# 一、AI PM 的分类体系

在讲具体工作内容之前，先建立一个清晰的分类坐标系。AI PM 的分类有两个维度：

# （一）纵向：产业层级

层级PM 类型核心工作
应用层（下游）业务/解决方案 PM将 AI 落地到具体场景，创造用户价值
技术层（中游）平台 PM / 模型策略 PM研发 AI 算法和平台，提供开发工具
基础层（上游）数据 PM / 基础设施 PM提供算力和数据支撑
Agent 层（新兴）Agent / Skills 策展 PM设计 Agent 工作流，管理企业 Skills 库

# （二）横向：客户类型

类型核心特征
ToB（企业级）降本增效、准确性要求高、决策周期长
ToC（消费级）情绪价值、低门槛、快速迭代

# （三）本文的分类展开方式

本文按产业层级 + 客户类型的组合来展开，覆盖市面上 90% 以上的 AI PM 岗位：

  1. 应用层 ToB PM — 企业知识库、智能客服、合同审查等
  2. 应用层 ToC PM — AI 绘画、AI 陪伴、AI 搜索等
  3. 技术层-平台 PM — AI 开发平台、低代码工具
  4. 技术层-模型/算法策略 PM — 大模型能力定义、推荐策略
  5. 基础层-数据 PM — 数据标注平台、数据集管理
  6. 基础层-基础设施 PM — AI 芯片、云计算实例
  7. Agent / Skills 策展 PM — Agent 工作流设计、Skills 库管理

# 二、应用层 ToB PM：每天在和"准确性"死磕

# （一）岗位画像

维度内容
核心目标用 AI 帮助企业降本增效
典型产品企业知识库、智能客服、合同审查、代码助手、智能投顾
核心挑战准确性必须高（≥95%），容错率低
决策周期长（3-12 个月签一个客户）
协作对象客户、销售、算法、研发、法务、合规

# （二）典型一天的工作内容

# 上午 9:00-12:00

9:00-9:30 看数据

  • 打开 BI 看板，查看昨天的核心指标：
    • 客户 A 的智能客服准确率：93.2%（目标 95%，低于预期）
    • 客户 B 的企业知识库检索成功率：87%（正常）
    • 整体 API 调用量：12.3 万次（比上月增长 15%）
  • 发现客户 A 的准确率下降了，标记为今天重点跟进项

9:30-10:30 处理 Badcase

  • 打开 Badcase 管理平台，筛选客户 A 昨天新增的 47 个 Badcase
  • 分类分析：
    • 答非所问：23 个（占比 49%）→ 可能是 Prompt 不够明确
    • 幻觉（编造信息）：8 个（占比 17%）→ 严重，需要立即处理
    • 回答不完整：12 个（占比 26%）→ 可能是上下文窗口限制
    • 其他：4 个
  • 把 8 个幻觉 case 发给算法团队，附上分析结论和优化建议

10:30-12:00 客户沟通

  • 和客户 A 的 IT 负责人开周会
  • 客户反馈："AI 客服最近答非所问的情况变多了，我们的用户投诉增加了"
  • 展示数据分析：准确率从 96% 降到 93%，主要原因是上周更新了知识库，新文档的格式不统一导致 RAG 检索效果下降
  • 给出解决方案：
    • 短期：优化知识库的文档切分策略（2 天内完成）
    • 中期：补充 500 条 FAQ 标注数据（1 周内完成）
    • 长期：升级 RAG 检索模型（下个月排期）
  • 客户满意，同意方案

# 下午 14:00-18:00

14:00-15:30 写 PRD

  • 正在做一个新功能："智能工单分类"
  • 需求背景：客户 C 的客服团队每天收到 2000+ 工单，人工分类耗时耗力
  • PRD 内容：
    • 功能目标：AI 自动识别工单类型，准确率达到 92% 以上
    • 分类体系：技术支持、 billing 问题、产品咨询、投诉建议（4 大类，12 小类）
    • 交互设计：工单提交后 AI 自动打标签，客服可修改
    • 评估标准：准确率、召回率、F1 值
    • 兜底策略：置信度低于 80% 时，标记为"待人工分类"
    • 数据需求：需要 5000 条已标注的工单数据

15:30-16:30 需求评审

  • 召集算法、研发、测试评审"智能工单分类"PRD
  • 算法同学提问："5000 条数据够不够？我们之前的项目用了 2 万条才达到 90%"
  • 回应："先跑 baseline，如果不够再补充。我们分阶段交付：先用 5000 条训练 v1，准确率达标就上线，不达标再补充数据训练 v2。"
  • 研发同学提问："工单数据涉及客户隐私，怎么处理？"
  • 回应："数据脱敏后再用于训练，PII 字段（手机号、邮箱）替换为占位符。详见 PRD 第 3.2 节数据安全方案。"
  • 评审通过，排期 3 周开发 + 1 周测试

16:30-18:00 技术沟通

  • 和算法同学讨论客户 A 的幻觉问题
  • 算法反馈："知识库更新后，文档切分的 chunk size 从 500 token 变成了 800 token，导致检索时的语义匹配度下降"
  • 讨论优化方案：
    • 方案 A：调回 500 token（简单，但可能影响长文档的理解）
    • 方案 B：采用滑动窗口切分（效果更好，但计算成本增加 20%）
    • 方案 C：混合策略（短文档 500 token，长文档 800 token + 重叠）
  • 决策：先用方案 A 快速验证（2 天），如果效果不够再用方案 C（1 周）
  • 产出：优化任务单，明确责任人和时间节点

# 晚上 19:00-20:00（可选加班）

看行业动态

  • 浏览机器之心、InfoQ，看看有没有新的 RAG 技术突破
  • 今天看到一篇关于"多路召回 + 重排序"的论文，可能适用于客户 B 的知识库场景
  • 标记为下周技术分享会的议题

# （四）典型产品案例详解

# 案例：企业知识库 AI PM 的一天

产品背景：为一家 5000 人规模的制造企业搭建内部知识库 AI，员工可以通过自然语言查询技术文档、操作手册、规章制度。

上午：

  • 9:00 查看昨天的使用数据：DAU 3200 人（目标 4000），平均查询 5.2 次/人
  • 9:30 分析低活跃度原因：发现产线工人的查询量很低，原因是他们更习惯语音输入，但当前产品只支持文字
  • 10:00 决定：新增语音输入功能，纳入下个迭代
  • 10:30 和销售沟通一个新客户需求：某金融公司也想做知识库，但要求私有化部署
  • 11:00 评估私有化部署成本：服务器 ¥50 万/年，运维 ¥20 万/年，总成本 ¥70 万/年，报价 ¥120 万/年，毛利 ¥50 万
  • 11:30 写报价方案，发给销售

下午：

  • 14:00 和算法团队讨论 RAG 优化：当前检索准确率 82%，目标是 90%
  • 15:00 发现一个问题：技术文档中的表格数据检索效果很差，因为表格被切分成纯文本后丢失了结构信息
  • 15:30 和算法同学一起设计解决方案：保留表格的 HTML 结构，检索时优先匹配表格标题
  • 16:00 写技术需求文档，排期 2 周
  • 17:00 测试新上线的"文档自动更新"功能：知识库文档过期后自动提醒管理员更新

    • 新增用户：8500（周环比 -5%，需要关注）
    • 付费转化率：4.2%（目标 5%，略低）
    • 用户留存：次日留存 35%，7 日留存 18%
  • 发现新增用户下降了，标记为今天重点

9:30-10:30 用户调研

  • 打开用户反馈后台，筛选昨天的高频反馈：
    • "生成的图片不够好看"（23 条）

    • "希望能自定义角色声音"（15 条）

# 案例：AI 陪伴产品 PM 的一天

产品背景：一款面向年轻人的 AI 陪伴 App，用户可以创建虚拟角色（朋友/恋人/偶像），进行日常聊天互动。

上午：

  • 9:00 看数据：DAU 45 万（目标 50 万），付费率 6.8%，ARPPU ¥35
  • 9:30 发现一个异常：昨晚 11-12 点的活跃用户突增 30%，查原因是某 KOL 在直播间推荐了产品
  • 10:00 和运营沟通：趁热打铁，联系该 KOL 做深度合作（定制专属角色）
  • 10:30 打开用户反馈：大量用户要求"角色能发语音"
  • 11:00 评估技术可行性：TTS 成本 ¥0.05/条，如果 50% 用户使用，日成本约 ¥1.1 万，月收入需要增加 ¥33 万才能 cover
  • 11:30 决定：先给付费用户开放语音功能，作为会员权益

下午：

# （二）典型一天的工作内容

# 上午 9:00-12:00

9:00-9:30 看 Agent 运行数据

  • 打开 Agent 监控看板：
    • 任务完成率：82%（目标 90%，需要提升）
    • 平均任务耗时：4.5 分钟（目标 3 分钟）
    • Skills 复用率：35%（目标 50%，需要提升）
    • 用户满意度：4.0/5
  • 发现任务完成率偏低，标记为重点

9:30-10:30 分析失败任务

  • 打开失败任务日志，筛选高优先级 case
  • 发现一个共性问题：Agent 在"跨系统操作"时经常失败
    • 例：用户要求"把销售数据从 CRM 导出，整理成报表发到邮箱"
    • Agent 能完成"导出 CRM 数据"和"整理报表"，但"发邮件"步骤经常失败
  • 根因：邮件系统的 API 权限变更，Agent 没有处理这种异常
  • 产出：异常处理需求，需要增加"权限检查"和"人工确认"机制

10:30-12:00 设计新 Skill

  • 销售团队反馈："希望 Agent 能自动生成销售周报"
  • 设计 Skill："销售周报生成"
    • 输入：时间范围（上周）、销售数据（CRM）、目标数据（OKR 系统）
    • 处理步骤：
      1. 从 CRM 拉取上周销售数据
      2. 从 OKR 系统拉取本周目标
      3. 计算完成率、同比/环比
      4. 生成周报（包含数据图表、文字分析）
      5. 发送邮件给销售经理
    • 异常处理：如果数据缺失，提示用户补充
    • 人工确认：生成后先给用户预览，确认后再发送
  • 画任务流图，写 Skill 定义文档

# 下午 14:00-18:00

14:00-15:00 Skills 库管理

  • 审查现有的 50 个 Skills，评估使用率和效果
  • 发现 8 个 Skills 使用率低于 5%，决定下线
  • 发现 3 个 Skills 效果评分低于 3.5/5，需要优化
  • 产出：Skills 库管理报告

15:00-16:00 权限设计

  • 和安全团队讨论 Agent 的权限管理
  • 设计"分层授权"机制：
    • L1（只读）：Agent 只能查看数据，不能修改
    • L2（有限操作）：Agent 可以修改指定范围内的数据
    • L3（全权操作）：Agent 可以执行所有操作，但需要人工确认
  • 为不同角色分配默认权限：
    • 普通员工：L1
    • 部门经理：L2
    • 高管：L3
  • 产出：权限设计文档

16:00-17:00 用户访谈

  • 和 3 个销售代表访谈，了解 Agent 使用体验
  • 反馈 1："Agent 生成的周报太模板化了，缺少个性化的洞察"
  • 反馈 2："希望 Agent 能记住我的偏好，比如我喜欢的图表类型"
  • 反馈 3："有时候 Agent 会误解我的指令，希望能先确认再执行"
  • 记录需求，纳入优化清单

17:00-18:00 写优化方案

  • 针对"任务完成率低"问题，设计优化方案：
    • 增加"预检查"机制：Agent 执行任务前，先检查所有依赖条件
    • 增加"分步确认"机制：复杂任务拆分成多个步骤，每步完成后给用户确认
    • 增加"异常处理"机制：遇到异常时，给出清晰的错误信息和解决建议
  • 产出：优化方案文档

# 十一、小结与自查

# 本节核心要点

  1. AI PM 按产业层级分为 7 类：应用层 ToB、应用层 ToC、技术层-平台、技术层-模型、基础层-数据、基础层-基础设施、Agent/Skills 策展
  2. 应用层 ToB PM 每天在和"准确性"死磕：看 Badcase、和客户沟通、写 PRD、优化 Prompt
  3. 应用层 ToC PM 每天在和"用户情绪"打交道：看增长数据、写 Prompt、设计有梗的功能、分析竞品
  4. 技术层-平台 PM 每天在和"开发者体验"较劲：设计 API、写文档、访谈开发者、看竞品
  5. 技术层-模型 PM 每天在和"模型效果"搏斗：看模型数据、分析 Badcase、设计评估体系、A/B 测试
  6. 基础层-数据 PM 每天在和"数据质量"较真：看质量报告、优化标注流程、审查合规、管理供应商
  7. 基础层-基础设施 PM 每天在和"算力成本"算账：看资源数据、优化调度、评估硬件、设计监控
  8. Agent/Skills 策展 PM 每天在和"任务流"博弈：分析失败任务、设计 Skills、管理权限、优化完成率
  9. 所有 AI PM 都要经历通用工作流：需求→设计→开发→测试→上线→运营
