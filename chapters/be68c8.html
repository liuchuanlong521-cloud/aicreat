# A2A：AI Agent 之间的"通用语言"

一句话定义：A2A（Agent-to-Agent Protocol）是 Google 在 2025 年推出的开放协议，相当于让不同"国籍"、不同"职业"的 AI Agent 能够互相听懂对方说话、协同完成任务的"世界语"。

想象一下：你手机里住着 Siri、手机里住着小爱同学、车里住着车载语音助手、公司系统里住着客服机器人——它们各司其职，但彼此之间完全无法沟通。你让 Siri 查个快递，它做不到，因为它和快递公司系统里的 Agent 是"两个世界的人"。

这就是当前 AI Agent 生态最真实的写照：各自为战、互不相通。A2A 的诞生，正是为了打破这种"巴别塔困境"。

# 一、为什么 AI Agent 需要一个"世界语"？

# 1.1 当前 Agent 生态：一座又一座的孤岛

2024-2025 年，AI Agent 领域爆发式增长。LangChain、AutoGen、Coze、Dify、文心智能体、通义千问……各家的 Agent 框架如雨后春笋般涌现。

但繁荣的背后，是一个残酷的现实：每个框架都在说自己的"方言"。

平台/框架所属阵营通信方式问题
LangChain开源生态自有链路和 Coze 的 Bot 无法直接对话
Coze字节跳动私有协议只能和同平台 Bot 协作
Dify开源/商业化REST API每接入一个外部 Agent 都要定制开发
AutoGen微软内部消息总线跨组织部署极其困难
文心智能体百度百度生态协议和外部系统打通成本高
钉钉魔法棒阿里钉钉内部协议出了钉钉就"哑火"

这就好比早期的互联网：每家公司的局域网都运行良好，但彼此无法互通。直到 HTTP 协议统一了标准，万维网才真正诞生。

A2A 想做 Agent 世界的 HTTP。

# 1.2 企业级场景的真实痛点

作为产品经理，你可能已经遇到这些场景：

  • 场景一：公司的采购 Agent 需要和供应商的库存 Agent 对接，但对方用的是 SAP 系统，自家用的是自研平台，两端 Agent"鸡同鸭讲"。
  • 场景二：客服 Agent 遇到一个复杂客诉，需要转给售后处理 Agent，但两个 Agent 之间没有标准通信方式，只能人工介入中转。
  • 场景三：企业买了三家不同厂商的 AI 服务（法律、财务、HR），三个 Agent 各自为政，员工需要分别和它们对话，效率反而不如以前。

A2A 就是要解决这类"最后一公里"的连通问题。它不提供 Agent 本身的智能，而是提供Agent 之间如何打招呼、如何分工、如何交付结果的一套社交礼仪。

# 1.3 A2A 不是什么

在深入之前，先澄清一个常见误解：

A2A 不是原因
不是 Agent 框架它不管 Agent 内部怎么思考、怎么调用 LLM
不是模型协议不涉及模型训练、推理、Prompt 工程
不是 MCP 的替代品A2A 和 MCP 是互补关系（后文详述）
不是云服务它是一套开放标准，不是 Google 独占的产品

# 二、A2A 的核心概念：四张名片看懂全貌

A2A 的协议设计非常简洁，核心只有四个概念。作为产品经理，你可以把它们理解为 Agent 之间"商务合作"的四件套。

# 2.1 Agent Card：Agent 的能力名片

一句话理解：每个 Agent 上线时，都会发布一张"电子名片"，上面写着"我是谁、我能干什么、怎么联系我"。

字段类比实际含义
name公司名Agent 的名称
description公司介绍Agent 能做什么的详细描述
skills业务范围Agent 支持的任务类型（如"比价"、"翻译"、"生成报告"）
endpoint联系电话其他 Agent 可以通过这个地址找到我
authentication准入要求和我通信需要什么认证（API Key、OAuth 等）

产品经理关注点：

  • Agent Card 的设计直接影响"Agent 发现"体验。想象一下 App Store 里的应用介绍——写得好不好，决定了别人愿不愿意和你"合作"。
  • 需要规划 Agent 的 skill 描述文案，既要准确又要吸引人（毕竟别的 Agent 或用户是靠这个来匹配你的）。

# 2.2 Task：一次协作的任务单

一句话理解：当两个 Agent 开始协作时，它们会共同签署一份"任务单"，记录谁提的需求、要干什么、当前进展如何。

一个 Task 包含：

  • id：任务唯一编号
  • status：状态（submitted → working → input-required → completed / failed / canceled）
  • history：完整的对话记录
  • artifacts：最终交付的成果

状态机设计是产品经理要特别关注的：

避坑指南：input-required 这个状态非常关键。它解决了 Agent 协作中最常见的"信息不足"问题——当 Agent B 发现 Agent A 给的信息不够时，不是直接报错，而是明确告诉对方"我还需要 X 信息"。设计多 Agent 流程时，一定要为这类"中途补充信息"的场景预留交互路径。

# 2.3 Message：消息信封

一句话理解：Agent 之间传递的信息都装在标准化的"信封"里，信封上写着发件人、收件人、消息类型、时间戳。

Message 支持多种内容类型：

内容类型用途示例
text纯文本指令或回复"请帮我查一下 XX 商品的库存"
file附件传输合同 PDF、Excel 报表
data结构化数据JSON 格式的比价结果
form需要对方填写的表单"请补充收货地址和联系人"

# 2.4 Artifact：交付物

一句话理解：任务完成后，产出的结果（文档、报表、代码、决策建议等）会被打包成 Artifact，正式"移交"给对方。

Artifact 和 Message 的区别：

  • Message 是过程中的沟通（像微信聊天）
  • Artifact 是最终成果（像邮件附件、项目交付包）
特性MessageArtifact
时效性过程性，可能多条最终性，任务结束才产生
数量多次往返通常一个或多个最终产物
用途沟通协商正式交付、可归档
示例"价格太高了，能不能降 5%？"最终生成的采购合同

# 三、A2A vs MCP：横向社交 vs 纵向工具箱

如果你了解 MCP（Model Context Protocol，模型上下文协议），可能会困惑：这两个协议到底什么关系？

# 3.1 一句话区分

MCP 解决的是"Agent 怎么用工具"，A2A 解决的是"Agent 怎么和其他 Agent 聊天"。

维度MCP（模型上下文协议）A2A（Agent 间协议）
通信方向纵向：Agent → 工具/数据源横向：Agent ↔ Agent
类比USB 接口（接外设）微信（人与人聊天）
连接对象数据库、文件系统、API、浏览器另一个 AI Agent
发起方通常是 Agent 主动调用工具任意一方都可以发起
对话深度单次请求-响应可以多轮对话、协商、补充信息
状态管理无状态有状态（Task 跟踪全过程）
典型场景Agent 查数据库、读本地文件、调搜索 API采购 Agent 和供应商 Agent 谈判

# 3.2 一个生活化比喻

假设你是一个"智能管家 Agent"：

  • MCP 是你家里的各种智能设备接口：你用 MCP 开空调（调温度）、用 MCP 开扫地机器人（启动清洁）。这些设备不会和你"商量"，你发指令，它执行。
  • A2A 是你和小区物业管家的对话：你说"我家水管坏了"，物业说"师傅下午 3 点到，需要你确认是否在家"，你说"在的，但请提前打电话"——这是有来有回的多轮协商。

# 3.3 两者如何协作

在真实产品中，A2A 和 MCP 往往是协同使用的：

产品经理关注点：

  • 不要陷入"选 A2A 还是 MCP"的非此即彼思维。一个复杂的 Agent 产品通常同时需要两者。
  • 在设计产品架构时，问自己：这个能力是自己内部用工具解决的（MCP），还是需要外部合作伙伴协同的（A2A）？

# 四、A2A 的技术架构：为什么产品经理要关心？

你可能会说："我是产品经理，不关心技术实现。"但 A2A 的技术选型直接影响你的产品设计空间和落地难度，所以至少需要理解其技术边界。

# 4.1 基于 HTTP + SSE：复用现有基础设施

A2A 协议建立在两个已有技术之上：

技术作用对产品经理的意义
HTTP传输层协议企业防火墙通常已经放行 HTTP/HTTPS，IT 部门阻力小
SSE（Server-Sent Events）服务器向客户端推送实时更新Agent 可以"边想边汇报"，用户体验更接近真人对话

为什么是 SSE 而不是 WebSocket？

方案A2A 的选择原因
WebSocket❌ 未采用需要维护长连接，企业防火墙/代理容易阻断
SSE✅ 采用基于 HTTP，穿透性更好；单向推送足够满足"进度汇报"需求
轮询❌ 未采用浪费资源，实时性差

避坑指南：如果你的产品面向的是金融、政务等强安全合规行业，IT 部门对 WebSocket 通常很敏感。A2A 选择 SSE 是一个经过深思熟虑的妥协——它让"实时进度推送"和"企业网络兼容性"取得了平衡。但 SSE 是单向的（服务器→客户端），如果场景需要 Agent 之间高频双向实时通信，A2A 可能不是最优解。

# 4.3 和现有技术的对比

对比项A2AFunction Call传统 REST API消息队列（MQ）
通信对象Agent ↔ AgentLLM → 函数/工具任意系统系统 ↔ 系统
发起方式双向均可只能由 LLM 发起任意一方生产者→消费者
对话能力✅ 多轮协商❌ 单次调用❌ 请求-响应⚠️ 需额外封装
进度反馈✅ 实时推送❌ 无❌ 无⚠️ 需额外实现
身份认证✅ 内置标准⚠️ 依赖实现⚠️ 依赖实现⚠️ 依赖实现
人类介入✅ 支持（input-required）❌ 不支持❌ 不支持⚠️ 需额外实现
学习成本中（新协议）低（LLM 内置）低（普遍使用）高（基础设施重）
适用场景Agent 生态互联单 Agent 能力扩展通用接口对接系统间异步解耦

产品经理如何选？

  • Function Call：适合单个 Agent 内部调用工具（查天气、算公式、调数据库）。
  • REST API：适合 Agent 和传统系统对接（ERP、CRM 等没有 Agent 能力的系统）。
  • 消息队列：适合高并发、高可靠性的系统间异步通信（订单系统解耦）。
  • A2A：适合两个都有"智能"的 Agent 之间需要协商、补充信息、多轮对话的场景。

# 五、产品应用场景：A2A 能做什么生意？

# 5.1 场景一：跨企业 Agent 协作（B2B 互联）

场景描述：制造商的采购 Agent 和上游供应商的库存 Agent 自动对接。

传统方式：采购员发邮件→供应商销售回邮件→来回确认→录入系统。

A2A 方式：

  1. 采购 Agent 自动扫描库存预警，发现 A 原料即将耗尽。
  2. 采购 Agent 通过 A2A 发现三家合格供应商的 Agent。
  3. 同时向三家发起询价 Task。
  4. 三家供应商 Agent 分别返回报价 Artifact。
  5. 比价 Agent（内部）综合分析，推荐最优方案。
  6. 审批 Agent 触发内部审批流，通过后自动下单。

商业价值：采购周期从 3-5 天缩短到小时级，且 7×24 小时可执行。

# 5.2 场景二：多 Agent 工作流编排（企业内部）

场景描述：一个"智能法务助手"产品，内部由多个子 Agent 协作完成合同审查。

子 Agent职责用 A2A 与其他 Agent 的交互
初审 Agent格式审查、完整性检查发现缺页 → 通过 A2A 通知用户交互 Agent
条款 Agent识别风险条款发现高危条款 → 通过 A2A 通知研判 Agent
研判 Agent评估风险等级需要相似案例 → 通过 A2A 请求案例库 Agent
排版 Agent生成审查报告接收所有前置 Agent 的 Artifact，输出最终报告

产品经理关注点：

  • 每个子 Agent 可以是不同技术栈实现的（一个用 Python/LangChain，一个用 Coze），A2A 屏蔽了底层差异。
  • 编排逻辑（谁先谁后、什么条件下分支）需要一个"主控 Agent"或工作流引擎来调度。

# 5.3 场景三：Agent 市场/商店

场景描述：类似 App Store，但卖的不是 App，而是"Agent 服务"。

  • 翻译 Agent（按字数收费）
  • 法律审查 Agent（按合同页数收费）
  • 数据分析 Agent（按数据量收费）
  • 客服 Agent（按对话轮数收费）

A2A 的价值：

  • 开发者只需要暴露 Agent Card，就能被整个市场发现。
  • 用户购买后，自己的 Agent 通过 A2A 直接和购买的 Agent 对接，无需额外配置。

产品经理关注点：

  • Agent 市场的商业模式设计（订阅制、按量计费、抽成模式）。
  • Agent 评分、评价、信任体系的建立（类比 App Store 的评分系统）。

# 5.4 场景四：企业级 Agent 编排平台

场景描述：大型企业有几十个甚至上百个 Agent（IT 运维、HR、财务、法务、客服……），需要一个"企业级调度中心"。

A2A 在其中扮演的角色：

  • 统一发现：所有 Agent 注册到企业内部的"Agent 目录"，按部门、能力、安全等级分类。
  • 统一编排：业务人员通过可视化流程编辑器，拖拽 Agent 节点，配置流转规则。
  • 统一监控：所有跨 Agent 的 Task 全程可追踪、可审计。

# 六、实战案例：设计一个"智能采购助手"

# 6.1 产品背景

目标用户：中型制造企业的采购部门（10-50 人规模） 核心痛点：

  1. 采购流程长：需求确认 → 询价 → 比价 → 审批 → 下单 → 跟踪，平均 5-7 天。
  2. 信息分散：ERP、邮件、微信、Excel 四处流转，容易遗漏。
  3. 供应商管理难：几十家供应商信息更新不及时，关键时刻找不到合适供应商。

# 6.2 产品架构设计

我们设计一个由 5 个 Agent 协作完成的"智能采购助手"：

# 6.3 多 Agent 协作流程设计（产品经理视角）

# Step 1：需求分析 Agent 分发任务

用户输入："下周需要采购 500 公斤 304 不锈钢板材，交期 10 天。"

需求分析 Agent 的处理：

  1. 通过 MCP 读取 ERP，确认没有库存缺口。
  2. 创建 Task 1（供应商匹配）："需要 304 不锈钢板材，500kg，10 天交期，推荐 3 家合格供应商。"
  3. 将 Task 1 通过 A2A 发送给供应商匹配 Agent。

# Step 2：供应商匹配 Agent 响应

供应商匹配 Agent 的 Agent Card 中声明了 skill："根据物料需求匹配合格供应商"。

它收到 Task 1 后：

  1. 查询内部供应商数据库（通过 MCP）。
  2. 返回 Artifact："推荐供应商 A（历史合作 12 次）、B（价格优势明显）、C（交期最稳定）。"
  3. Task 1 状态变为 completed。

# Step 3：并行询价

需求分析 Agent 收到供应商名单后，并行创建 3 个 Task：

  • Task 2-1 → 供应商 A 的 Agent
  • Task 2-2 → 供应商 B 的 Agent
  • Task 2-3 → 供应商 C 的 Agent

每个 Task 内容："询价 304 不锈钢板材 500kg，10 天交期，请报含税价和付款方式。"

避坑指南：并行询价时，一定要设置超时机制。现实世界中不是所有供应商 Agent 都会及时响应。建议设计：48 小时未响应自动标记为超时，触发备选供应商流程。另外，不同供应商的报价格式可能不同（有的报含税价，有的报不含税），需要在询价 Agent 的 skill 描述中明确要求输出格式。

# Step 4：比价 Agent 综合分析

三家供应商 Agent 陆续返回报价 Artifact。比价 Agent 收到后：

维度供应商 A供应商 B供应商 C
单价¥45/kg¥42/kg¥44/kg
交期8 天10 天9 天
付款方式月结 30 天预付 100%月结 60 天
历史合格率99.2%97.5%98.8%
综合评分928590

比价 Agent 输出 Artifact："推荐供应商 A，理由：虽然单价略高，但历史质量最稳定、交期最短、付款条件友好。"

# Step 5：审批 Agent 处理

审批 Agent 收到比价结果后：

  1. 判断金额是否超过采购员自主审批权限（如 > ¥20,000 需上级审批）。
  2. 若需审批，通过 A2A 向"审批工作流 Agent"发起 Task。
  3. 审批完成后，通过 MCP 自动在 ERP 中生成采购订单。

# 6.4 产品设计的关键决策点

决策点方案 A方案 B建议
询价方式串行（一家问完再问下一家）并行（同时问多家）选 B，效率更高，但需处理超时
比价逻辑纯价格最低多维度综合评分选 B，企业采购不能只看价格
失败处理自动终止流程自动转人工 + 记录原因选 B，初期保留人工兜底
人类介入点仅在最后审批关键节点都需确认渐进策略：初期多介入，成熟后逐步自动化

# 七、安全与信任设计：Agent 世界的"身份证与监控"

当 Agent 开始自主与其他 Agent 通信时，安全和信任是最高优先级的问题。作为产品经理，你需要在设计之初就考虑以下机制。

# 7.1 Agent 身份认证

认证层级机制适用场景
基础层API Key内部 Agent 之间通信
企业层OAuth 2.0 / JWT跨企业 Agent 协作
高阶层数字证书（mTLS）金融、政务等高安全场景

产品经理关注点：

  • 不同安全等级的 Agent 应该只能和同等级或更高等级的 Agent 通信（类比保密级别）。
  • 在 Agent Card 中声明认证要求，让调用方提前知道"门槛"。

# 7.2 权限控制

不是每个 Agent 都能调用任何其他 Agent 的全部能力。需要设计"最小权限原则"：

采购部门 Agent 的权限：
  ✓ 调用供应商查询 Agent
  ✓ 调用比价 Agent
  ✓ 调用审批 Agent
  ✗ 调用财务记账 Agent（需额外授权）
  ✗ 调用人事档案 Agent（完全禁止）

产品经理关注点：

  • 审计日志不仅是安全需要，也是产品价值点——客户可以清晰看到"我的 Agent 到底干了什么"。
  • 设计"审计看板"功能，让客户可视化查看 Agent 协作全流程。

# 7.4 内容安全

Agent 之间传输的内容可能包含敏感信息（合同条款、价格、客户数据）：

  • 传输加密：A2A 基于 HTTPS，天然支持传输层加密。
  • 内容脱敏：在 Agent Card 中标注"接收数据是否会被第三方处理"，让数据提供方知情。
  • 合规标记：标注数据跨境、个人信息等合规标签。

# 8.2 当前阶段判断

A2A 目前处于早期生态建设阶段：

  • ✅ 协议标准已发布，技术设计合理
  • ✅ 大厂背书，短期不会消亡
  • ⚠️ 实际落地案例有限，缺乏最佳实践沉淀
  • ⚠️ 国内生态几乎空白，中文资料极少
  • ❌ 尚未形成类似 HTTP 那样的"事实标准"地位

产品经理关注点：如果你所在的公司面向的是海外市场或跨国企业，A2A 值得提前布局。如果主要面向国内中小企业，当前优先级可以适当后移，但建议持续关注——协议标准的早期采纳者往往能在生态成熟时占据先机。

# 九、挑战与局限：A2A 不是银弹

# 9.1 生态尚处早期

A2A 最大的挑战是网络效应：协议的价值取决于有多少 Agent 支持它。目前支持的 Agent 数量还很少，"鸡生蛋、蛋生鸡"的问题需要时间来解决。

# 9.2 标准化 vs 灵活性的矛盾

A2A 提供了标准通信格式，但 Agent 的核心能力——如何理解任务、如何决策、如何生成回复——仍然由各 Agent 自己决定。这意味着：

  • 两个 A2A Agent 虽然能"通话"，但未必能"理解"对方。
  • 复杂任务的多轮协商中，Agent 的"情商"差异会导致协作体验参差不齐。

# 9.3 商业利益冲突

各大厂商真的会完全拥抱一个开放协议吗？

  • Coze 的 Bot 生态是字节的护城河，完全开放 A2A 可能削弱平台粘性。
  • Salesforce 的 Agentforce 是收费服务，开放互通可能影响商业收入。
  • 每家厂商都有动力"形式上支持、实际上限制"A2A 的互通能力。

产品经理关注点：在设计产品时，不要假设所有外部 Agent 都会乖乖支持 A2A。预留"降级方案"（如人工介入、传统 API 对接）是明智的。

# 9.4 技术局限

局限说明应对策略
SSE 单向性服务器推送强，客户端主动发送弱复杂双向场景考虑 WebSocket 补充
无内置计费协议层面不涉及付费结算产品层自行设计计费逻辑
无服务质量保障不保证 Agent 响应时间设计超时、重试、降级机制
语义鸿沟能通信不代表能互相理解在 Task 描述中尽量结构化、标准化

# 写在最后

A2A 的诞生，标志着 AI Agent 从"单打独斗"走向"群体智能"的关键一步。

作为 AI 产品经理，你不需要记住 Agent Card 的每一个字段，也不需要理解 SSE 的底层实现。但你需要理解的是：A2A 代表了一种趋势——未来的 AI 产品不再是孤立的功能点，而是一个可以相互协作、共同进化的生态。

今天，A2A 还是一个新物种，生态尚未成熟。但历史告诉我们，协议标准的价值往往在生态爆发后才被真正认识到。HTTP 在 1991 年发布时无人问津，十年后它支撑了整个互联网。A2A 是否会成为 Agent 世界的 HTTP？现在无人知晓，但值得保持关注。

至少，当你在下一次产品评审会上听到"我们的 Agent 能不能和 XX 平台的 Bot 打通"时，你可以自信地说："有 A2A，这不再是问题。"
