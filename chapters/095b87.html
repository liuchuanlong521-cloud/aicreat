核心考点

前言

欢迎来到第5章的最后一节。前面我们聊了需求挖掘、竞品分析、需求评估、PRD写作、风险边界——这些都是"做什么"和"为什么做"的问题。而这一节，我们要解决"怎么做"的底层架构问题：AI产品的结构如何设计？

很多AI产品经理有一个误区：认为架构设计是技术团队的事，自己不需要关心。但事实是，如果你不懂AI产品的架构，你根本无法做出合理的功能规划、无法评估开发周期、无法与工程师高效沟通，更无法在项目中做出正确的技术选型决策。

你不需要会画架构图（虽然学会更好），但你需要理解：一个AI产品从用户点击到模型返回结果，中间经过了哪些模块？每个模块的职责是什么？模块之间如何协作？数据如何流转？

本文将从产品经理的视角，用尽量通俗的语言，把AI产品的架构彻底讲清楚。读完这一节，你将拥有一张完整的"AI产品架构地图"。

# 一、AI产品的经典五层架构

如果把一个AI产品比作一家餐厅，那么它的五层架构可以这样理解：

架构层餐厅类比核心职责关键问题
应用层餐厅大堂、服务员、菜单用户直接接触的所有界面和交互用户怎么点菜？怎么上菜？体验好不好？
服务层后厨调度、传菜系统、收银台接收订单、协调各岗位、处理业务逻辑订单怎么分配？怎么保证出菜顺序？怎么结账？
模型层主厨的大脑+手艺理解需求、做出决策、生成内容主厨水平如何？做什么菜最拿手？
数据层食材仓库、调料架、菜谱档案存储所有原材料和成品，随时取用食材新鲜吗？库存够吗？取用方便吗？
基础设施层厨房设备、水电煤、店面装修提供稳定的运行环境灶火够大吗？停电了怎么办？

下面我们对每一层进行详细拆解。

# 二、应用层设计：用户的第一触点

# （一）应用层的核心职责

应用层是用户直接接触的产品形态，负责：

  • 多端接入：Web、App、小程序、浏览器插件、企业微信/钉钉机器人
  • 交互设计：输入框、按钮、语音入口、文件上传区域
  • AI状态反馈：让用户知道"AI正在思考""AI正在生成""AI遇到了问题"
  • 结果呈现：如何把AI生成的内容展示得清晰、可信、可交互

# （二）AI产品特有的交互设计

AI产品的应用层，和传统产品最大的区别在于**"不确定性"的呈现**。

# 1. AI状态提示

传统产品的状态是确定的：点击按钮 → 加载中 → 成功/失败。AI产品的状态更复杂：

状态用户心理设计要点
思考中"AI在干活吗？卡住了吗？"展示思考过程（如Claude的thinking动画）、预计等待时间
生成中"内容对吗？我要不要打断？"流式输出（逐字显示）、支持随时停止生成
置信度低"这个答案靠谱吗？"显示置信度分数、标注"AI生成，仅供参考"、提供信息来源
需要确认"AI理解对了吗？"在行动前展示AI的理解摘要，让用户确认
遇到限制"为什么不能回答？"清晰说明限制原因（如"涉及个人隐私，无法回答"）

# 2. 人机协同入口

好的AI产品不会"替用户做决定"，而是"帮用户更好地做决定"。应用层需要设计明确的人机协同入口：

  • 反馈按钮：👍/👎，让用户标记AI回答的好坏
  • 修改建议：AI给出初稿，用户可以直接在界面上编辑
  • 人工接管：当AI置信度低于阈值时，一键转人工
  • 多方案对比：AI给出3个不同风格的答案，用户选择或组合

# 3. 多模态输入输出

现代AI产品越来越强调多模态：

输入侧：
├── 文本输入（最基础）
├── 语音输入（语音识别→文本→模型）
├── 图片输入（OCR/图像理解→模型）
├── 文件输入（PDF/Word/Excel解析→文本→模型）
└── 视频输入（抽帧/音频提取→模型）

输出侧：
├── 文本输出（最基础）
├── 富文本输出（Markdown、表格、代码块）
├── 语音输出（TTS文本转语音）
├── 图片输出（文生图、数据可视化图表）
└── 结构化输出（JSON、XML，供下游系统使用）

# （三）应用层的技术实现方式

实现方式适用场景优点缺点
Web应用（React/Vue）通用场景、快速迭代跨平台、开发快、易部署需要网络、性能受限
原生App（iOS/Android）高频使用、需要系统能力体验流畅、可离线、推送及时开发成本高、审核周期长
小程序微信/支付宝生态内传播无需下载、获客成本低功能受限、依赖平台
浏览器插件辅助现有工作流上下文感知强（知道用户在浏览什么页面）权限敏感、平台政策风险
钉钉/企微机器人企业内部协作集成办公流程、通知触达率高交互形式受限
API/SDK面向开发者的产品灵活集成、生态扩展需要开发者对接

# 三、服务层设计：产品的"中枢神经系统"

服务层是应用层和模型层之间的"桥梁"，负责处理所有业务逻辑。如果把模型层比作"大脑"，服务层就是"小脑"——协调各部件的动作，确保整体运转流畅。

# （一）服务层的核心模块

# 1. API网关（API Gateway）

职责：所有外部请求的入口，负责统一接收、校验、路由。

关键功能：

  • 请求校验：检查参数是否合法、用户是否有权限
  • 限流熔断：防止流量突增压垮系统（如每秒最多1000次调用）
  • 路由分发：根据请求类型，转发到不同的服务模块
  • 协议转换：把HTTP/REST请求转换为内部服务的调用格式

AI产品的特殊考量：

  • 模型调用通常耗时较长（几秒到几十秒），API网关需要支持长连接或异步回调
  • 需要区分"普通请求"和"模型请求"，对模型请求设置更宽松的超时时间

# 2. 认证与授权（Auth）

职责：确认"你是谁"（认证）和"你能做什么"（授权）。

AI产品的特殊考量：

  • 模型级别的权限控制：不同用户等级调用不同模型（免费用户→轻量模型，付费用户→旗舰模型）
  • 功能级别的权限控制：某些高级功能（如代码生成、数据分析）仅对特定用户开放
  • 内容安全审核：在认证层就拦截高风险用户或IP

# 3. 会话管理（Session Management）

职责：管理用户与AI的多轮对话状态。

关键设计：

会话数据结构示例：

会话管理的挑战：

  • 上下文长度限制：当对话历史超过模型上下文窗口时，需要摘要压缩或丢弃早期内容
  • 跨设备同步：用户在手机上聊了一半，切换到Web端需要无缝接续
  • 会话持久化：断电/断网后，对话历史不能丢失

# 4. 上下文组装（Context Assembly）

这是AI产品服务层最特殊的模块，也是Context Engineering的工程化落地。

职责：把各种信息源组装成模型能理解的上下文。

组装流程：

用户输入: "昨天说的那个方案怎么样了？"

【步骤1：理解用户意图】
→ 识别实体："昨天"、"方案"
→ 意图分类：查询状态

【步骤2：检索相关信息】
→ 从对话历史中找到"昨天"的讨论内容
→ 从知识库中检索"方案"的定义和背景
→ 从项目管理系统中获取方案的最新状态

【步骤3：组装上下文】
系统Prompt（角色设定 + 约束条件）
+ 对话历史摘要（保留关键信息，压缩冗余）
+ 检索到的知识片段（Top 3 最相关）
+ 实时数据（项目管理系统中的最新状态）
+ 用户当前问题
─────────────────────────────
= 最终发送给模型的上下文

【步骤4：后处理】
→ 模型返回结果
→ 过滤敏感内容
→ 格式化输出
→ 记录到会话历史

# 5. 结果后处理（Post-processing）

职责：对模型输出进行加工，确保符合产品要求。

常见处理：

  • 内容审核：调用内容安全API，过滤违规内容
  • 格式转换：把模型输出的Markdown转为HTML，或把JSON格式化
  • 引用标注：给模型输出中的事实性陈述添加来源链接
  • 置信度标注：如果模型输出置信度低，附加提示"此内容可能不准确"

# 6. 计费系统（Billing）

职责：精确记录每个用户的Token消耗，支撑商业化。

计费维度：

计费项说明示例
按Token计费记录每次调用的输入/输出Token数用户A本月消耗 150万输入Token + 30万输出Token
按次数计费记录调用API的次数用户B本月调用 500 次
按功能计费不同功能不同单价普通问答 ¥0.01/次，代码生成 ¥0.05/次
按模型计费不同模型不同单价GPT-4o ¥0.05/次，GPT-4o mini ¥0.005/次

# （二）服务层的高可用设计

AI产品的服务层需要特别考虑模型服务的稳定性：

策略说明
超时降级模型响应超过5秒，自动返回"请稍后再试"或切换到轻量模型
熔断机制当模型API连续失败时，暂时停止调用，避免雪崩
负载均衡多个模型实例之间分配请求，避免单点过载
异步处理对于耗时任务（如生成长文、分析大数据），采用"先接收→后台处理→完成后通知"的模式
缓存复用对相同/相似的问题，直接返回缓存结果，减少模型调用

# 2. 多模型策略

很少有AI产品只依赖单一模型。成熟的产品通常采用**"大模型+小模型"**的分层策略：

用户请求
    ↓
【第一层：意图识别模型】（小模型，快速、便宜）
    → 分类：问答 / 生成 / 分析 / 其他
    ↓
【第二层：专用模型路由】
    ├── 问答类 → 知识问答模型（RAG增强）
    ├── 生成类 → 创意写作模型
    ├── 分析类 → 数据分析模型（Code Interpreter）
    └── 其他 → 通用大模型（兜底）
    ↓
【第三层：结果质检模型】（小模型，快速）
    → 检查输出是否合规、格式是否正确
    ↓
返回给用户

# （四）模型评测体系

模型上线前和上线后，都需要持续评测：

评测类型评测内容方法
离线评测用标准测试集评估模型效果准备1000条标注好的测试数据，批量跑模型，计算准确率
在线评测监控真实用户场景下的表现抽样用户的真实请求，人工标注模型输出的好坏
对抗评测测试模型在边界情况下的表现故意输入诱导性、歧义性、攻击性的Prompt
回归评测确保模型升级后没有变差每次模型更新，用固定测试集跑一遍，对比历史分数

2. 查询流程：
   用户问题 → Embedding模型 → 向量 → 向量数据库相似度检索 → Top K相关文档

Elasticsearch传统搜索引擎+向量检索需要同时支持全文检索和语义检索

# 3. 分块策略（Chunking Strategy）

把长文档切成小段存入向量数据库，是RAG效果的关键。

分块策略做法优点缺点
固定长度每500个字符切一块简单、均匀可能切断句子，语义不完整
按段落切以换行/空行为界保留段落完整性段落长度差异大，不均匀
按语义切用模型判断语义边界语义最完整计算成本高
重叠切分相邻块有重叠区域避免信息丢失在边界存储冗余增加
层级切分先按章切，再按节切，再按段切保留文档结构实现复杂

# 六、基础设施层：稳定运行的底座

# （一）算力资源管理

AI产品的算力需求有两种模式：

模式说明适用场景
API调用模式调用第三方模型API（OpenAI、Anthropic等），按量付费大多数AI应用产品
自托管模式自己部署开源模型，需要GPU服务器数据敏感、调用量极大、需要定制化

自托管的算力规划：

GPU需求估算：
- 模型参数量：70B参数的模型，推理需要约 2-4 张 A100/H100
- 并发请求：每增加100并发，约需增加 1-2 张 GPU
- 模型数量：如果同时运行3个不同模型，GPU数量 ×3

示例：一个日活10万的AI产品，自托管70B模型
- 推理GPU：8 × A100（应对峰值并发）
- Embedding GPU：2 × A100（文档向量化）
- 微调GPU：4 × A100（定期模型微调）
- 总计：约 14 张 A100，年成本约 ¥300-500万
