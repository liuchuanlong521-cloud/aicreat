核心考点

前言

如果你做过 RAG（检索增强生成），一定遇到过这两个概念：Embedding（嵌入）和向量数据库。它们是大模型外挂知识库的核心基础设施。

简单来说：Embedding 负责把"文字"变成"数字向量"，向量数据库负责在海量向量中"找相似"。两者配合，让大模型能从数百万篇文档中秒级找到最相关的几篇。

但"把文字变成向量"和"找相似"这两件事，看似简单，实则涉及深厚的技术积累——从 Embedding 模型的训练原理，到向量索引算法的工程实现，再到分布式系统的架构设计，每一层都值得深入理解。

本文将从原理到工程、从算法到选型，系统深入地讲解 Embedding 和向量数据库的方方面面。

# 一、Embedding：给语义一个"数学坐标"

# （一）从"关键词匹配"到"语义理解"：为什么 Embedding 是必须的？

想象你要从 100 万本书中找"人工智能在医疗中的应用"相关资料。

传统方法（关键词匹配 / TF-IDF）：

你翻看书名和目录，找包含"人工智能""医疗""应用"这些词的书。但问题很多：

  • 《机器学习辅助诊断技术》——内容高度相关，但没有"人工智能"这个词
  • 《人工智能概论》——标题命中关键词，但和医疗无关
  • 《深度学习在影像识别中的实践》——用"深度学习"而不是"人工智能"，被漏掉
  • 用户搜"AI 看病"——同义词完全匹配不上

关键词匹配只能找到字面相关的内容，找不到语义相关的内容。

Embedding 方法（语义向量匹配）：

你给每本书的内容生成一个高维向量（比如 768 维或 1024 维）。这个向量不是随机生成的——它编码了文本的语义信息。

语义相近的文本，向量在空间中距离更近；语义无关的文本，向量距离更远。

于是：

  • "人工智能"和"机器学习"的向量距离很近（语义相近）
  • "人工智能"和"手机"的向量距离很远（语义无关）
  • 用户搜"AI 看病"，虽然字面不同，但向量位置和"人工智能在医疗中的应用"很接近

Embedding 让搜索从"字面匹配"升级为"语义匹配"。

# （二）Embedding 的技术原理：从 Word2Vec 到对比学习

Embedding 技术的发展经历了三代演进，每一代都在解决前一代的局限。

# 第一代：Word2Vec（2013）——"物以类聚，词以群分"

核心思想：通过海量文本训练，让经常出现在相似上下文中的词，拥有相似的向量。

经典示例：

Word2Vec 训练完成后，你会发现：

  • "国王" - "男人" + "女人" ≈ "女王"
  • "北京" - "中国" + "美国" ≈ "华盛顿"

这说明向量不仅编码了"语义相似"，还编码了"语义关系"。

局限性：

局限说明
一词多义"苹果"只有一个向量，无法区分是水果还是公司
静态表示无论上下文怎么变，同一个词的向量永远不变
无上下文感知"我在银行工作"和"我在河边"的"bank"向量相同

# 第二代：BERT（2018）——"上下文决定含义"

核心突破：引入 Transformer 的 Encoder，让同一个词在不同上下文中有不同的向量。

"苹果很好吃" → "苹果"的向量偏向"水果"
"苹果发布了新 iPhone" → "苹果"的向量偏向"公司"
1
2

BERT 的 Embedding 用法：

BERT 本身是为"理解"设计的（分类、NER、问答）。但研究者发现，取 BERT 最后一层的 [CLS] token 的隐藏状态，或者取所有 token 向量的平均值，就可以得到一个句子的 Embedding。

局限性：

局限说明
不适合语义相似度BERT 的预训练任务（MLM、NSP）不是为了"语义相似度"设计的
句子对比较效果差直接用 BERT 做句子相似度，效果不如专门训练的模型

# 第三代：Sentence-BERT 与对比学习（2019-至今）——"为相似度而生"

Sentence-BERT 的革命：

研究者发现：BERT 在句子相似度任务上效果差，不是因为 BERT 不够强，而是因为训练目标不对。

BERT 的训练目标是"预测被遮住的词"，而不是"判断两个句子是否语义相同"。

Sentence-BERT 的做法：在 BERT 基础上，用句子对的语义相似度数据进行微调——让语义相同的句子向量接近，语义不同的句子向量远离。

对比学习（Contrastive Learning）的核心思想：

训练数据：
- 正样本对（语义相同）：("今天天气很好", "今天是个晴天") → 向量距离拉近
- 负样本对（语义不同）：("今天天气很好", "这本书很有趣") → 向量距离推远

训练目标：让正样本对的距离尽可能小，负样本对的距离尽可能大

类比：

想象你在训练一个"人脸识别系统"：

  • 给系统看两张同一个人的照片 → 系统学习到"这两张应该很近"
  • 给系统看两张不同人的照片 → 系统学习到"这两张应该很远"

对比学习就是让 Embedding 模型学会"什么应该近、什么应该远"。

# 双塔模型 vs 单塔模型

Embedding 的生成方式有两种架构：

架构原理优点缺点代表
双塔模型（Bi-Encoder）query 和文档各自独立编码成向量，然后计算相似度速度快，可离线预计算文档向量精度较低，没有交互BGE、E5、OpenAI Embedding
单塔模型（Cross-Encoder）query 和文档拼接在一起输入模型，直接输出相似度分数精度极高，有充分的交互速度慢，无法离线预计算BGE Reranker、Cohere Rerank

实际应用中的组合：

工业界的标准做法是"双塔召回 + 单塔精排"：

  1. 双塔模型（Embedding）负责从百万文档中快速召回 Top-100
  2. 单塔模型（Cross-Encoder）负责对 Top-100 精确重排序，选出 Top-5

这样既快又准——双塔负责"海选"，单塔负责"决赛"。

# （四）多语言 Embedding 的特殊挑战

语言的"向量平等性"：

理想情况下，"苹果"（中文）和"apple"（英文）应该在向量空间中处于同一位置——因为它们指同一个东西。

但早期的 Embedding 模型往往是在单语言数据上训练的，不同语言的向量空间完全独立。

多语言对齐技术：

技术原理效果

对比学习对齐用翻译对作为正样本（"苹果" ↔ "apple"）语义等价词向量接近
指令微调给模型语言指令，让它理解跨语言语义支持跨语言检索

实际表现：

模型中英文对齐效果跨语言检索
OpenAI text-embedding-3优秀✅ 支持
BGE-M3优秀✅ 支持 100+ 语言
E5-multilingual良好✅ 支持
早期单语言模型无对齐❌ 不支持

# 二、相似度度量：向量之间的"距离"

把文本变成向量后，需要计算向量之间的相似度。这不仅仅是"算距离"那么简单——不同的度量方式适用于不同的场景，选择错误的度量方式会导致检索效果大打折扣。

# （一）余弦相似度（Cosine Similarity）——最常用

核心思想：计算两个向量夹角的余弦值。

为什么余弦相似度适合语义匹配？

因为 Embedding 模型通常会对输出向量做L2 归一化（把向量长度缩放到 1）。归一化后，向量的"长度"信息被抹掉了，只剩下"方向"信息。

而语义信息主要编码在"方向"上——两个向量指向同一个方向，说明它们在讨论同一件事；指向相反方向，说明它们语义相反。

特点：

  • 值域：-1（完全相反）到 1（完全相同）
  • 只关注方向，不关注长度
  • 对向量的缩放不敏感

适用场景：文本语义相似度（默认选择）

# （二）欧氏距离（Euclidean Distance）——关注绝对位置

核心思想：计算两个向量在空间中的直线距离。

与余弦相似度的区别：

余弦相似度：两个人站在原点，面朝的方向是否相同（不管走多远）。 欧氏距离：两个人在广场上的实际距离有多远（考虑走了多远 + 方向是否相同）。

什么时候用欧氏距离？

当 Embedding 向量没有做归一化时，欧氏距离比余弦相似度更合适——因为它同时考虑了方向和长度。

某些早期的 Embedding 模型（如 Word2Vec）输出不做归一化，这时候欧氏距离更合理。

# （三）点积（Dot Product）——最快的相似度

核心思想：两个向量对应元素相乘后求和。

为什么点积最快？

点积的计算最简单——只是一系列乘法和加法。而余弦相似度需要在点积的基础上再除以两个向量的长度（需要开方运算）。

在大规模检索中，点积比余弦相似度快 10-20%。

点积 = 余弦相似度 × 向量长度乘积

如果向量做了归一化（长度都为 1），点积和余弦相似度的结果完全相同。

所以很多向量数据库在内部用点积计算，因为速度快，且只要输入向量是归一化的，结果就等同于余弦相似度。

# （四）三种度量方式的对比与选择

度量方式公式考虑方向考虑长度计算速度适用场景
余弦相似度cos(θ) = (A·B) / (|A| |B|)✅❌中等归一化后的语义匹配
欧氏距离|A-B| = √(Σ(Ai-Bi)²)✅✅慢非归一化向量
点积A·B = Σ(Ai × Bi)✅（归一化后）✅最快大规模检索，归一化向量
曼哈顿距离Σ|Ai-Bi|✅✅中等特殊场景

AI PM 关注点：

在绝大多数 RAG 场景中：

  1. 确保 Embedding 向量做了归一化
  2. 使用点积或余弦相似度作为度量方式
  3. 如果算法团队用了欧氏距离，确认他们是否知道向量没有归一化

# 三、向量数据库：海量向量的"高速公路"

# （一）为什么需要专门的向量数据库？

假设你有 1000 万篇文档，每篇文档对应一个 768 维的向量。存储占用：

1000 万 × 768 维 × 4 字节(浮点) = 约 30GB
1

暴力搜索的问题：

用户 query 来了，你需要计算 query 向量和 1000 万个文档向量的相似度。

  • 每次查询：1000 万次向量运算
  • 768 维向量的一次相似度计算 ≈ 768 次乘法和加法
  • 总计算量：1000 万 × 768 ≈ 76 亿次运算
  • 在单核 CPU 上：需要 数秒到数十秒
  • 完全不可接受

向量数据库的解决思路：

不精确计算所有距离，而是构建索引结构，把搜索空间从"全量"缩小到"最可能相关的子集"。

就像查字典：你不会从第一页翻到最后一页，而是先查索引，定位到大概的页码范围，再在范围内查找。

# （二）ANN（近似最近邻）算法的本质

ANN 算法的核心思想：用空间换时间——预先构建索引结构，查询时只搜索一小部分数据。

牺牲什么？

ANN 是"近似"搜索——它可能漏掉 1%-5% 的真正最近邻，但换来的是 100-1000 倍的速度提升。

在绝大多数 RAG 场景中，1% 的精度损失完全可以接受（因为后续还有重排序和大模型生成环节兜底）。

主流 ANN 算法详解：

# 1. HNSW（Hierarchical Navigable Small World）——当前主流

核心思想：构建多层图结构，越上层越稀疏（"高速公路"），越下层越密集（" local 街道"）。

搜索过程：

Step 1：从顶层最稀疏的图开始，快速定位到目标区域附近
    （就像在导航 App 上，先缩放全国地图，找到大概的城市）

Step 2：逐层向下，在每层细化位置
    （从城市 → 区县 → 街道 → 具体门牌号）

Step 3：在最底层精确找到最近的 K 个邻居

# 2. IVF（Inverted File Index）——聚类+搜索

核心思想：先把所有向量聚成 K 个类，查询时只搜索最近的几个类。

建索引：
1. 用 K-Means 把 1000 万向量聚成 1000 个类
2. 每个类有一个中心点（centroid）
3. 每个向量只属于一个类

查询：
1. 计算 query 向量和 1000 个中心点的距离
2. 选出最近的 nprobe 个类（如 10 个）
3. 只在这 10 个类里的向量中搜索

# 3. PQ（Product Quantization）——压缩存储

核心思想：把高维向量压缩成低维的短码，用短码计算近似距离。

直觉理解：

想象你在记录一个人的外貌特征：

  • 原始方式：精确记录身高 175.3cm、体重 68.5kg、头围 56.2cm……（高精度，占空间）
  • PQ 方式：身高"中高"、体重"正常"、头围"中等"……（粗略分类，省空间）

PQ 就是把向量的每个维度从"精确浮点数"压缩成"粗略的类别编号"，存储和计算都大大节省。

压缩效果：

原始维度压缩方式压缩后大小精度损失
768 维 × 4 字节 = 3072 字节PQ（8 字节）8 字节5-10%
768 维 × 4 字节 = 3072 字节PQ（16 字节）16 字节2-5%

适用场景：

  • 数据量极大（> 1 亿），内存不够存原始向量
  • 对精度要求不是极致，可以容忍少量损失
  • 通常和 HNSW 或 IVF 组合使用（HNSW + PQ、IVF + PQ）

# 4. Flat（暴力搜索）——精度 100% 的baseline

特点：不做任何索引，直接和全部向量计算相似度。

唯一的价值：作为评估 ANN 算法精度的 baseline。

  • 用 Flat 搜索 Top-10，记录结果
  • 用 HNSW 搜索 Top-10，对比结果
  • 计算"召回率"：HNSW 的 Top-10 里有多少和 Flat 的 Top-10 相同

ANN 算法选择指南：

数据量 < 10 万
    ├── 需要 100% 精度 → Flat（暴力搜索也够用）
    └── 追求速度 → HNSW

数据量 10 万 - 1000 万
    ├── 默认推荐 → HNSW
    ├── 内存紧张 → IVF 或 IVF + PQ
    └── 需要动态增删 → HNSW（IVF 增删成本高）

数据量 > 1000 万
    ├── 内存充足 → HNSW
    ├── 内存紧张 → IVF + PQ 或 HNSW + PQ
    └── 分布式部署 → Milvus / Pinecone

# 六、高级主题：超越基础向量检索

# （一）多向量表示（Multi-Vector / ColBERT）

问题：传统的双塔模型把一个文档压缩成一个向量，信息损失很大。

一篇 1000 字的文章，压成一个 768 维的向量——就像一个压缩包，解压后很多细节丢失了。

ColBERT 的解决方案：

不对文档做"整体压缩"，而是保留文档中每个 token 的向量。

  • 文档有 200 个 token → 存 200 个向量
  • 查询有 10 个 token → 分别和文档的 200 个向量计算相似度
  • 取最大相似度作为 query-document 的匹配分数

效果：

  • 精度比单向量高 10-20%
  • 存储成本增加 100-200 倍
  • 适合对精度要求极高、数据量中等的场景

# （二）稀疏向量（Sparse Embedding / SPLADE）

问题：密集向量（Dense Embedding）擅长语义匹配，但对精确的关键词匹配不够敏感。

稀疏向量的思路：

类似于传统的 TF-IDF/ BM25——给每个词一个权重，但权重是用神经网络学出来的。

一个稀疏向量可能有 3 万个维度（对应词表大小），但只有几十个非零值。

混合检索：

dense vector（语义匹配）+ sparse vector（关键词匹配）
    ↓
融合排序 → 最终结果

# （三）重排序（Re-ranking）的深层原理

为什么双塔召回后还需要重排序？

双塔模型的缺陷：query 和文档是独立编码的——它们没有交互。

就像两个人分别写简历，HR 只看简历打分，没有面试交流。有些 subtle 的匹配信号在独立编码时会丢失。

Cross-Encoder 的优势：

把 query 和文档拼接在一起输入模型，让模型能捕捉它们之间的交互信号。

就像面试——候选人和面试官面对面交流，能发现简历上看不到的匹配点。

重排序的代价与收益：

阶段计算量精度作用
双塔召回小（离线预计算）中从百万到百
Cross-Encoder 重排序大（逐对计算）高从百到十
大模型生成最大最高从十到一（最终答案）

# 十、小结

# 核心要点

  1. Embedding 经历了三代演进：Word2Vec（静态词向量）→ BERT（上下文感知）→ 对比学习（为相似度而生）。当前主流是双塔对比学习模型（BGE、E5、OpenAI text-embedding-3）。

  2. 双塔召回 + 单塔重排序是工业界标准：双塔负责从百万文档中快速召回 Top-100，Cross-Encoder 负责精排选出 Top-5。

  3. 向量数据库的核心是 ANN 索引：HNSW 是默认选择（速度快、支持动态增删），IVF 适合内存受限场景，PQ 用于极致压缩。

  4. pgvector 是最推荐的入门方案，Milvus/Pinecone 适合大规模生产环境。

  5. 文档切分是 RAG 效果的关键：Chunk Size 300-800 Token，Overlap 50-200 Token，策略选择取决于文档类型。

  6. 成本需要精细规划：存储（向量+索引+原文 ≈ 原始数据的 5-10 倍）、Embedding API（按 Token 计费）、向量数据库（按存储和查询计费）。

  7. 高级技术能进一步提升效果：稀疏向量（SPLADE）增强关键词匹配、ColBERT 多向量表示减少信息损失、混合搜索（RRF）融合多种检索信号。

# 给 AI PM 的一句话

向量数据库和 Embedding 是大模型产品的"基础设施层"——它们不像大模型那样引人注目，但它们的选型、调优和运维质量，直接决定了 RAG 产品的用户体验和成本结构。一个优秀的 AI PM，应该能和工程师讨论 HNSW 的参数调优、能评估不同 Embedding 模型的 MTEB 分数、能估算百万级向量数据库的存储成本。这些能力，让你在技术决策中拥有真正的话语权。
