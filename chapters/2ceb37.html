核心考点

前言

在上一节《智能体（Agent）》中，我们知道了 Agent 是能思考也能行动的 AI。但 Agent 的"行动"不是凭空产生的——它依靠一个个具体的 Skill（技能） 来完成任务。

查天气是一个 Skill，发邮件是一个 Skill，查数据库是一个 Skill，写 Python 代码也是一个 Skill。Skill 是 Agent 与真实世界交互的"桥梁"，是 Agent 从"空想家"变成"实干家"的关键。

本文将深入讲解 Skill 的核心原理、分类体系、设计方法，以及作为 AI PM，如何设计和评估 Skill 体系。

# 一、什么是 Skill？Agent 的"工具箱"

# （一）一个形象的类比：装修公司的项目经理

想象你请了一个装修公司的项目经理（Agent）来帮你装修房子。

没有 Skill 的项目经理：

你问他："能帮我装个吊灯吗？" 他说："吊灯一般需要固定在天花板的承重结构上，需要注意电线的走向……"——说得头头是道，但就是不干活。

你问他："能帮我刷墙吗？" 他说："刷墙需要先打磨、再底漆、再面漆，选择环保材料很重要……"——还是只动口不动手。

有 Skill 的项目经理：

你跟他说："帮我装个吊灯。" 他立刻拿出电话（调用 Skill）："电工师傅，来 3 号楼 502，装一个吊灯。" 电工来了，干活，装好。

你跟他说："把卧室刷成浅蓝色。" 他立刻拿出电话（调用 Skill）："油漆工，带浅蓝色环保漆来 502。" 油漆工来了，打磨、底漆、面漆，完工。

Skill 就是这个项目经理手里的"通讯录"和"工作清单"——每个 Skill 对应一个具体的工种，项目经理知道什么时候该叫谁来做什么。

# （二）Skill 的技术定义

Skill 是 Agent 可以调用的原子化能力单元，它封装了一个具体的操作或功能。每个 Skill 通常包含：

Skill = 功能描述 + 输入参数定义 + 执行逻辑 + 输出格式
1

举例："查询天气" Skill

组成部分内容
功能描述查询指定城市和日期的天气信息
输入参数city（城市名，字符串）、date（日期，字符串）
执行逻辑调用天气 API，获取实时天气数据
输出格式JSON：{ weather, temperature, humidity, wind }

Skill 和 Function Calling 的关系：

Skill 是 Function Calling 的产品化封装。

  • Function Calling 是底层机制——模型输出函数调用请求
  • Skill 是上层抽象——把一组相关的函数、API、逻辑封装成一个"能力模块"

类比：Function Calling 是"打电话"这个动作，Skill 是"通讯录里的一个联系人"。

# （三）参数提取：从"自然语言"到"结构化数据"

用户的表达是自然语言，但 Skill 需要结构化参数。参数提取就是做这个转换。

示例：

用户："帮我查一下下周三上海的天气，我要出差。"

需要提取的参数：
- city: "上海"
- date: "下周三" → 需要解析为具体日期（如 2024-06-12）

挑战：
- "下周三"是相对的，需要结合当前日期计算
- "出差"是背景信息，不是参数，需要过滤掉
- 用户没说"查询天气"四个字，但需要理解意图

# 三、Skill 的分类体系

# （一）按功能领域分类

类别典型 Skill说明
信息查询查天气、查股票、查汇率、查新闻从外部数据源获取实时信息
数据操作查数据库、写 Excel、生成报表操作结构化数据
内容生成写邮件、写文案、生成图片、生成 PPT创作类能力
通信协作发邮件、发消息、创建日程、开会议办公协同
系统操作操作 CRM、操作 ERP、操作工单系统企业系统集成
计算分析计算器、数据分析、代码执行逻辑计算
多媒体语音识别、语音合成、OCR、图像识别感知类能力

# （二）按执行方式分类

类型说明示例
API 型 Skill调用外部 HTTP API查天气、查股票、发邮件
数据库型 Skill执行 SQL 查询查询用户订单、统计销售数据
代码型 Skill执行一段代码Python 计算、数据处理
本地工具型 Skill调用本地软件/命令操作 Excel、执行 Shell 命令
Agent 型 Skill调用另一个子 Agent让"数据分析 Agent"处理复杂报表

# （三）按权限等级分类

等级风险示例是否需要确认
只读（Read-only）极低查询天气、查文档❌ 不需要
写操作（Write）中发邮件、创建日程⚠️ 建议确认
敏感操作（Sensitive）高转账、删除数据、修改配置✅ 必须确认
高危操作（Critical）极高大额转账、批量删除、系统重启✅ 必须确认 + 二次验证

AI PM 关注点：

Skill 的权限设计是 Agent 产品的安全底线。

  • 只读 Skill 可以自动执行，提升效率
  • 写操作 Skill 建议加确认环节
  • 敏感操作必须人工确认，且保留审计日志

# 五、如何设计一个好的 Skill？

# （一）Skill 设计的五大原则

原则说明反例
单一职责一个 Skill 只做一件事"查询天气并发送邮件"——应该拆成两个 Skill
参数明确输入参数清晰、必填/选填明确参数叫"data"——不知道要传什么
描述精准Skill 和参数的描述要准确描述写"查询信息"——太模糊
输出稳定返回格式统一、可预期有时候返回 JSON，有时候返回纯文本
容错健壮参数错误时给出清晰报错API 挂了，返回"未知错误"

# （二）Skill 描述（Description）的艺术

Skill 的描述决定了大模型能不能"正确理解"什么时候该调用这个 Skill。

差的描述：

"name": "query",
"description": "查询数据"
1
2

问题：太模糊。"查询数据"是什么意思？查什么数据？什么场景下用？

好的描述：

"name": "query_sales_data",
"description": "查询销售数据。当用户询问销售额、订单量、销售业绩、同比环比等数据时使用。支持按时间范围（日/周/月/年）、地区、产品品类筛选。"
1
2

优点：明确说明了使用场景（什么时候调用）、支持的功能（能查什么）、筛选条件（参数能力）。

# （三）参数设计最佳实践

示例：设计一个"预订会议室" Skill

{
  "name": "book_meeting_room",
  "description": "预订会议室。当用户需要预定会议室、开会的场地时使用。",
  "parameters": {
    "type": "object",
    "properties": {
      "date": {
        "type": "string",
        "description": "会议日期，格式：YYYY-MM-DD，如 2024-06-15"
      },
      "start_time": {
        "type": "string",
        "description": "开始时间，格式：HH:MM，如 14:00"
      },
      "duration_minutes": {
        "type": "integer",
        "description": "会议时长（分钟），如 60"
      },
      "capacity": {
        "type": "integer",
        "description": "参会人数，用于筛选足够大的会议室",
        "default": 4
      },
      "room_name": {
        "type": "string",
        "description": "指定会议室名称（可选），如不提供则自动推荐",
        "default": null
      }
    },
    "required": ["date", "start_time", "duration_minutes"]

}

# （四）Skill 的错误处理设计

好的 Skill 应该返回结构化的错误信息：

  "success": false,

# 七、AI PM 视角：Skill 体系的产品设计

# （一）Skill 体系的规划流程

Step 1：用户场景分析
    └── 用户在这个 Agent 里会做什么？
    └── 示例：企业客服 Agent → 查订单、查物流、申请退换货、咨询产品

Step 2：Skill 拆分
    └── 每个场景对应一个或多个 Skill
    └── 示例：查订单 → "query_order" Skill；申请退换货 → "create_return" Skill

Step 3：优先级排序
    ├── P0：核心高频 Skill（必须做）
    ├── P1：重要但低频 Skill（尽快做）
    └── P2：锦上添花 Skill（有余力再做）

Step 4：接口设计
    └── 定义每个 Skill 的参数、返回值、错误码

Step 5：安全评审
    └── 每个 Skill 的风险等级？是否需要人工确认？

Step 6：效果验证
    └── Skill 的准确率？召回率？用户体验？

# （二）Skill 数量的权衡

Skill 数量优点缺点
太少（<5 个）模型选择简单、准确率高功能单一，用户价值有限
适中（10-30 个）功能丰富、模型仍能理解维护成本增加
太多（>50 个）功能极其丰富模型选错 Skill 的概率大增、维护困难

建议：

  • MVP 阶段：5-10 个核心 Skill
  • 成熟阶段：15-30 个 Skill
  • 如果超过 30 个，考虑做 Skill 分组或层级架构

# （三）Skill 的冷启动问题

新 Skill 上线后，模型可能不知道"什么时候该用它"。

解决方案：

方法说明

# 九、小结

# 核心要点

  1. Skill 是 Agent 的"能力积木"：每个 Skill 封装一个具体的功能，Agent 通过调用 Skill 来完成任务。

  2. Skill = 功能描述 + 输入参数 + 执行逻辑 + 输出格式：四要素缺一不可。

  3. Skill 描述决定模型能否正确调用：描述要精准、包含使用场景、参数格式要清晰。

  4. 权限分级是安全底线：只读 Skill 自动执行，敏感操作必须人工确认。

  5. Skill 设计遵循单一职责原则：一个 Skill 只做一件事，复杂的用编排组合。

  6. Skill 数量要适度：MVP 阶段 5-10 个，成熟阶段 15-30 个，太多会导致模型选错。

  7. Skill 是产品差异化的关键：同样的底层模型，Skill 体系的设计决定了 Agent 的能力边界和用户体验。

# 给 AI PM 的一句话

如果说大模型是 Agent 的"大脑"，那么 Skill 就是 Agent 的"手脚"。大脑再聪明，没有手脚也只能空想；手脚再灵活，没有大脑指挥也只能乱动。作为 PM，你的核心任务是设计一套"恰到好处"的 Skill 体系——覆盖用户的核心需求、描述清晰让模型能理解、权限可控让用户放心、数量适中让维护可持续。Skill 设计得好，Agent 产品就成功了一半。
