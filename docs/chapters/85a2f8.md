::: tip 核心考点
前言

《提示词工程》中，我们学习了"如何说"——通过优化 Prompt 的措辞和结构，让模型输出更精准。但有一个更底层的问题：**模型在回答时，到底"知道"些什么？**

假设你问模型："我们项目上周讨论的登录方案确定了吗？"模型一脸茫然——它不知道你们的项目、没参加过你们的讨论、不了解你们的代码库。

**Context Engineering（上下文工程）** 解决的就是这个问题：如何为模型构建、筛选、组织最有价值的信息，让它在回答时"掌握足够的事实"。如果说 Prompt Engineering 是"说话的艺术"，Context Engineering 就是"备课的艺术"。

在大模型上下文窗口突破百万 token、RAG 和 Agent 成为主流架构的今天，Context Engineering 已经从"高级技巧"变成了 AI 产品经理的核心能力。
:::

##  一、什么是 Context Engineering？

![](https://oss.fullcoding.cn/20260526/c111ffcb-e441-4ccf-9ba6-ef0604ba42ed_1779779611688.png)

###  （一）一个直观的类比

**Prompt Engineering 像教一个人怎么说话；Context Engineering 像给一个人准备考试前的复习资料。**

> 考试范围有 10 本书，但考卷只有 100 道题。你不能把 10 本书全塞进考场——时间不够，人也看不完。
> 
> 你需要：
> 
> -   筛选出最可能考的重点章节
> -   把重点内容整理成精炼的笔记
> -   按逻辑顺序编排，让人能快速理解
> 
> Context Engineering 做的就是这件事——**在海量信息中，为模型筛选、整理、组织出"最有助于回答问题"的那部分上下文。**

###  （二）技术定义

Context Engineering 是**为大型语言模型设计、构建、优化输入上下文的全流程工程化方法**。它关注三个核心问题：

<table><thead><tr><th style="text-align:left;">问题</th><th style="text-align:left;">说明</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>给什么？（What）</strong></td><td style="text-align:left;">从海量信息源中，筛选出与当前任务最相关的信息</td></tr><tr><td style="text-align:left;"><strong>怎么给？（How）</strong></td><td style="text-align:left;">以什么格式、什么顺序、什么粒度组织这些信息</td></tr><tr><td style="text-align:left;"><strong>给多少？（How much）</strong></td><td style="text-align:left;">在上下文窗口的限制内，平衡信息量和信息密度</td></tr></tbody></table>

###  （三）Context Engineering vs Prompt Engineering

这两个概念经常被混淆，但它们的关注点截然不同：

<table><thead><tr><th style="text-align:left;">维度</th><th style="text-align:left;">Prompt Engineering</th><th style="text-align:left;">Context Engineering</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>关注点</strong></td><td style="text-align:left;">"怎么说"——指令的措辞、结构、语气</td><td style="text-align:left;">"给什么"——模型回答问题时能参考哪些信息</td></tr><tr><td style="text-align:left;"><strong>优化对象</strong></td><td style="text-align:left;">用户的提问方式</td><td style="text-align:left;">模型可见的信息集合</td></tr><tr><td style="text-align:left;"><strong>核心技能</strong></td><td style="text-align:left;">结构化表达、角色设定、约束设计</td><td style="text-align:left;">信息检索、数据清洗、知识组织</td></tr><tr><td style="text-align:left;"><strong>典型场景</strong></td><td style="text-align:left;">让模型写得更像某个风格、输出指定格式</td><td style="text-align:left;">让模型基于企业知识库回答客户问题</td></tr><tr><td style="text-align:left;"><strong>类比</strong></td><td style="text-align:left;">演讲技巧</td><td style="text-align:left;">资料准备</td></tr></tbody></table>

**两者的关系**：

```
最终输入给模型的 = Prompt（你怎么说）+ Context（你给什么背景信息）

输出质量 = f(Prompt 质量, Context 质量, 模型能力)
```

Prompt Engineering 再精妙，如果 Context 里缺少关键信息，模型也只能"瞎编"（幻觉）。Context Engineering 再完善，如果 Prompt 表达不清，模型也会答非所问。

##  二、为什么 Context Engineering 越来越重要？

###  （一）长上下文窗口：机会与挑战并存

2024-2026 年，大模型的上下文窗口从 4K 暴涨到 1M+ token：

<table><thead><tr><th style="text-align:left;">时间</th><th style="text-align:left;">代表性模型</th><th style="text-align:left;">上下文窗口</th></tr></thead><tbody><tr><td style="text-align:left;">2023 年初</td><td style="text-align:left;">GPT-3.5</td><td style="text-align:left;">4K</td></tr><tr><td style="text-align:left;">2023 年底</td><td style="text-align:left;">GPT-4</td><td style="text-align:left;">8K / 32K</td></tr><tr><td style="text-align:left;">2024 年</td><td style="text-align:left;">Claude 3</td><td style="text-align:left;">200K</td></tr><tr><td style="text-align:left;">2025 年</td><td style="text-align:left;">Gemini 1.5 Pro</td><td style="text-align:left;">1M</td></tr><tr><td style="text-align:left;">2026 年</td><td style="text-align:left;">Claude 3.7 / Kimi K2</td><td style="text-align:left;">1M+</td></tr></tbody></table>

**这带来了一个误区**："上下文窗口足够大了，直接把全部文档塞进去就行。"

**真相是**：

-   **长上下文 ≠ 高利用率**：研究表明，模型对长上下文中间部分的信息提取能力会下降（"Lost in the Middle"问题）
-   **长上下文 ≠ 低成本**：上下文越长，推理成本（时间和金钱）越高
-   **长上下文 ≠ 高精度**：信息过载反而会让模型抓不住重点

> 案例：你把一本 500 页的产品手册全部塞进 Prompt，问模型"我们产品的退货政策是什么？"模型可能在第 300 页找到了答案，但因为中间还夹杂着大量无关信息，它给出的回答可能遗漏了关键条款。

###  （二）RAG 的局限：检索到了，但组织不好

我们在《讲透 RAG》一节学过，RAG 通过检索外部知识来增强模型能力。但 RAG 只管"把相关文档找出来"，不管"怎么把这些文档组织成最优上下文"。

**RAG 的常见问题**：

<table><thead><tr><th style="text-align:left;">问题</th><th style="text-align:left;">表现</th><th style="text-align:left;">根因</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>信息碎片化</strong></td><td style="text-align:left;">检索到 10 段相关内容，但每段只有 2-3 句话，缺乏上下文</td><td style="text-align:left;">切片策略过细</td></tr><tr><td style="text-align:left;"><strong>信息冗余</strong></td><td style="text-align:left;">检索到的多段内容其实在说同一件事</td><td style="text-align:left;">去重机制缺失</td></tr><tr><td style="text-align:left;"><strong>逻辑断裂</strong></td><td style="text-align:left;">内容按相似度排序，但时间线或因果关系被打乱</td><td style="text-align:left;">缺乏语义组织</td></tr><tr><td style="text-align:left;"><strong>噪声污染</strong></td><td style="text-align:left;">检索结果中混入了低相关度的内容</td><td style="text-align:left;">阈值设置不当</td></tr></tbody></table>

这些问题，都需要 Context Engineering 来解决。

###  （三）Agent 的复杂决策：上下文是"记忆"

Agent 在执行多步骤任务时，每一步都需要依赖之前步骤的结果。这些历史信息构成了 Agent 的"工作记忆"。

**如果上下文管理不好**：

-   Agent 忘了 3 步之前用户的约束条件
-   Agent 被中间步骤的错误信息带偏
-   Agent 的"思考链"太长，导致最终决策质量下降

Context Engineering 决定了 Agent 能"记住"多少、"记住"什么、以及怎么"回忆"。

##  三、Context Engineering 的核心技术

Context Engineering 可以拆解为四个关键环节：**构建 → 压缩 → 检索 → 组织**。我们逐一讲解。

###  （一）上下文构建：从原始数据到可用信息

**目标**：把分散在各种来源的原始数据，转换成模型能理解的结构化信息。

**信息来源类型**：

<table><thead><tr><th style="text-align:left;">来源</th><th style="text-align:left;">示例</th><th style="text-align:left;">构建要点</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>结构化数据</strong></td><td style="text-align:left;">数据库、Excel、JSON</td><td style="text-align:left;">转为自然语言描述或表格</td></tr><tr><td style="text-align:left;"><strong>非结构化文档</strong></td><td style="text-align:left;">PDF、Word、网页</td><td style="text-align:left;">提取正文、过滤页眉页脚、保留层级结构</td></tr><tr><td style="text-align:left;"><strong>对话历史</strong></td><td style="text-align:left;">用户和模型的多轮对话</td><td style="text-align:left;">筛选关键轮次，压缩重复内容</td></tr><tr><td style="text-align:left;"><strong>代码库</strong></td><td style="text-align:left;">项目源码、配置文件</td><td style="text-align:left;">提取关键函数、类定义、依赖关系</td></tr><tr><td style="text-align:left;"><strong>实时信息</strong></td><td style="text-align:left;">天气、股价、库存</td><td style="text-align:left;">标注信息获取时间，处理时效性</td></tr></tbody></table>

**构建原则**：

1.  **保留语义完整性**：不要把一个完整的流程拆得七零八落
2.  **标注信息来源**：让模型知道这段信息来自哪里、是否可信
3.  **处理时效性**：明确标注信息的生成时间，避免模型用过期信息做判断

**示例：结构化数据转上下文**

原始数据（数据库记录）：

```
{"user_id": 10086, "order_date": "2026-05-20", "amount": 299, "status": "refunded"}
```

构建后的上下文：

```
【订单信息】
用户 ID：10086
下单日期：2026-05-20
订单金额：299 元
当前状态：已退款
数据来源：订单系统（2026-05-25 查询）
```

###  （二）上下文压缩：在海量信息中抓重点

**目标**：在保留核心语义的前提下，减少上下文长度。

**常用技术**：

####  1. 摘要压缩（Summarization）

把长文档压缩成简短摘要，只保留关键信息。

```
原始内容：一篇 5000 字的产品需求文档
压缩后：200 字的"需求概述 + 核心功能点 + 验收标准"
```

**适用场景**：历史文档、背景信息、参考资料

####  2. 选择性保留（Selective Retention）

根据与当前问题的相关度，只保留最相关的段落。

```
原始内容：用户手册 100 页
压缩后：只保留与"退货流程"相关的 3 个章节（约 5 页）
```

**适用场景**：RAG 检索结果、知识库问答

####  3. 结构化压缩（Structured Compression）

用更紧凑的格式表达同样的信息。

```
原始内容：
"我们的退货政策规定，自签收之日起 7 天内，商品未使用、包装完好、
配件齐全的情况下，可以申请无理由退货。退货邮费由买家承担，
特殊商品（生鲜、定制类）不支持退货。"

压缩后（结构化）：
退货政策：
- 时限：签收后 7 天
- 条件：未使用 + 包装完好 + 配件齐全
- 费用：买家承担邮费
- 例外：生鲜、定制类不支持
```

####  4. 向量化压缩（Embedding-based Compression）

用向量表示替代原始文本，在需要时再解码。这是更前沿的研究方向。

**压缩技术的权衡**：

<table><thead><tr><th style="text-align:left;">技术</th><th style="text-align:left;">压缩率</th><th style="text-align:left;">信息损失</th><th style="text-align:left;">实现难度</th></tr></thead><tbody><tr><td style="text-align:left;">摘要压缩</td><td style="text-align:left;">中（5-10x）</td><td style="text-align:left;">中</td><td style="text-align:left;">低</td></tr><tr><td style="text-align:left;">选择性保留</td><td style="text-align:left;">高（10-50x）</td><td style="text-align:left;">低（保留完整段落）</td><td style="text-align:left;">中</td></tr><tr><td style="text-align:left;">结构化压缩</td><td style="text-align:left;">中（3-5x）</td><td style="text-align:left;">低</td><td style="text-align:left;">低</td></tr><tr><td style="text-align:left;">向量化压缩</td><td style="text-align:left;">极高（100x+）</td><td style="text-align:left;">待验证</td><td style="text-align:left;">高</td></tr></tbody></table>

###  （三）上下文检索：找到"最需要"的信息

**目标**：在需要时，快速、准确地找到与当前任务最相关的信息。

Context Engineering 中的检索，和 RAG 的检索有微妙的不同：

<table><thead><tr><th style="text-align:left;">维度</th><th style="text-align:left;">RAG 检索</th><th style="text-align:left;">Context Engineering 检索</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>检索对象</strong></td><td style="text-align:left;">外部知识库</td><td style="text-align:left;">任意信息源（对话历史、代码库、文档等）</td></tr><tr><td style="text-align:left;"><strong>检索目的</strong></td><td style="text-align:left;">找到"相关文档"</td><td style="text-align:left;">找到"对当前决策最有帮助的信息"</td></tr><tr><td style="text-align:left;"><strong>结果处理</strong></td><td style="text-align:left;">直接拼接进 Prompt</td><td style="text-align:left;">需要进一步筛选、排序、组织</td></tr><tr><td style="text-align:left;"><strong>时效性要求</strong></td><td style="text-align:left;">一般</td><td style="text-align:left;">高（特别是对话和代码场景）</td></tr></tbody></table>

**进阶检索策略**：

####  1. 多路召回（Multi-channel Retrieval）

同时用多种方式检索，合并结果：

-   向量语义检索：找"意思相关"的内容
-   关键词检索：找"精确匹配"的内容
-   图谱检索：找"逻辑关联"的内容（如"这个功能依赖哪个模块"）

####  2. 层次化检索（Hierarchical Retrieval）

先粗粒度定位，再细粒度深挖：

```
第 1 层：检索到"用户手册第 3 章"
第 2 层：在第 3 章中检索"退货政策"小节
第 3 层：在"退货政策"中定位"例外条款"
```

####  3. 时序感知检索（Temporal-aware Retrieval）

对有时间线的信息（如对话历史、版本变更），优先检索最近的内容：

```
对话历史权重 = 语义相关度 × 时间衰减系数
```

###  （四）上下文组织：让信息"好消化"

**目标**：以最优的结构和顺序呈现信息，帮助模型高效理解。

####  组织原则 1：先总后分

先给概览，再给细节。模型和人类的阅读理解习惯一致——先看到"地图"，再看"街道"。

```
❌ 不好的组织：
[段落 1：登录接口的字段定义]
[段落 2：产品整体架构]
[段落 3：登录接口的错误码]
[段落 4：用户角色权限体系]

✅ 好的组织：
[概述：这是一个电商平台的登录模块]
[架构：登录模块在系统中的位置和依赖关系]
[接口详情：字段定义、错误码、示例]
[关联信息：用户角色、权限、安全策略]
```

####  组织原则 2：重要性排序

把最相关的信息放在上下文的开头和结尾（模型对中间部分的注意力较弱）。

```
【高优先级】与当前问题直接相关的核心信息
【中优先级】辅助理解的背景信息
【低优先级】参考资料和延伸阅读
【高优先级】关键约束条件和特殊说明
```

####  组织原则 3：显式标注关系

不要让模型"猜"信息之间的关系，要显式标注：

```
❌ 隐式关系：
"用户需要登录后才能下单。"
"下单后 24 小时内可以取消。"

✅ 显式关系：
【规则 A】登录 → 下单（前置条件）
【规则 B】下单时间 < 24h → 可取消（时间约束）
【规则依赖】规则 B 依赖规则 A（必须先登录下单）
```

####  组织原则 4：隔离冲突信息

如果上下文中有矛盾的信息（如新旧版本的政策），要显式标注：

```
【退货政策 - 2026-01-01 生效版本】
签收后 7 天可退...

【退货政策 - 2026-06-01 生效版本】
签收后 15 天可退...

⚠️ 注意：当前日期 2026-05-25，应适用旧版本（7 天）。
```

##  四、典型场景中的 Context Engineering

###  （一）RAG 系统：从"检索到文档"到"组织好上下文"

**问题**：传统 RAG 只关注"能不能找到相关文档"，但找到后怎么组织，直接影响回答质量。

**Context Engineering 优化方案**：

```
用户提问："这款手机的保修政策是什么？"

【步骤 1：多路召回】
- 向量检索：找到"保修政策"相关段落（3 段）
- 关键词检索：找到"保修期""维修"相关内容（2 段）
- 图谱检索：找到"手机""配件"的保修差异（1 段）

【步骤 2：去重与筛选】
- 发现 2 段内容重复，保留更完整的那段
- 排除 1 段低相关度的"配件保修"内容

【步骤 3：压缩】
- 把 3 段长文摘要为"核心政策要点"

【步骤 4：组织】
最终上下文结构：
---
【问题】用户询问 XX 手机的保修政策
【核心政策】（摘要）
  - 保修期限：1 年
  - 保修范围：主机、电池、充电器
  - 不保范围：人为损坏、进水、私自拆机
【详细条款】（原文关键段落）
【例外说明】（海外版/企业版的特殊政策）
【信息时效】文档版本：2026-03-15
---
```

###  （二）Agent 系统：管理"工作记忆"

Agent 执行多步骤任务时，每一步都会产生新的信息。Context Engineering 要管理这个动态增长的记忆：

**策略 1：短期记忆 vs 长期记忆分层**

<table><thead><tr><th style="text-align:left;">记忆类型</th><th style="text-align:left;">内容</th><th style="text-align:left;">管理方式</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>短期记忆</strong></td><td style="text-align:left;">当前任务的最近 3-5 步操作</td><td style="text-align:left;">完整保留，直接放入上下文</td></tr><tr><td style="text-align:left;"><strong>中期记忆</strong></td><td style="text-align:left;">本轮对话的关键决策和约束</td><td style="text-align:left;">摘要压缩后保留</td></tr><tr><td style="text-align:left;"><strong>长期记忆</strong></td><td style="text-align:left;">用户画像、历史偏好、项目背景</td><td style="text-align:left;">从知识库中动态检索</td></tr></tbody></table>

**策略 2：关键信息锚定**

在上下文中始终保留用户的核心约束，防止 Agent"遗忘"：

```
【任务目标】帮用户预订一张下周去上海的机票
【硬性约束】✈️ 预算 < 1500 元 | 🕐 出发时间：上午 8-12 点 | 🚫 不接红眼航班

【已执行步骤】
1. 查询到 3 个符合条件的航班...（摘要）
2. 用户选择了航班 CA1234...（摘要）

【下一步】确认座位偏好
```

**策略 3：错误信息隔离**

当某一步出现错误时，不要让错误信息污染后续决策：

```
【步骤 3 尝试】调用支付接口 → ❌ 失败（余额不足）
【错误隔离】已记录失败原因，不影响后续步骤
【步骤 3 修正】提示用户更换支付方式 → ✅ 成功
```

###  （三）VibeCoding：让 AI"读懂"整个项目

在 VibeCoding 场景中，模型需要理解整个代码库的上下文才能生成正确的代码。Context Engineering 的关键挑战是：**代码库通常远大于上下文窗口，怎么让模型掌握"足够的背景"？**

###  （二）常见上下文问题诊断

**症状 1：模型"幻觉"严重**

> 表现：模型经常编造不存在的信息。
> 
> 根因诊断：
> 
> -   上下文里缺少关键信息，模型只能"猜"
> -   上下文里有矛盾信息，模型无法判断哪个是对的
> -   上下文组织混乱，模型理解错了信息之间的关系

**症状 2：模型"答非所问"**

> 表现：回答的内容和问题的关联度很低。
> 
> 根因诊断：
> 
> -   检索策略有问题，召回的内容和问题不匹配
> -   上下文里噪声太多，淹没了关键信息
> -   问题本身需要的信息分散在多个文档中，但只检索到了一部分

**症状 3：模型"记性差"**

> 表现：多轮对话后，模型忘记了之前的约束条件。
> 
> 根因诊断：
> 
> -   对话历史太长，早期的关键信息被截断
> -   没有显式保留"核心约束"在上下文中
> -   中期记忆没有做摘要，导致有效信息密度下降

###  （三）优化上下文的实用方法

####  方法 1：建立"上下文基线"

为你的核心场景，人工整理一份"理想上下文"，作为评估基准：

```
场景：用户询问"如何退货"
理想上下文应该包含：
✅ 退货时限
✅ 退货条件
✅ 退货流程
✅ 运费承担方
✅ 例外情况（哪些商品不能退）
✅ 退款到账时间

每次系统升级后，用同样的测试问题，对比实际上下文和理想上下文的差距。
```

对同一批问题，用不同的上下文构建策略，对比回答质量：

####  方法 3：监控"上下文利用率"

在系统中埋点，统计：

-   每次请求的平均上下文长度
-   模型输出中引用了上下文里的哪些信息
-   上下文里的信息有多少被"浪费"了（未引用）

**目标**：让上下文中的每一条信息都"物尽其用"。

##  六、写在最后

Context Engineering 是一个正在快速演进的领域。随着大模型上下文窗口越来越长、多模态能力越来越强，上下文的形态也在从"纯文本"扩展到"文本 + 图像 + 音频 + 结构化数据"。

但无论技术如何演进，Context Engineering 的核心逻辑不会变：

::: tip 核心考点
核心原则

**给模型"恰好足够"的信息——不多不少、不早不晚、不乱不散。**
:::

作为 AI 产品经理，你需要记住三个关键数字：

1.  **70%**：在 RAG 和 Agent 系统中，回答质量的瓶颈 70% 出在上下文上，而不是模型能力上
2.  **3 步**：优化上下文的三个步骤——找到对的信息、压缩到合适的长度、组织成清晰的结构
3.  **1 个测试**：每次上线前，用"理想上下文"做基线测试，确保系统交付的信息质量达标

Prompt Engineering 让你学会"怎么问"，RAG 让你学会"怎么找"，Agent 让你学会"怎么做"。而 Context Engineering，让你学会 **"怎么让 AI 知道它需要知道的一切"**。
