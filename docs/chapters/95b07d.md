#  Function Call：让大模型从"嘴炮王者"变身"实干家"

> 如果说大模型是一个博学多才但闭门不出的书生，那 Function Call 就是给他配了一个万能助理——书生负责思考和决策，助理负责跑腿和办事。

* * *

##  一、Function Call 是什么：大模型的"遥控器"

**一句话定义**：Function Call（函数调用）是指大语言模型在理解用户意图后，不直接生成回答，而是判断应该调用哪个外部工具/函数，并输出调用该函数所需的参数，由程序执行后再将结果反馈给模型，最终生成完整回答。

###  1.1 用一个生活场景理解

想象你走进一家五星级酒店的大堂，对着前台说："我想明天去北京，帮我安排一下。"

如果没有 Function Call，前台（大模型）只能基于自己的知识告诉你："北京是个好地方，有很多景点，比如故宫、长城……"——说得天花乱坠，但你的机票和酒店一点着落都没有。

有了 Function Call，前台会变成这样：

1.  **听懂需求**：用户要出差去北京，需要机票和酒店
2.  **判断该找谁**：这事儿得找订票系统和酒店系统
3.  **填好工单**：在内部系统下单——查询明天去北京的航班、预订公司协议酒店
4.  **拿到结果**：系统返回航班列表和酒店房态
5.  **回复用户**："已为您查到明天 3 趟航班，推荐上午 9 点的国航 CA1234，同时预订了北京朝阳区的 XX 酒店，含早餐，离客户公司 2 公里。"

**Function Call 的本质，就是让大模型学会"分工"：思考的事我来做，执行的事交给专业系统。**

###  1.2 技术层面发生了什么（产品经理只需了解这个程度）

```
用户提问
   ↓
大模型分析：这个问题需要调用外部工具吗？
   ↓
是 → 输出 JSON：{"function": "查询航班", "参数": {"目的地": "北京", "日期": "明天"}}
   ↓
程序解析 JSON，调用真实的航班查询 API
   ↓
API 返回结果：[{航班1信息}, {航班2信息}]
   ↓
结果返回给大模型
   ↓
大模型基于航班数据，生成最终回答
```

你看，大模型其实没有真的去"查航班"——它只是发了一张"工单"，真正干活的是后端的航班系统。但用户感知上，就是 AI 帮我查到了航班。

##  二、为什么需要 Function Call：大模型的三大"先天不足"

大模型虽然聪明，但天生有三大短板，Function Call 就是为了补齐这些短板而生的。

###  2.1 不能获取实时信息

大模型的知识是"历史知识"，训练数据有截止日期。你问它"今天北京天气怎么样"，它要么瞎编，要么说不知道。

**没有 Function Call 的对话**：

> 用户：今天北京天气怎么样？ 大模型：很抱歉，我无法获取实时天气信息。建议您查看天气预报网站。

**有了 Function Call 的对话**：

> 用户：今天北京天气怎么样？ AI：北京今天晴，气温 18-26°C，南风 2 级，空气质量良，适合外出。下午 3 点可能有阵雨，建议带伞。

**背后的逻辑**：模型识别出"需要实时天气"→ 调用天气 API → 获取实时数据 → 组织语言回答。

###  2.2 不能执行操作

大模型只能"说话"，不能"做事"。你说"帮我订一张去上海的机票"，它不能真的去航空公司下单。

Function Call 让大模型变成了"指挥官"，它可以发出指令，由外部系统执行实际的业务操作：订票、下单、发邮件、创建日程、转账……

###  2.3 不能访问私有数据

企业内部的客户资料、订单数据、库存信息，大模型在训练时肯定没见过。Function Call 就像一个数据桥梁，让大模型在用户提问时，实时去查询企业的私有数据库。

##  三、核心原理：一张工单的生命周期

作为产品经理，你不需要懂代码，但需要理解 Function Call 的完整流程——这直接决定了你如何设计产品交互、如何定义功能边界。

###  3.1 四步流程（产品经理视角）

**第一步：注册工具（告诉模型你会什么）**

在产品启动时，我们把所有可用的"工具"清单告诉大模型。就像给新员工发一本《岗位操作手册》，里面写着：

-   你会查询天气（需要什么参数：城市、日期）
-   你会预订酒店（需要什么参数：城市、入住日期、离店日期、预算）
-   你会查询订单（需要什么参数：订单号、手机号）

这个清单在专业术语里叫 **Function Schema**，后面我们会详细讲怎么设计。

**第二步：用户提问（触发判断）**

用户说："我明天去深圳出差，帮我找个 500 块左右的酒店。"

大模型接收到这个问题后，会先进行"意图分析"：这个问题需要调用工具吗？需要调用哪个工具？需要传哪些参数？

**第三步：输出"工单"（JSON 格式）**

大模型不直接回答，而是输出一个结构化的 JSON：

```
{
  "name": "search_hotel",
  "arguments": {
    "city": "深圳",
    "check_in": "2026-05-30",
    "check_out": "2026-05-31",
    "max_price": 500
  }
}
```

这就是"工单"——模型已经判断清楚：要调用"搜索酒店"函数，参数都已填好。

**第四步：执行与返回**

程序收到这个 JSON 后，调用真实的酒店搜索 API，拿到结果后再传给大模型。大模型基于真实数据生成最终回答：

> "已为您找到深圳 5 家符合条件的酒店，推荐以下 3 家：
> 
> 1.  XX 酒店（福田区），商务大床房 ¥468，距会展中心 1.5 公里，评分 4.8
> 2.  XX 公寓（南山区），标准间 ¥430，近科技园，评分 4.6
> 3.  XX 快捷（罗湖区），大床房 ¥399，距高铁站 800 米，评分 4.5
> 
> 需要我帮您预订哪一家？"

很多产品经理会问：Function Call 和 Prompt Engineering（提示词工程）有什么关系？用了 Function Call 还需要写 Prompt 吗？

###  4.2 两者的关系：Prompt 是地基，Function Call 是上层建筑

**Function Call 并不取代 Prompt Engineering，而是在它的基础上扩展了能力边界。**

你可以这样理解：

-   **Prompt Engineering** 是"用嘴说"——你告诉模型"你是谁、你要干什么、怎么回答"
-   **Function Call** 是"给工具"——你告诉模型"除了这些，你还可以用这些工具"

实际上，Function Call 的生效高度依赖 Prompt 设计。如果你没有在系统提示词里把 Function Schema 描述清楚，模型根本不知道该调用什么工具。

##  五、六大产品应用场景：Function Call 能做什么

Function Call 不是炫技，而是解决真实的产品问题。以下是六个最典型的应用场景，每个都配有产品设计思路。

###  场景一：实时数据查询——让 AI 拥有"当下之眼"

**案例：智能投研助手**

用户问："特斯拉最近一周股价走势如何？有什么重要新闻？"

**Function Call 设计**：

-   `get_stock_price(symbol, period)`：获取股价数据
-   `get_company_news(symbol, days)`：获取公司新闻
-   `analyze_trend(data)`：基于数据生成分析

**产品价值**：投资经理不用在多个终端之间切换，直接对话获取整合后的分析。

###  场景二：操作外部系统——让 AI 成为"超级入口"

**案例：智能办公助手**

用户说："帮我预约明天下午 3 点和张总的会议室，再发一封会议邮件。"

**Function Call 设计**：

-   `check_room_availability(date, time, duration)`：查会议室空闲情况
-   `book_room(room_id, date, time, attendees)`：预订会议室
-   `send_email(to, subject, content, attachments)`：发送邮件

**产品价值**：一句话完成过去需要在 3 个系统里操作的流程。

###  场景三：多步骤任务——让 AI 具备"规划能力"

**案例：智能理赔助手**

用户说："我的车昨天剐蹭了，想走保险。"

这需要一连串操作：

1.  查询用户保单信息 → `get_policy_info(user_id)`
2.  创建理赔工单 → `create_claim(user_id, incident_date, type)`
3.  预约定损地点 → `book_assessment(claim_id, location, preferred_time)`
4.  发送理赔指引短信 → `send_sms(phone, template_id, params)`

大模型会自主规划调用顺序，一步步完成整个流程，并在每一步向用户确认关键信息。

###  场景四：权限控制——让 AI 知道"什么能干什么不能干"

**案例：企业知识库助手**

不同级别的员工能查到的信息不同：

-   普通员工：只能查公开文档
-   部门经理：可以查部门预算、人员编制
-   HR：可以查全员薪酬（脱敏）

通过 Function Call 的权限设计，同一个 AI 助手，对不同用户暴露不同的工具集合。模型根本"看不到"它没有权限调用的函数，自然也不会越权。

###  场景五：结构化输出——让 AI 输出"机器能读的答案"

**案例：智能表单填写**

用户发了一大段语音："我叫张三，手机号 13800138000，我想申请 5 月 30 号到 6 月 2 号去上海出差，预算是 3000 块，住亚朵或者全季都可以。"

大模型可以调用一个"信息提取"函数，直接输出结构化的 JSON：

```
{
  "applicant": "张三",
  "phone": "13800138000",
  "destination": "上海",
  "start_date": "2026-05-30",
  "end_date": "2026-06-02",
  "budget": 3000,
  "hotel_preference": ["亚朵", "全季"]
}
```

这个 JSON 可以直接写入数据库，无需人工二次录入。

###  场景六：混合智能——模型决策 + 专业算法

**案例：智能风控审批**

用户申请贷款，AI 助手需要：

1.  调用征信查询接口 → 获取信用评分
2.  调用反欺诈模型 → 获取风险等级
3.  调用规则引擎 → 判断是否符合准入条件
4.  大模型综合所有结果 → 生成审批结论和解释

这里大模型不负责算风险（这是专业算法模型的事），它负责"整合信息、解释结论、与客户沟通"。

##  六、Function Call vs RAG：不是竞争对手，是黄金搭档

很多产品经理会把 Function Call 和 RAG（检索增强生成）搞混，甚至觉得两者是"二选一"的关系。实际上，它们是解决不同问题的两把利器，经常一起使用。

###  6.1 两者的核心差异

<table><thead><tr><th style="text-align:left;">维度</th><th style="text-align:left;">RAG（检索增强生成）</th><th style="text-align:left;">Function Call（函数调用）</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>解决的问题</strong></td><td style="text-align:left;">大模型知识不足/过时</td><td style="text-align:left;">大模型无法获取实时数据/执行操作</td></tr><tr><td style="text-align:left;"><strong>数据来源</strong></td><td style="text-align:left;">向量数据库、文档库、知识库</td><td style="text-align:left;">API、数据库、业务系统</td></tr><tr><td style="text-align:left;"><strong>获取方式</strong></td><td style="text-align:left;">语义检索（向量相似度匹配）</td><td style="text-align:left;">结构化调用（传参获取精确结果）</td></tr><tr><td style="text-align:left;"><strong>返回内容</strong></td><td style="text-align:left;">文本片段、文档段落</td><td style="text-align:left;">结构化数据、执行结果</td></tr><tr><td style="text-align:left;"><strong>执行能力</strong></td><td style="text-align:left;">无，只能查文档</td><td style="text-align:left;">有，可以触发操作</td></tr><tr><td style="text-align:left;"><strong>典型场景</strong></td><td style="text-align:left;">企业知识问答、智能客服</td><td style="text-align:left;">订票、下单、查实时数据</td></tr></tbody></table>

###  6.2 类比理解

-   **RAG** 像给大模型配了一个图书馆管理员：用户提问，管理员去书库找相关的书，把相关章节翻出来给大模型参考。
-   **Function Call** 像给大模型配了一个助理团队：用户有需求，大模型判断该让哪个助理去办（查天气、订机票、写邮件）。

###  6.3 组合使用的威力

**案例：智能医疗助手**

用户问："我最近总是头晕，可能是什么问题？需要做什么检查？挂什么科？"

一个完整的 AI 产品可能会这样处理：

1.  **RAG 环节**：从医学知识库中检索"头晕"相关的疾病知识、检查项目、科室信息
2.  **Function Call 环节**：
    -   调用医院 API：查询最近 3 天神经内科的号源
    -   调用检查预约 API：查询血常规、头颅 CT 的可预约时间
3.  **大模型整合**：基于医学知识和实时号源信息，生成完整建议

> **产品经理关注点**：在产品架构设计时，不要纠结"用 RAG 还是用 Function Call"，而要思考"用户的问题需要哪些信息、需要哪些操作"，然后两者搭配使用。

##  八、实战案例：设计一个"智能差旅助手"

###  8.1 产品背景

某互联网公司有 2000 名员工，每月差旅报销量巨大。员工出差需要：查航班→订酒店→提交报销→跟踪审批。目前这些操作分散在 4 个系统里，体验极差。

##  九、产品经理如何定义 Function Schema

Function Schema 是 Function Call 的"产品需求文档"，定义得好坏直接决定模型能不能正确调用。以下是设计原则。

###  9.1 函数命名：让模型和人类都能看懂

<table><thead><tr><th style="text-align:left;">❌ 不好的命名</th><th style="text-align:left;">✅ 好的命名</th><th style="text-align:left;">原因</th></tr></thead><tbody><tr><td style="text-align:left;">func_01</td><td style="text-align:left;">search_flight</td><td style="text-align:left;">模型无法理解数字含义</td></tr><tr><td style="text-align:left;">getData</td><td style="text-align:left;">get_weather_by_city</td><td style="text-align:left;">太笼统，模型不知道获取什么数据</td></tr><tr><td style="text-align:left;">hotel</td><td style="text-align:left;">book_hotel</td><td style="text-align:left;">名词无法表达动作，模型不知道是查还是订</td></tr></tbody></table>

**命名规范**：`动词_名词_修饰词`，如 `search_flight`、`cancel_order`、`get_user_profile`。

###  9.2 函数描述：说清楚"这个函数是干什么的"

每个函数都需要一段 description，这是模型判断"该不该调用这个函数"的核心依据。

<table><thead><tr><th style="text-align:left;">❌ 不好的描述</th><th style="text-align:left;">✅ 好的描述</th></tr></thead><tbody><tr><td style="text-align:left;">"查询航班"</td><td style="text-align:left;">"根据出发地、目的地和日期查询可选航班列表，返回航班号、起降时间、价格和余票信息。仅用于查询，不执行预订操作。"</td></tr></tbody></table>

**要点**：说清楚函数能做什么、不能做什么、返回什么信息。

###  9.3 参数设计：必填 vs 选填的艺术

<table><thead><tr><th style="text-align:left;">原则</th><th style="text-align:left;">说明</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>核心信息必填</strong></td><td style="text-align:left;">没有这些信息函数完全无法执行</td></tr><tr><td style="text-align:left;"><strong>偏好信息选填</strong></td><td style="text-align:left;">有则筛选，无则返回全部</td></tr><tr><td style="text-align:left;"><strong>提供默认值</strong></td><td style="text-align:left;">减少用户输入负担</td></tr><tr><td style="text-align:left;"><strong>参数类型明确</strong></td><td style="text-align:left;">string/number/boolean/enum，不要用模糊类型</td></tr></tbody></table>

**示例**：查询航班

-   必填：出发地、目的地、出发日期（没有这些查不了）
-   选填：偏好时段、最高价格、航空公司偏好（有就筛选，没有就全返回）

###  9.4 参数描述：每个字段都要解释清楚

<table><thead><tr><th style="text-align:left;">参数名</th><th style="text-align:left;">❌ 不好的描述</th><th style="text-align:left;">✅ 好的描述</th></tr></thead><tbody><tr><td style="text-align:left;">departure_date</td><td style="text-align:left;">"出发日期"</td><td style="text-align:left;">"航班出发日期，格式 YYYY-MM-DD，如 2026-06-01。不支持过去日期。"</td></tr><tr><td style="text-align:left;">max_price</td><td style="text-align:left;">"最高价"</td><td style="text-align:left;">"能接受的最大票价（人民币），单位元。仅返回票价低于此值的航班。"</td></tr></tbody></table>

**要点**：格式、单位、取值范围、限制条件，都要写清楚。

###  9.5 避免"万能函数"陷阱

很多产品经理为了省事，喜欢设计一个"万能查询函数"：

```
❌ 错误示范：
function: query(type, keyword)
// type 可以是 flight/hotel/order/weather/news...
```

这样做的后果是模型经常搞错 type，或者把酒店查询参数传到航班查询里。

**正确做法**：宁可函数多几个，也要保证每个函数职责单一、参数清晰。

##  十、安全与权限设计：别让 AI 成为"内鬼"

Function Call 让 AI 拥有了"动手"的能力，这既是优势，也是风险。如果设计不当，AI 可能会越权操作、误删数据、甚至泄露敏感信息。

###  10.1 三大安全风险

<table><thead><tr><th style="text-align:left;">风险类型</th><th style="text-align:left;">具体表现</th><th style="text-align:left;">防护方案</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>越权调用</strong></td><td style="text-align:left;">普通员工通过 AI 查到高管薪酬</td><td style="text-align:left;">用户身份校验 + 函数级权限控制</td></tr><tr><td style="text-align:left;"><strong>参数注入</strong></td><td style="text-align:left;">用户输入恶意参数导致数据泄露</td><td style="text-align:left;">参数校验 + 白名单机制</td></tr><tr><td style="text-align:left;"><strong>误操作</strong></td><td style="text-align:left;">AI 理解错意图，帮用户取消了重要订单</td><td style="text-align:left;">高危操作二次确认 + 操作日志</td></tr></tbody></table>

###  10.2 权限设计四层模型

**第一层：函数可见性**

不同角色看到不同的"工具箱"：

<table><thead><tr><th style="text-align:left;">角色</th><th style="text-align:left;">可见函数</th></tr></thead><tbody><tr><td style="text-align:left;">普通员工</td><td style="text-align:left;">查询航班、查询酒店、提交报销、查进度</td></tr><tr><td style="text-align:left;">部门经理</td><td style="text-align:left;">以上 + 审批报销、查看部门差旅预算</td></tr><tr><td style="text-align:left;">财务人员</td><td style="text-align:left;">以上 + 导出报销报表、修改报销规则</td></tr><tr><td style="text-align:left;">系统管理员</td><td style="text-align:left;">全部函数</td></tr></tbody></table>

**实现方式**：在调用大模型前，根据用户角色过滤 Function Schema 列表。模型"看不到"的函数，自然也不会调用。

**第二层：参数级权限**

同样是"查询订单"，普通员工只能查自己的，客服主管可以查本组的，管理员可以查全公司的。

**实现方式**：在 API 网关层校验用户身份，不依赖模型"自觉"。

**第三层：高危操作确认**

以下操作必须人工二次确认：

-   取消已支付订单
-   删除数据
-   转账/付款
-   修改他人信息

**产品方案**：AI 生成"操作确认卡片"，用户点击"确认"后才真正执行。

**第四层：操作审计日志**

所有 Function Call 调用记录都要留痕：谁、什么时候、调用了什么函数、传了什么参数、结果如何。便于事后追溯。

###  10.3 产品经理关注点

-   **安全不是后端一个人的事**：你在设计 Function Schema 时就要标注"此函数是否涉及敏感数据""此函数是否为高危操作"
-   **默认拒绝原则**：没有明确权限的，默认不让调用
-   **最小权限原则**：每个函数只暴露必要的最小数据集

##  十一、常见误区与避坑指南

###  误区一：Function Call 是万能的

**错误认知**：有了 Function Call，大模型什么都能做。

**真相**：Function Call 只是"调用工具的协议"，工具本身的能力决定了上限。如果你的航班查询 API 本身只能查 3 天内的数据，Function Call 也变不出 30 天后的航班。

**避坑**：在引入 Function Call 前，先盘点现有系统的 API 能力，别对大模型有不切实际的期待。

###  误区二：Schema 设计随便写写就行

**错误认知**：参数描述不重要，模型那么聪明，肯定能理解。

**真相**：模型对 Schema 的理解完全依赖于你的文字描述。描述模糊，模型就会猜，猜错就得试错，试错就增加延迟和成本。

**避坑**：把 Schema 当作给新员工的岗位说明书来写——假设读它的人什么都不懂，需要手把手教。

###  误区三：错误处理交给后端就行了

**错误认知**：API 报错后端处理就行，前端/模型不用管。

**真相**：用户看到的是 AI 助手的回答，如果 API 超时了，AI 支支吾吾或者说"系统错误"，体验极差。

**避坑**：产品设计时要定义完整的"错误处理话术库"，让 AI 在遇到不同错误时，能给用户清晰、友好的反馈，并提供替代方案。

###  误区四：Function Call 可以完全替代界面

**错误认知**：有了对话式 AI，原来的页面都不需要了。

**真相**：Function Call 适合"任务型"交互，但不适合"浏览型"交互。比如选酒店，用户可能想先看地图、看图片、看评价——这些用对话交互效率极低。

**避坑**：Function Call + 传统界面混合设计。对话负责"发起任务和确认"，界面负责"展示复杂信息和精细操作"。

###  误区五：只测 happy path

**错误认知**：测试时只试正常的用户输入，上线后发现各种奇葩情况。

**真相**：真实用户的表达千奇百怪："帮我搞个去上海的票""下周二飞魔都，住好点的地方""我不想去浦东那边，太远了"。

**避坑**：测试阶段必须覆盖：模糊表达、口语化表达、缺参数、多意图、否定意图（"不要早上的航班"）等各种边界情况。

###  13.2 产品经理行动清单

**如果你正准备在产品中引入 Function Call，按以下清单逐项检查：**

-   \[ \] **需求确认**：用户的问题中，有多少比例需要实时数据或执行操作？（如果低于 20%，Function Call 价值有限）
-   \[ \] **API 盘点**：现有业务系统是否已有可用的 API？如果没有，开发成本是多少？
-   \[ \] **模型选型**：基于预算和场景，选定 1-2 个主用模型做 POC 测试
-   \[ \] **Schema 设计**：完成核心场景的 Function Schema 设计文档
-   \[ \] **权限梳理**：梳理每个函数的用户权限要求，画出权限矩阵
-   \[ \] **异常设计**：列出所有可能的错误场景，设计对应的用户提示话术
-   \[ \] **测试用例**：准备 20+ 条测试用例，覆盖正常、边界、异常场景
-   \[ \] **成本测算**：测算单用户单次对话的平均成本，评估规模化后的费用
-   \[ \] **体验打磨**：设计加载态、中间态、错误态的交互方案
-   \[ \] **数据埋点**：设计 Function Call 成功率、延迟、错误率的监控指标

###  13.3 快速自检：你的产品适合 Function Call 吗？

回答以下问题，如果有一半以上选"是"，说明你的产品非常值得引入 Function Call：

1.  用户经常问"现在/今天/本周……"这类需要实时数据的问题？
2.  用户需要在 AI 对话中完成操作（下单、预约、提交申请）？
3.  你的产品涉及多个业务系统，用户需要在系统间切换？
4.  用户的问题经常需要多个步骤才能解决？
5.  你的业务数据无法公开用于大模型训练（需要私有化/实时查询）？
6.  现有纯对话体验让用户觉得"光说不练"？

##  写在最后

Function Call 是大模型从"聊天玩具"走向"生产力工具"的关键一步。对 AI 产品经理来说，它既是机遇也是挑战：

-   **机遇**：你可以设计出真正"能干活"的 AI 产品，让用户感受到"智能"二字的重量
-   **挑战**：你需要理解技术边界、设计严谨的调用流程、考虑安全和异常、平衡成本与体验

记住，Function Call 不是让大模型变得更聪明，而是让它变得更"有用"。聪明是模型自己的事，有用才是产品经理该操心的事。
