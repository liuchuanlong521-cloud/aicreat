#  3.22 AG-UI：让 AI Agent 真正"住进"你的产品界面

> **一句话定义**：AG-UI（Agent-User Interaction Protocol，Agent-用户交互协议）是 2025 年诞生的开放标准，它定义了 AI Agent 与前端界面之间如何"对话"——让后端的智能体能够实时、结构化、可交互地驱动前端界面，让用户看到 Agent 在"想"什么、"做"什么、"要"什么。

想象一下：用户在你的 SaaS 产品里说一句"帮我分析一下上个月的销售数据"，Agent 开始在后端运转。传统体验里，用户只能盯着转圈圈，等 10 秒后弹出一个最终结果。而 AG-UI 带来的体验是：用户看到 Agent 正在"拆解任务"、"调用数据库"、"生成图表"、"发现异常"——每一步都实时出现在界面上，中间还能暂停、纠正、确认。

这不是更炫的动画，而是**产品交互范式的升级**：AI 从一个"黑盒 API"变成了一个"可见、可控、可协作的同事"。

* * *

##  一、AG-UI 是什么：Agent 与界面的"通用翻译器"

![](https://oss.fullcoding.cn/20260708/891c6395-cc80-4921-8919-107d7872cc3d_1783510986351.png)

AG-UI 是一个**开放、轻量级、基于事件流**的协议。它标准化了 Agent 后端向前端应用发送什么、前端如何理解并响应。

你可以把它理解为 Agent 世界的"HDMI 线"：

-   以前，每个 Agent 产品都要自己发明一套"后端说什么、前端怎么画"的规则
-   AG-UI 出现后，只要前后端都支持这个协议，就能即插即用

在 AG-UI 的语境里，一次用户交互不是简单的"请求 → 响应"，而是一段**持续的、双向的、有状态的对话流**：

<table><thead><tr><th>传统 API 模式</th><th>AG-UI 事件流模式</th></tr></thead><tbody><tr><td>用户提问 → 等待 → 收到最终答案</td><td>用户提问 → 实时看到思考过程、工具调用、状态更新</td></tr><tr><td>一次请求返回一个 JSON</td><td>多个事件按顺序流式到达</td></tr><tr><td>出错只能整体重试</td><td>可以中途打断、修改、恢复</td></tr><tr><td>前端被动展示</td><td>前端与 Agent 协同工作</td></tr></tbody></table>

###  产品经理视角的理解

AG-UI 不解决"Agent 有多聪明"的问题，它解决的是"**Agent 的聪明如何被用户看见和使用**"的问题。

就像一个好的下属不仅要把结果交给你，还要在过程中同步进展、遇到困难及时请示、关键决策请求确认。AG-UI 就是让 Agent 具备这种"职场沟通能力"的协议。

##  二、为什么需要 AG-UI：从"等结果"到"看过程"

![](https://oss.fullcoding.cn/20260708/e2ed47d8-9ba9-4add-a7bc-a0116eee97cd_1783511288685.png)

在 AG-UI 之前，Agent 产品的前后端对接通常有三种方式，每种都有明显痛点。

###  2.1 三种传统对接方式及其问题

**方式一：传统 REST API**

前端发一个问题，后端返回一个答案。简单直接，但完全看不到中间过程。

问题：

-   Agent 执行了 10 秒，用户不知道它在忙什么
-   一旦出错，无法定位是哪一步错了
-   无法支持"中途需要用户补充信息"的复杂场景

**方式二：SSE 流式文本**

像 ChatGPT 一样，一个字一个字地吐答案。体验好了一些，但仍然只是把"最终回答"切成片段显示。

问题：

-   只能展示文本，无法展示"Agent 正在调用工具"
-   无法更新前端的状态（比如表格、图表、表单）
-   无法支持多轮人机协作

**方式三：各团队自己造轮子**

每个产品自定义一套事件格式、状态协议、中断机制。

问题：

-   前端和后端深度耦合，换模型或换 UI 框架成本极高
-   无法复用生态组件（一个 Agent 组件很难移植到另一个产品）
-   调试困难，出了问题全靠猜

###  2.2 AG-UI 解决的四个核心痛点

<table><thead><tr><th>痛点</th><th>传统方式的表现</th><th>AG-UI 的方案</th></tr></thead><tbody><tr><td><strong>过程不可见</strong></td><td>用户只能等待最终结果</td><td>事件流实时展示思考、工具调用、状态变化</td></tr><tr><td><strong>交互不自然</strong></td><td>一问一答，无法中途介入</td><td>支持中断、确认、修改、恢复等人机协作</td></tr><tr><td><strong>前后端绑定</strong></td><td>换前端或换后端都要重写</td><td>标准化协议，前后端可独立演进</td></tr><tr><td><strong>生态无法复用</strong></td><td>每个团队重复造轮子</td><td>一次接入，可对接多种 Agent 框架和 UI 组件</td></tr></tbody></table>

用一个比喻来说：**传统模式是打电话给客服，说完等结果；AG-UI 模式是客服坐在你对面，边想边说边操作，你还能随时插话**。

##  三、AG-UI 在 Agent 协议栈中的位置

如果你已经了解了 MCP 和 A2A，可以把 Agent 世界想象成一座办公楼：

<table><thead><tr><th>协议</th><th>解决的连接关系</th><th>办公楼类比</th></tr></thead><tbody><tr><td><strong>MCP</strong></td><td>Agent ↔ 工具/数据</td><td>员工的办公设备和资料库</td></tr><tr><td><strong>A2A</strong></td><td>Agent ↔ Agent</td><td>员工之间的跨部门协作</td></tr><tr><td><strong>AG-UI</strong></td><td>Agent ↔ 用户界面</td><td>员工向老板汇报工作的会议室</td></tr></tbody></table>

三者不是竞争关系，而是**互补关系**，共同构成完整的 Agent 生态。

###  3.1 一张图理解三者的协作

```
用户界面（Frontend）
    ↑↓ AG-UI：实时交互、状态同步、人机协作
Agent 运行时（Agent Runtime）
    ↑↓ A2A：多 Agent 分工协作
    ↑↓ MCP：调用工具、查询数据
外部系统 / 数据库 / API
```

###  3.2 实战中的组合场景

假设用户在企业的 CRM 系统中说："帮我跟进一下华东区最近 3 个丢单风险客户。"

一次完整的 AG-UI + MCP + A2A 协作可能是：

1.  **AG-UI**：前端把用户指令发给 Agent，Agent 通过事件流实时告诉前端"我正在分析客户数据"
2.  **MCP**：Agent 调用 CRM 数据库，查询客户近期互动记录、订单状态
3.  **A2A**：Agent 把"客户画像分析"任务委托给专门的"客户分析 Agent"
4.  **AG-UI**：分析结果以结构化卡片形式流式展示给用户，用户点击"生成挽回方案"
5.  **MCP**：Agent 调用邮件系统，生成并预览挽回邮件
6.  **AG-UI**：邮件内容展示给用户，用户修改后点击"发送"，Agent 执行

**产品经理关注点**：AG-UI 是你最容易直接感知和设计的协议，因为它直接决定了用户看到什么、能做什么。

##  四、核心概念：产品经理只需要理解五个词

你不需要会写 AG-UI 的事件格式，但需要理解五个核心概念，因为**它们会直接映射到你的产品设计里**。

###  4.1 Thread（会话线程）—— 一次完整的"工作流"

Thread 是用户和 Agent 之间一次持续的对话上下文。不是每条消息都重新开始，而是在同一个 Thread 里累积状态。

**产品设计启示**：

-   用户应该能回到之前的 Thread，继续未完成的任务
-   Thread 需要有标题、时间、状态等元信息，方便用户管理
-   长任务中断后，Thread 要保证状态不丢失

###  4.2 Event（事件）—— Agent 说的话

AG-UI 把 Agent 与前端的所有交互都封装成事件。每个事件都有类型、载荷和时间戳。

常见的标准事件类型：

<table><thead><tr><th>事件类型</th><th>含义</th><th>前端如何响应</th><th>产品场景</th></tr></thead><tbody><tr><td><code>TEXT_MESSAGE_CONTENT</code></td><td>Agent 输出的文本片段</td><td>追加到聊天窗口</td><td>流式回复</td></tr><tr><td><code>TOOL_CALL_START</code></td><td>Agent 开始调用工具</td><td>显示"正在查询数据库..."</td><td>工具调用反馈</td></tr><tr><td><code>TOOL_CALL_END</code></td><td>工具调用结束</td><td>展示工具返回结果</td><td>结果确认</td></tr><tr><td><code>STATE_DELTA</code></td><td>应用状态发生变化</td><td>更新表格/图表/表单</td><td>数据可视化</td></tr><tr><td><code>RUN_STARTED</code> / <code>RUN_FINISHED</code></td><td>任务开始/完成</td><td>控制加载态</td><td>流程状态</td></tr><tr><td><code>INTERRUPT</code></td><td>Agent 暂停，等待用户输入</td><td>弹出确认框/表单</td><td>人机协作</td></tr><tr><td><code>ERROR</code></td><td>执行出错</td><td>展示错误信息</td><td>异常处理</td></tr></tbody></table>

**产品经理关注点**：事件类型决定了前端能呈现什么样的交互。设计产品时，你要想清楚：哪些节点需要让用户看见？哪些需要让用户参与？

###  4.3 State（共享状态）—— 前后端共同的"记事本"

State 是前端和 Agent 共享的数据状态。Agent 可以修改 State，前端也可以修改 State，两者保持同步。

**产品设计启示**：

-   State 里放什么，直接影响产品的协作深度
-   比如代码编辑器场景：State 可以是当前文件内容、光标位置、选中代码
-   比如数据分析场景：State 可以是当前筛选条件、图表配置、分析结论

###  4.4 Interrupt（中断）—— Agent 也会"请示"

Interrupt 是 AG-UI 的杀手级能力之一。当 Agent 遇到需要用户确认、补充信息或做决策的场景时，可以主动暂停执行。

**三种常见的中断类型**：

<table><thead><tr><th>中断类型</th><th>说明</th><th>产品场景</th></tr></thead><tbody><tr><td><strong>确认型</strong></td><td>"我即将执行 XX 操作，你同意吗？"</td><td>发送邮件、扣款、删除数据</td></tr><tr><td><strong>补充型</strong></td><td>"我需要更多信息才能继续"</td><td>用户补充文件、填写表单</td></tr><tr><td><strong>选择型</strong></td><td>"有多个方案，你选哪个？"</td><td>选择报价、选择供应商</td></tr></tbody></table>

###  4.5 Generative UI（生成式 UI）—— Agent 不止会聊天

AG-UI 支持 Agent 向前端"提议"渲染什么 UI 组件。这意味着 Agent 不仅能输出文字，还能输出图表、表格、表单、按钮等交互元素。

**产品设计启示**：

-   不要让 Agent 只输出 Markdown 文本
-   设计一套"Agent 可以调用的 UI 组件库"（如数据卡片、趋势图、审批面板）
-   生成式 UI 要经过前端验证，避免 Agent"乱画界面"

##  五、AG-UI 的工作流程：一次完整的用户交互

假设用户在一个数据分析产品中输入："帮我分析一下 Q2 华东区的销售下滑原因。"

一次 AG-UI 驱动的完整交互可能是这样的：

![](https://oss.fullcoding.cn/20260708/f9aca6c4-bfba-43b3-841f-a620774e3b28_1783511519389.png)

```
步骤 1：用户输入
  前端通过 AG-UI 向后端 Agent 发送消息
  
步骤 2：Agent 开始思考
  → 发送 RUN_STARTED 事件
  → 发送 TEXT_MESSAGE_CONTENT："我来帮你分析 Q2 华东区销售情况..."
  
步骤 3：Agent 调用工具
  → 发送 TOOL_CALL_START："正在查询华东区 Q2 订单数据"
  → 通过 MCP 调用数据仓库
  → 发送 TOOL_CALL_END：返回数据摘要
  
步骤 4：Agent 更新前端状态
  → 发送 STATE_DELTA：更新销售趋势图表
  → 用户看到图表实时变化
  
步骤 5：Agent 发现异常
  → 发送 TEXT_MESSAGE_CONTENT："我发现 5 月份华东区新客户转化率下降了 18%"
  → 发送 STATE_DELTA：高亮显示异常月份
  
步骤 6：Agent 请求确认
  → 发送 INTERRUPT："是否需要我进一步分析客户流失原因？"
  → 用户点击"继续分析"
  
步骤 7：Agent 继续执行
  → 调用客户分析 Agent（A2A）
  → 发送 STATE_DELTA：更新客户流失归因图
  
步骤 8：任务完成
  → 发送 TEXT_MESSAGE_CONTENT："分析完成，核心结论..."
  → 发送 RUN_FINISHED
```

**产品经理关注点**：

-   哪些事件应该展示给用户，哪些应该静默处理？
-   事件之间的间隔多久算"卡顿"？需要设计骨架屏和进度提示
-   用户在中断时能否修改指令、补充信息、取消任务？

##  六、产品应用场景：AG-UI 能做什么产品？

###  6.1 AI 数据分析助手

**痛点**：传统 BI 工具一问一答，用户看不到分析过程，也不信任 AI 的结论。

**AG-UI 方案**：

-   实时展示 Agent 的查询步骤
-   图表随 State 更新实时变化
-   关键结论处弹出"查看推理过程"按钮
-   用户可以中断并修正分析维度

**产品价值**：从"黑盒分析师"升级为"透明分析伙伴"。

###  6.2 智能代码助手（Copilot 类）

**痛点**：代码补全是静态的，无法理解用户在项目中的实时上下文。

**AG-UI 方案**：

-   Agent 读取当前文件、光标位置、项目结构（State）
-   实时流式输出代码建议
-   多步骤重构任务中，每改一个文件就同步一次 State
-   危险操作（如删除文件）通过 INTERRUPT 请求确认

###  6.3 企业级工作流助手

**痛点**：企业内部流程复杂，Agent 执行过程中需要多次人工确认。

**AG-UI 方案**：

-   流程启动后，用户可以看到当前执行到哪一步
-   需要审批的节点自动弹出审批面板
-   用户可以在中断时补充附件、修改申请内容
-   全程可审计、可回放

###  6.4 智能客服（带操作能力）

**痛点**：传统客服机器人只会回答，无法帮用户真正办理业务。

**AG-UI 方案**：

-   Agent 一边与用户对话，一边调用后端系统
-   用户看到"正在查询订单"、"正在为您申请退款"等实时状态
-   关键操作（如退款、改地址）需要用户点击确认
-   复杂问题可以无缝转人工，Context 完整传递

###  6.5 AI 教育/培训助手

**痛点**：AI 辅导过程中，学生不知道 AI 为什么给出某个答案。

**AG-UI 方案**：

-   展示 AI 的解题步骤
-   学生可以在某一步提问、要求解释
-   通过生成式 UI 展示互动式题目、进度条、知识点卡片

<table><thead><tr><th>场景</th><th>核心挑战</th><th>AG-UI 的解决方式</th></tr></thead><tbody><tr><td>数据分析</td><td>过程不透明、结论难信任</td><td>实时事件流 + 可视化状态同步</td></tr><tr><td>代码助手</td><td>上下文复杂、操作风险高</td><td>State 共享 + 中断确认</td></tr><tr><td>企业工作流</td><td>多节点、需审批</td><td>中断机制 + 流程可视化</td></tr><tr><td>智能客服</td><td>只能问答、不能办理</td><td>工具调用可视化 + 关键操作确认</td></tr><tr><td>教育辅导</td><td>黑盒输出、无法互动</td><td>分步展示 + 生成式 UI</td></tr></tbody></table>

##  七、实战案例：设计一个"智能销售助手"

接下来，我们用一个完整案例，演示如何用 AG-UI 设计一个面向销售团队的 AI 产品。

###  7.1 业务背景

某 B2B 公司销售团队每天需要处理大量客户信息、跟进线索、准备拜访材料。现有痛点：

-   销售每天要切换 CRM、邮件、文档、日历 4-5 个系统
-   准备一次客户拜访需要 30-60 分钟
-   销售新人不知道如何根据客户画像组织话术

###  7.2 产品目标

-   把客户拜访准备时间从 45 分钟缩短到 5 分钟
-   提升新人销售的首次拜访成功率
-   让销售过程数据沉淀到 CRM

###  7.3 产品架构

```
销售助手界面（React）
    ↑↓ AG-UI
Agent 运行时（LangGraph）
    ↑↓ MCP      → CRM、邮件、日历、文档系统
    ↑↓ A2A      → 客户画像 Agent、话术生成 Agent
```

###  7.4 一次完整的用户旅程

**用户（销售）输入**："帮我准备明天下午 3 点去拜访 ABC 公司张总的材料。"

**Step 1：任务启动**

-   前端发送消息，Agent 返回 `RUN_STARTED`
-   Agent 输出："好的，我来帮你准备这次拜访。"

**Step 2：查询客户信息**

-   `TOOL_CALL_START`："正在查询 ABC 公司资料"
-   通过 MCP 调用 CRM，获取客户基本信息、历史订单、最近互动
-   `TOOL_CALL_END`：返回客户资料摘要
-   `STATE_DELTA`：前端客户卡片更新

**Step 3：分析决策者**

-   `TOOL_CALL_START`："正在分析张总背景"
-   通过 A2A 调用"客户画像 Agent"
-   `STATE_DELTA`：决策者画像卡片出现

**Step 4：生成拜访议程**

-   Agent 输出："基于张总的关注点，我建议本次拜访重点讨论："
-   `STATE_DELTA`：议程列表出现在界面右侧

**Step 5：请求用户确认/补充**

-   `INTERRUPT`："是否需要我生成对应的 PPT 介绍材料？"
-   用户选择"需要，重点突出我们的成本优势"

**Step 6：生成材料**

-   `TOOL_CALL_START`："正在生成拜访 PPT"
-   通过 MCP 调用文档系统
-   `STATE_DELTA`：PPT 预览卡片出现
-   `TOOL_CALL_END`：生成完成

**Step 7：写入日历并发送通知**

-   `TOOL_CALL_START`："正在同步到日历"
-   通过 MCP 调用日历系统
-   `TOOL_CALL_END`：确认同步

**Step 8：任务完成**

-   Agent 输出总结："拜访准备完成。已生成 PPT、同步日历，建议提前 15 分钟出发。"
-   `RUN_FINISHED`

###  7.5 关键产品设计决策

##  八、产品经理设计 AG-UI 产品时的关键清单

###  8.1 事件可见性设计

不是每个事件都需要展示给用户。建议分层：

<table><thead><tr><th>层级</th><th>展示方式</th><th>示例</th></tr></thead><tbody><tr><td><strong>用户可见层</strong></td><td>直接展示在对话区或状态区</td><td>Agent 正在查询数据、已生成结论</td></tr><tr><td><strong>轻提示层</strong></td><td>进度条、骨架屏、小气泡</td><td>工具调用中、状态同步中</td></tr><tr><td><strong>调试层</strong></td><td>仅开发者/管理员可见</td><td>完整事件流、Token 消耗</td></tr></tbody></table>

###  8.2 中断体验设计

中断是 AG-UI 最具产品价值的特性之一，但设计不好会很打断用户。

**设计原则**：

-   **最小打断**：只在真正需要时中断
-   **上下文清晰**：中断时告诉用户为什么停、需要什么
-   **操作明确**：提供清晰的选项（确认/取消/修改）
-   **状态保留**：中断期间不丢失已完成的进度

###  8.3 错误与异常处理

<table><thead><tr><th>异常类型</th><th>产品方案</th></tr></thead><tbody><tr><td>工具调用失败</td><td>展示失败原因，提供重试或跳过选项</td></tr><tr><td>Agent 输出异常</td><td>展示原始输出，允许用户手动纠正</td></tr><tr><td>网络中断</td><td>自动恢复 Thread，从断点继续</td></tr><tr><td>用户长时间无响应</td><td>保存草稿，发送提醒通知</td></tr></tbody></table>

###  8.4 性能与体验平衡

-   **首屏响应**：用户发送消息后，300ms 内要有反馈
-   **流式体验**：文本输出建议按 Token 流式展示
-   **工具调用反馈**：超过 2 秒的工具调用需要有进度提示
-   **状态更新**：避免界面频繁抖动，合并短时间内的多次 STATE\_DELTA

##  十、AG-UI 的局限与挑战

AG-UI 很强大，但作为产品经理，你需要清醒认识这些限制。

###  10.1 生态仍在早期

虽然 AG-UI 已经获得 LangGraph、CrewAI、Microsoft Agent Framework、Google ADK 等主流框架支持，但相比 REST API 仍属新兴协议。

**建议**：

-   优先选择已有 AG-UI SDK 或中间件的技术栈
-   在架构中保留适配层，便于未来协议升级

###  10.2 事件设计需要产品深度参与

AG-UI 给了你很灵活的事件定义能力，但这也意味着**事件设计的好坏直接决定产品体验**。

**建议**：

-   产品经理要和工程师一起定义事件类型和 State 结构
-   不要把所有内部细节都暴露给用户
-   为每个事件设计清晰的前端响应策略

###  10.3 生成式 UI 的边界

Agent 生成 UI 很酷，但也存在风险：

-   Agent 可能提议不合适的组件
-   界面风格可能不一致
-   安全风险（Agent 生成恶意按钮？）

**建议**：

-   使用"UI 组件白名单"机制
-   前端对 Agent 提议的 UI 进行验证和渲染控制
-   敏感操作必须通过 INTERRUPT 请求确认

###  10.4 调试复杂度提升

事件流让系统更灵活，但也更难调试。一个用户问题可能触发几十个事件，定位问题需要专业工具。

**建议**：

-   建立事件流日志和回放能力
-   设计"开发者模式"查看完整事件链
-   使用 LangSmith 等可观测性工具追踪

<table><thead><tr><th>挑战</th><th>影响程度</th><th>应对策略</th></tr></thead><tbody><tr><td>生态早期</td><td>中</td><td>选有 SDK 支持的框架，预留适配层</td></tr><tr><td>事件设计复杂</td><td>高</td><td>产品与工程协同定义，避免过度暴露</td></tr><tr><td>生成式 UI 风险</td><td>中</td><td>组件白名单 + 前端验证 + 确认机制</td></tr><tr><td>调试难度</td><td>中高</td><td>事件日志 + 回放 + 可观测性工具</td></tr><tr><td>性能开销</td><td>中</td><td>合并事件、缓存状态、控制流频率</td></tr></tbody></table>

##  十二、总结

AG-UI 代表了 AI 产品交互的一个重要趋势：**从"用户等待结果"到"用户与 Agent 共同工作"**。

对于 AI 产品经理来说，这意味着：

1.  **你可以设计出更有信任感的产品**——用户不再面对黑盒，而是看到 Agent 每一步的思考
2.  **你可以设计出更有协作感的产品**——Agent 不再是单向输出工具，而是会请示、会确认、会接受的伙伴
3.  **你可以设计出更有扩展性的产品**——一次基于 AG-UI 的架构投入，可以对接多个 Agent 框架和 UI 组件

当然，AG-UI 不是银弹。它的价值在"复杂、多步骤、需要人机协作的 Agent 产品"中才能充分发挥。如果你的产品只是简单问答，不必强求。但当你的 AI 产品开始涉及"理解 → 调用工具 → 更新界面 → 请求确认 → 继续执行"的复杂舞蹈时，AG-UI 就是那根让前后端、人与 Agent 紧密配合的指挥棒。

**记住一个原则**：好的 AI 产品不是让用户觉得"AI 很神秘"，而是让用户觉得"AI 很可靠"。AG-UI 的核心价值，正是把 Agent 的神秘过程变成用户可以看见、理解和掌控的透明体验。
