前言

欢迎来到第5章的最后一节。前面我们聊了需求挖掘、竞品分析、需求评估、PRD写作、风险边界——这些都是"做什么"和"为什么做"的问题。而这一节，我们要解决"怎么做"的底层架构问题：**AI产品的结构如何设计？**

很多AI产品经理有一个误区：认为架构设计是技术团队的事，自己不需要关心。但事实是，**如果你不懂AI产品的架构，你根本无法做出合理的功能规划、无法评估开发周期、无法与工程师高效沟通，更无法在项目中做出正确的技术选型决策。**

你不需要会画架构图（虽然学会更好），但你需要理解：一个AI产品从用户点击到模型返回结果，中间经过了哪些模块？每个模块的职责是什么？模块之间如何协作？数据如何流转？

本文将从产品经理的视角，用尽量通俗的语言，把AI产品的架构彻底讲清楚。读完这一节，你将拥有一张完整的"AI产品架构地图"。
:::

##  二、应用层设计：用户的第一触点

###  （一）应用层的核心职责

应用层是用户直接接触的产品形态，负责：

-   **多端接入**：Web、App、小程序、浏览器插件、企业微信/钉钉机器人
-   **交互设计**：输入框、按钮、语音入口、文件上传区域
-   **AI状态反馈**：让用户知道"AI正在思考""AI正在生成""AI遇到了问题"
-   **结果呈现**：如何把AI生成的内容展示得清晰、可信、可交互

###  （二）AI产品特有的交互设计

AI产品的应用层，和传统产品最大的区别在于\*\*"不确定性"的呈现\*\*。

####  1. AI状态提示

传统产品的状态是确定的：点击按钮 → 加载中 → 成功/失败。AI产品的状态更复杂：

<table><thead><tr><th style="text-align:left;">状态</th><th style="text-align:left;">用户心理</th><th style="text-align:left;">设计要点</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>思考中</strong></td><td style="text-align:left;">"AI在干活吗？卡住了吗？"</td><td style="text-align:left;">展示思考过程（如Claude的thinking动画）、预计等待时间</td></tr><tr><td style="text-align:left;"><strong>生成中</strong></td><td style="text-align:left;">"内容对吗？我要不要打断？"</td><td style="text-align:left;">流式输出（逐字显示）、支持随时停止生成</td></tr><tr><td style="text-align:left;"><strong>置信度低</strong></td><td style="text-align:left;">"这个答案靠谱吗？"</td><td style="text-align:left;">显示置信度分数、标注"AI生成，仅供参考"、提供信息来源</td></tr><tr><td style="text-align:left;"><strong>需要确认</strong></td><td style="text-align:left;">"AI理解对了吗？"</td><td style="text-align:left;">在行动前展示AI的理解摘要，让用户确认</td></tr><tr><td style="text-align:left;"><strong>遇到限制</strong></td><td style="text-align:left;">"为什么不能回答？"</td><td style="text-align:left;">清晰说明限制原因（如"涉及个人隐私，无法回答"）</td></tr></tbody></table>

####  2. 人机协同入口

好的AI产品不会"替用户做决定"，而是"帮用户更好地做决定"。应用层需要设计明确的人机协同入口：

-   **反馈按钮**：👍/👎，让用户标记AI回答的好坏
-   **修改建议**：AI给出初稿，用户可以直接在界面上编辑
-   **人工接管**：当AI置信度低于阈值时，一键转人工
-   **多方案对比**：AI给出3个不同风格的答案，用户选择或组合

####  3. 多模态输入输出

现代AI产品越来越强调多模态：

```
输入侧：
├── 文本输入（最基础）
├── 语音输入（语音识别→文本→模型）
├── 图片输入（OCR/图像理解→模型）
├── 文件输入（PDF/Word/Excel解析→文本→模型）
└── 视频输入（抽帧/音频提取→模型）

输出侧：
├── 文本输出（最基础）
├── 富文本输出（Markdown、表格、代码块）
├── 语音输出（TTS文本转语音）
├── 图片输出（文生图、数据可视化图表）
└── 结构化输出（JSON、XML，供下游系统使用）
```

##  三、服务层设计：产品的"中枢神经系统"

服务层是应用层和模型层之间的"桥梁"，负责处理所有业务逻辑。如果把模型层比作"大脑"，服务层就是"小脑"——协调各部件的动作，确保整体运转流畅。

###  （一）服务层的核心模块

![](https://oss.fullcoding.cn/20260526/12a5c491-4552-42ca-8a14-b9d24a327d3d_1779784126810.png)

####  1. API网关（API Gateway）

**职责**：所有外部请求的入口，负责统一接收、校验、路由。

**关键功能**：

-   **请求校验**：检查参数是否合法、用户是否有权限
-   **限流熔断**：防止流量突增压垮系统（如每秒最多1000次调用）
-   **路由分发**：根据请求类型，转发到不同的服务模块
-   **协议转换**：把HTTP/REST请求转换为内部服务的调用格式

**AI产品的特殊考量**：

-   模型调用通常耗时较长（几秒到几十秒），API网关需要支持**长连接**或**异步回调**
-   需要区分"普通请求"和"模型请求"，对模型请求设置更宽松的超时时间

####  2. 认证与授权（Auth）

**职责**：确认"你是谁"（认证）和"你能做什么"（授权）。

**AI产品的特殊考量**：

-   **模型级别的权限控制**：不同用户等级调用不同模型（免费用户→轻量模型，付费用户→旗舰模型）
-   **功能级别的权限控制**：某些高级功能（如代码生成、数据分析）仅对特定用户开放
-   **内容安全审核**：在认证层就拦截高风险用户或IP

####  3. 会话管理（Session Management）

**职责**：管理用户与AI的多轮对话状态。

**关键设计**：

```
会话数据结构示例：
{
  "session_id": "sess_abc123",
  "user_id": "user_456",
  "created_at": "2026-05-26T10:00:00Z",
  "messages": [
    {"role": "user", "content": "帮我写一封邮件", "timestamp": "..."},
    {"role": "assistant", "content": "好的，请告诉我收件人和主题", "timestamp": "..."},
    {"role": "user", "content": "发给张三，主题是项目延期", "timestamp": "..."}
  ],
  "context_summary": "用户需要写一封项目延期通知邮件，收件人张三",
  "metadata": {
    "total_tokens": 2450,
    "model_used": "gpt-4o",
    "preference": {"tone": "formal"}
  }
}
```

**会话管理的挑战**：

-   **上下文长度限制**：当对话历史超过模型上下文窗口时，需要摘要压缩或丢弃早期内容
-   **跨设备同步**：用户在手机上聊了一半，切换到Web端需要无缝接续
-   **会话持久化**：断电/断网后，对话历史不能丢失

####  4. 上下文组装（Context Assembly）

这是AI产品服务层最特殊的模块，也是Context Engineering的工程化落地。

**职责**：把各种信息源组装成模型能理解的上下文。

**组装流程**：

```
用户输入: "昨天说的那个方案怎么样了？"

【步骤1：理解用户意图】
→ 识别实体："昨天"、"方案"
→ 意图分类：查询状态

【步骤2：检索相关信息】
→ 从对话历史中找到"昨天"的讨论内容
→ 从知识库中检索"方案"的定义和背景
→ 从项目管理系统中获取方案的最新状态

【步骤3：组装上下文】
系统Prompt（角色设定 + 约束条件）
+ 对话历史摘要（保留关键信息，压缩冗余）
+ 检索到的知识片段（Top 3 最相关）
+ 实时数据（项目管理系统中的最新状态）
+ 用户当前问题
─────────────────────────────
= 最终发送给模型的上下文

【步骤4：后处理】
→ 模型返回结果
→ 过滤敏感内容
→ 格式化输出
→ 记录到会话历史
```

####  5. 结果后处理（Post-processing）

**职责**：对模型输出进行加工，确保符合产品要求。

**常见处理**：

-   **内容审核**：调用内容安全API，过滤违规内容
-   **格式转换**：把模型输出的Markdown转为HTML，或把JSON格式化
-   **引用标注**：给模型输出中的事实性陈述添加来源链接
-   **置信度标注**：如果模型输出置信度低，附加提示"此内容可能不准确"

####  6. 计费系统（Billing）

**职责**：精确记录每个用户的Token消耗，支撑商业化。

**计费维度**：

##  四、模型层设计：产品的"智能大脑"

模型层是AI产品最核心的差异化来源。同样的前端界面，用不同的模型，用户体验可能天差地别。

###  （一）模型层的核心职责

```
模型层 = 模型接入 + Prompt管理 + 模型路由 + 效果评测 + 持续优化

####  2. 多模型策略

很少有AI产品只依赖单一模型。成熟的产品通常采用\*\*"大模型+小模型"\*\*的分层策略：

```
用户请求
    ↓
【第一层：意图识别模型】（小模型，快速、便宜）
    → 分类：问答 / 生成 / 分析 / 其他
    ↓
【第二层：专用模型路由】
    ├── 问答类 → 知识问答模型（RAG增强）
    ├── 生成类 → 创意写作模型
    ├── 分析类 → 数据分析模型（Code Interpreter）
    └── 其他 → 通用大模型（兜底）
    ↓
【第三层：结果质检模型】（小模型，快速）
    → 检查输出是否合规、格式是否正确
    ↓
返回给用户
```

**多模型策略的优势**：

-   **成本优化**：70%的简单请求用小模型处理，成本降低80%
-   **效果优化**：每个任务都用最适合的模型，整体效果更好
-   **风险分散**：某个模型出问题时，可以自动切换到备用模型

###  （三）Prompt管理工程

Prompt是模型层的"配置项"，需要像管理代码一样管理Prompt。

####  1. Prompt版本管理

```
prompts/
├── v1.0/
│   ├── system_prompt.txt      # 系统Prompt
│   ├── qa_prompt.txt          # 问答场景Prompt
│   └── summary_prompt.txt     # 摘要场景Prompt
├── v1.1/
│   ├── system_prompt.txt      # 优化了角色设定
│   ├── qa_prompt.txt          # 增加了拒答策略
│   └── summary_prompt.txt
└── config.yaml                # 当前生效版本配置
```

##  五、数据层设计：产品的"记忆和知识库"

###  （一）数据层的核心组成

```
数据层
├── 向量数据库（Vector DB）      ← AI产品特有
├── 关系数据库（SQL DB）          ← 用户信息、订单、配置
├── 对象存储（Object Storage）    ← 文件、图片、音视频
├── 缓存（Cache）                 ← 热点数据加速
├── 消息队列（Message Queue）     ← 异步任务解耦
└── 数据管道（Data Pipeline）     ← 数据采集、清洗、标注
```

###  （二）向量数据库：RAG的基石

向量数据库是AI产品（尤其是RAG类应用）最核心的数据基础设施。

####  1. 向量数据库的工作原理

```
1. 文档入库流程：
   原始文档 → 文本分块（Chunking）→ Embedding模型 → 向量 → 存入向量数据库

2. 查询流程：
   用户问题 → Embedding模型 → 向量 → 向量数据库相似度检索 → Top K相关文档
```

###  （三）数据管道：从原始数据到可用知识

```
原始数据源
    ├── 产品文档（Word/PDF/Markdown）
    ├── 客服对话记录
    ├── 用户反馈（工单、评论）
    ├── 外部知识（网页、论文）
    └── 结构化数据（数据库、Excel）
            ↓
    【数据采集】定时抓取/API同步/人工上传
            ↓
    【数据清洗】去重/去噪/格式统一/敏感信息脱敏
            ↓
    【数据分块】按策略切分为合适大小的Chunk
            ↓
    【数据标注】（可选）人工标注质量、相关性
            ↓
    【向量化】Embedding模型转换为向量
            ↓
    【入库】存入向量数据库 + 关系数据库（元数据）
            ↓
    【索引更新】增量更新或全量重建
```

###  （四）数据回流与飞轮

AI产品最大的护城河不是模型，而是**数据飞轮**：

```
用户使用产品
    → 产生新的交互数据（提问、反馈、修改）
    → 数据回流到数据层
    → 用于优化模型（微调、Prompt优化）
    → 用于优化检索（更好的Embedding、更好的分块）
    → 产品体验提升
    → 更多用户使用
    → （循环）
```

**AI PM 的关键职责**：设计数据回流的机制和闭环。比如：

-   用户点了"👎"，这条记录是否进入了Badcase库？
-   用户手动修改了AI生成的内容，修改前后的差异是否被记录？
-   哪些数据可以自动回流？哪些需要人工审核后才能回流？

###  （一）算力资源管理

AI产品的算力需求有两种模式：

<table><thead><tr><th style="text-align:left;">模式</th><th style="text-align:left;">说明</th><th style="text-align:left;">适用场景</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>API调用模式</strong></td><td style="text-align:left;">调用第三方模型API（OpenAI、Anthropic等），按量付费</td><td style="text-align:left;">大多数AI应用产品</td></tr><tr><td style="text-align:left;"><strong>自托管模式</strong></td><td style="text-align:left;">自己部署开源模型，需要GPU服务器</td><td style="text-align:left;">数据敏感、调用量极大、需要定制化</td></tr></tbody></table>

**自托管的算力规划**：

```
GPU需求估算：
- 模型参数量：70B参数的模型，推理需要约 2-4 张 A100/H100
- 并发请求：每增加100并发，约需增加 1-2 张 GPU
- 模型数量：如果同时运行3个不同模型，GPU数量 ×3

示例：一个日活10万的AI产品，自托管70B模型
- 推理GPU：8 × A100（应对峰值并发）
- Embedding GPU：2 × A100（文档向量化）
- 微调GPU：4 × A100（定期模型微调）
- 总计：约 14 张 A100，年成本约 ¥300-500万
```

AI产品发布：

```

**模型版本管理**：

-   每个模型版本需要有唯一标识（如 `gpt-4o-2026-05-25`）
-   支持快速回滚到上一个稳定版本
-   模型配置（Prompt、温度参数、Top-p）与代码分离，支持热更新
