::: tip 核心考点
前言

在上一节《智能体（Agent）》中，我们知道了 Agent 是能思考也能行动的 AI。但 Agent 的"行动"不是凭空产生的——它依靠一个个具体的 **Skill（技能）** 来完成任务。

查天气是一个 Skill，发邮件是一个 Skill，查数据库是一个 Skill，写 Python 代码也是一个 Skill。Skill 是 Agent 与真实世界交互的"桥梁"，是 Agent 从"空想家"变成"实干家"的关键。

本文将深入讲解 Skill 的核心原理、分类体系、设计方法，以及作为 AI PM，如何设计和评估 Skill 体系。

##  一、什么是 Skill？Agent 的"工具箱"

###  （一）一个形象的类比：装修公司的项目经理

想象你请了一个装修公司的项目经理（Agent）来帮你装修房子。

**没有 Skill 的项目经理**：

> 你问他："能帮我装个吊灯吗？" 他说："吊灯一般需要固定在天花板的承重结构上，需要注意电线的走向……"——说得头头是道，但就是不干活。
> 
> 你问他："能帮我刷墙吗？" 他说："刷墙需要先打磨、再底漆、再面漆，选择环保材料很重要……"——还是只动口不动手。

**有 Skill 的项目经理**：

> 你跟他说："帮我装个吊灯。" 他立刻拿出电话（调用 Skill）："电工师傅，来 3 号楼 502，装一个吊灯。" 电工来了，干活，装好。
> 
> 你跟他说："把卧室刷成浅蓝色。" 他立刻拿出电话（调用 Skill）："油漆工，带浅蓝色环保漆来 502。" 油漆工来了，打磨、底漆、面漆，完工。

**Skill 就是这个项目经理手里的"通讯录"和"工作清单"**——每个 Skill 对应一个具体的工种，项目经理知道什么时候该叫谁来做什么。

###  （二）Skill 的技术定义

Skill 是 Agent 可以调用的**原子化能力单元**，它封装了一个具体的操作或功能。每个 Skill 通常包含：

```
Skill = 功能描述 + 输入参数定义 + 执行逻辑 + 输出格式
```

**举例："查询天气" Skill**

<table><thead><tr><th style="text-align:left;">组成部分</th><th style="text-align:left;">内容</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>功能描述</strong></td><td style="text-align:left;">查询指定城市和日期的天气信息</td></tr><tr><td style="text-align:left;"><strong>输入参数</strong></td><td style="text-align:left;">city（城市名，字符串）、date（日期，字符串）</td></tr><tr><td style="text-align:left;"><strong>执行逻辑</strong></td><td style="text-align:left;">调用天气 API，获取实时天气数据</td></tr><tr><td style="text-align:left;"><strong>输出格式</strong></td><td style="text-align:left;">JSON：{ weather, temperature, humidity, wind }</td></tr></tbody></table>

**Skill 和 Function Calling 的关系**：

> Skill 是 Function Calling 的**产品化封装**。
> 
> -   Function Calling 是底层机制——模型输出函数调用请求
> -   Skill 是上层抽象——把一组相关的函数、API、逻辑封装成一个"能力模块"
> 
> 类比：Function Calling 是"打电话"这个动作，Skill 是"通讯录里的一个联系人"。

![](https://oss.fullcoding.cn/20260525/b6066c1a-0efb-4c02-9b56-8a396b79ff6a_1779698116295.png)

###  （二）意图识别：Agent 怎么知道该调用哪个 Skill？

**方法一：基于规则的关键词匹配**

```
如果用户输入包含"天气""气温""下雨" → 调用"查询天气"Skill
如果用户输入包含"邮件""发信""E-mail" → 调用"发送邮件"Skill
```

> 优点：简单、快速、可控 缺点：无法处理复杂表达、同义词、多意图

**方法二：基于大模型的意图理解**

```
System Prompt：
你是一个智能助手，可以调用以下 Skill：
1. get_weather：查询天气
2. send_email：发送邮件
3. query_database：查询数据库

请判断用户意图，输出需要调用的 Skill 名称和参数。

用户输入：明天出门需要带伞不？

模型输出：
{
  "skill": "get_weather",
  "parameters": { "city": "当前城市", "date": "明天" }
}
```

> 优点：理解能力强，能处理复杂表达 缺点：需要模型支持 Function Calling，有一定延迟

**方法三：混合策略（推荐）**

```
快速规则匹配 → 命中则直接调用
    ↓ 未命中
大模型意图理解 → 判断 Skill
    ↓ 不确定
追问用户澄清意图
```

###  （三）参数提取：从"自然语言"到"结构化数据"

用户的表达是自然语言，但 Skill 需要结构化参数。参数提取就是做这个转换。

**示例**：

```
用户："帮我查一下下周三上海的天气，我要出差。"

需要提取的参数：
- city: "上海"
- date: "下周三" → 需要解析为具体日期（如 2024-06-12）

挑战：
- "下周三"是相对的，需要结合当前日期计算
- "出差"是背景信息，不是参数，需要过滤掉
- 用户没说"查询天气"四个字，但需要理解意图
```

##  五、如何设计一个好的 Skill？

###  （一）Skill 设计的五大原则

<table><thead><tr><th style="text-align:left;">原则</th><th style="text-align:left;">说明</th><th style="text-align:left;">反例</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>单一职责</strong></td><td style="text-align:left;">一个 Skill 只做一件事</td><td style="text-align:left;">"查询天气并发送邮件"——应该拆成两个 Skill</td></tr><tr><td style="text-align:left;"><strong>参数明确</strong></td><td style="text-align:left;">输入参数清晰、必填/选填明确</td><td style="text-align:left;">参数叫"data"——不知道要传什么</td></tr><tr><td style="text-align:left;"><strong>描述精准</strong></td><td style="text-align:left;">Skill 和参数的描述要准确</td><td style="text-align:left;">描述写"查询信息"——太模糊</td></tr><tr><td style="text-align:left;"><strong>输出稳定</strong></td><td style="text-align:left;">返回格式统一、可预期</td><td style="text-align:left;">有时候返回 JSON，有时候返回纯文本</td></tr><tr><td style="text-align:left;"><strong>容错健壮</strong></td><td style="text-align:left;">参数错误时给出清晰报错</td><td style="text-align:left;">API 挂了，返回"未知错误"</td></tr></tbody></table>

###  （二）Skill 描述（Description）的艺术

**Skill 的描述决定了大模型能不能"正确理解"什么时候该调用这个 Skill。**

**差的描述**：

```
"name": "query",
"description": "查询数据"
```

> 问题：太模糊。"查询数据"是什么意思？查什么数据？什么场景下用？

**好的描述**：

```
"name": "query_sales_data",
"description": "查询销售数据。当用户询问销售额、订单量、销售业绩、同比环比等数据时使用。支持按时间范围（日/周/月/年）、地区、产品品类筛选。"
```

> 优点：明确说明了使用场景（什么时候调用）、支持的功能（能查什么）、筛选条件（参数能力）。

###  （三）参数设计最佳实践

**示例：设计一个"预订会议室" Skill**

```
{
  "name": "book_meeting_room",
  "description": "预订会议室。当用户需要预定会议室、开会的场地时使用。",
  "parameters": {
    "type": "object",
    "properties": {
      "date": {
        "type": "string",
        "description": "会议日期，格式：YYYY-MM-DD，如 2024-06-15"
      },
      "start_time": {
        "type": "string",
        "description": "开始时间，格式：HH:MM，如 14:00"
      },
      "duration_minutes": {
        "type": "integer",
        "description": "会议时长（分钟），如 60"
      },
      "capacity": {
        "type": "integer",
        "description": "参会人数，用于筛选足够大的会议室",
        "default": 4
      },
      "room_name": {
        "type": "string",
        "description": "指定会议室名称（可选），如不提供则自动推荐",
        "default": null
      }
    },
    "required": ["date", "start_time", "duration_minutes"]
  }
}
```

**设计要点**：

<table><thead><tr><th style="text-align:left;">要点</th><th style="text-align:left;">说明</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>参数命名清晰</strong></td><td style="text-align:left;"><code>duration_minutes</code> 比 <code>duration</code> 更明确</td></tr><tr><td style="text-align:left;"><strong>描述包含格式</strong></td><td style="text-align:left;"><code>"格式：YYYY-MM-DD"</code>——减少模型理解错误</td></tr><tr><td style="text-align:left;"><strong>默认值</strong></td><td style="text-align:left;">非必填参数提供默认值，减少用户输入负担</td></tr><tr><td style="text-align:left;"><strong>必填/选填明确</strong></td><td style="text-align:left;"><code>required</code> 数组清晰标注</td></tr><tr><td style="text-align:left;"><strong>枚举值</strong></td><td style="text-align:left;">如果参数值有限，用 <code>enum</code> 限定</td></tr></tbody></table>

###  （四）Skill 的错误处理设计

**好的 Skill 应该返回结构化的错误信息**：

```
// 成功返回
{
  "success": true,
  "data": { "weather": "小雨", "temperature": "15-20℃" }
}

// 错误返回
{
  "success": false,
  "error_code": "CITY_NOT_FOUND",
  "error_message": "未找到城市 '北鲸'，您是否想查询 '北京'？",
  "suggestions": ["北京", "北极"]
}
```

**错误处理的好处**：

-   Agent 可以根据 `error_code` 决定下一步（重试？追问用户？换 Skill？）
-   `suggestions` 可以帮助用户纠正输入
-   `error_message` 可以直接展示给用户

##  六、Skill 的组合与编排

###  （一）串行编排：一步接一步

```
用户："帮我订明天下午去北京的高铁，然后查一下北京下周的天气"

Agent 执行：
Step 1：调用"查询高铁"Skill → 获取车次列表
Step 2：展示给用户，用户选择 G123
Step 3：调用"预订高铁"Skill → 完成预订
Step 4：调用"查询天气"Skill（city=北京, date=下周）→ 获取天气预报
Step 5：生成总结回答
```

###  （二）并行编排：同时执行多个 Skill

```
用户："帮我查一下北京和上海的天气"

Agent 执行：
并行调用：
  ├── 查询天气（city=北京）
  └── 查询天气（city=上海）

等待两个都返回后，合并生成回答。
```

###  （三）条件编排：根据结果选择路径

```
用户："帮我查一下账户余额，如果超过 1 万就转 5000 到储蓄卡"

Agent 执行：
Step 1：调用"查询余额"Skill
    ↓
判断：余额 > 10000？
    ├─ 是 → 调用"转账"Skill（金额=5000）
    └─ 否 → 回复"余额不足，当前余额 XXX"
```

###  （四）循环编排：重复执行直到满足条件

```
用户："帮我找一家明天晚上有位的西餐厅，人均 300 左右"

Agent 执行：
循环：
  1. 调用"搜索餐厅"Skill（条件：西餐、明天晚上、人均 300）
  2. 检查是否有空位
  3. 如果有 → 返回结果，结束
  4. 如果无 → 放宽条件（人均范围扩大），重新搜索
  5. 最多尝试 3 次
```

##  七、AI PM 视角：Skill 体系的产品设计

###  （一）Skill 体系的规划流程

```
Step 1：用户场景分析
    └── 用户在这个 Agent 里会做什么？
    └── 示例：企业客服 Agent → 查订单、查物流、申请退换货、咨询产品

Step 2：Skill 拆分
    └── 每个场景对应一个或多个 Skill
    └── 示例：查订单 → "query_order" Skill；申请退换货 → "create_return" Skill

Step 3：优先级排序
    ├── P0：核心高频 Skill（必须做）
    ├── P1：重要但低频 Skill（尽快做）
    └── P2：锦上添花 Skill（有余力再做）

Step 4：接口设计
    └── 定义每个 Skill 的参数、返回值、错误码

Step 5：安全评审
    └── 每个 Skill 的风险等级？是否需要人工确认？

Step 6：效果验证
    └── Skill 的准确率？召回率？用户体验？
```

##  九、小结

###  核心要点

1.  **Skill 是 Agent 的"能力积木"**：每个 Skill 封装一个具体的功能，Agent 通过调用 Skill 来完成任务。
    
2.  **Skill = 功能描述 + 输入参数 + 执行逻辑 + 输出格式**：四要素缺一不可。
    
3.  **Skill 描述决定模型能否正确调用**：描述要精准、包含使用场景、参数格式要清晰。
    
4.  **权限分级是安全底线**：只读 Skill 自动执行，敏感操作必须人工确认。
    
5.  **Skill 设计遵循单一职责原则**：一个 Skill 只做一件事，复杂的用编排组合。
    
6.  **Skill 数量要适度**：MVP 阶段 5-10 个，成熟阶段 15-30 个，太多会导致模型选错。
    
7.  **Skill 是产品差异化的关键**：同样的底层模型，Skill 体系的设计决定了 Agent 的能力边界和用户体验。
    

###  给 AI PM 的一句话

> **如果说大模型是 Agent 的"大脑"，那么 Skill 就是 Agent 的"手脚"。大脑再聪明，没有手脚也只能空想；手脚再灵活，没有大脑指挥也只能乱动。作为 PM，你的核心任务是设计一套"恰到好处"的 Skill 体系——覆盖用户的核心需求、描述清晰让模型能理解、权限可控让用户放心、数量适中让维护可持续。Skill 设计得好，Agent 产品就成功了一半。**
