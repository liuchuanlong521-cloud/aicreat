::: tip 核心考点
前言

大模型有两个致命弱点：**幻觉**（编造不存在的信息）和**知识截止**（不知道训练之后发生的事）。

RAG（Retrieval-Augmented Generation，检索增强生成）就是为解决这两个问题而生的。它让大模型在回答问题之前，先去查资料——就像学生考试前翻课本一样，有了参考资料，答案自然就准了。

RAG 是当前大模型产品落地的**首选技术方案**。据行业统计，超过 80% 的企业级大模型应用都采用了某种形式的 RAG。

本文将从原理到实践，从基础架构到高级优化，系统讲解 RAG 的方方面面。
:::

##  一、为什么需要 RAG？大模型的两个致命弱点

###  （一）幻觉：一本正经地胡说八道

大模型为了"生成流畅的文本"，有时会编造看似合理但实际错误的内容。

**案例**：

> 用户："请介绍一下张三教授的研究成果。"
> 
> 大模型："张三教授是清华大学计算机系的知名学者，主要研究量子计算，曾获得国家自然科学奖一等奖，发表了 200 多篇论文……"
> 
> 现实：世界上可能根本没有"张三教授"这个人，或者他的研究方向完全不是量子计算。

**为什么大模型会幻觉？**

> 大模型的训练目标是"生成流畅、合理的文本"，而不是"生成绝对真实的文本"。当它不确定答案时，它会"猜测"一个最可能的答案——而不是说"我不知道"。
> 
> 就像一个自信的演讲者，即使不知道细节，也会即兴发挥，讲得头头是道。

###  （二）知识截止：不知道新鲜事儿

大模型的知识来自训练数据，而训练数据有截止日期。

<table><thead><tr><th style="text-align:left;">模型</th><th style="text-align:left;">知识截止时间</th></tr></thead><tbody><tr><td style="text-align:left;">GPT-3.5</td><td style="text-align:left;">2021 年 9 月</td></tr><tr><td style="text-align:left;">GPT-4</td><td style="text-align:left;">2023 年 12 月</td></tr></tbody></table>

**案例**：

> 用户："2024 年奥运会哪个国家金牌最多？"
> 
> 大模型："我不知道 2024 年奥运会的信息，我的知识截止于 2023 年 12 月。"
> 
> 或者更糟——它可能编造一个答案。

###  （三）RAG 如何解决这两个问题？

**核心思想**：让大模型先"查资料"，再"写答案"。

```
用户提问
    ↓
检索模块：从知识库中找到最相关的文档片段
    ↓
大模型：基于检索到的真实信息生成回答
    ↓
用户收到有依据的回答
```

**类比：开卷考试**

> 闭卷考试（纯大模型）：学生凭记忆答题，记错了就写错了。
> 
> 开卷考试（RAG）：学生可以翻课本，答案基于课本内容，错误率大幅降低。
> 
> RAG 就是让大模型从"闭卷考试"变成"开卷考试"。

**作用**：把长文档切成适合检索的小块。

**为什么需要切分？**

> Embedding 模型有最大输入长度限制（通常 512-4096 Token）。如果一篇文章有 1 万字，直接编码会：
> 
> -   超出模型限制，被截断
> -   即使没超，长文本的 Embedding 会"稀释"关键信息
> 
> 切分成小块后，每块都聚焦一个主题，检索更精准。

###  （三）Embedding 与向量存储

这部分在上一节《向量数据库与嵌入模型》中已经详细讲解，此处简要回顾：

```
文本 → Embedding 模型 → 向量 → 存入向量数据库

用户 query → Embedding 模型 → 向量 → 在向量数据库中搜索 Top-K
```

**选型建议**：

-   **Embedding 模型**：中文用 BGE，英文用 OpenAI text-embedding-3，混合场景用 E5
-   **向量数据库**：小规模用 pgvector/Chroma，大规模用 Milvus/Pinecone

###  （四）大模型生成（Generator）

**作用**：基于检索到的上下文，生成最终回答。

**Prompt 模板**：

```
你是[角色描述]。请根据以下参考资料回答用户问题。
如果参考资料中没有相关信息，请诚实地说"根据现有资料，我无法确定"。

## 参考资料
[检索到的文档片段 1]
[检索到的文档片段 2]
[检索到的文档片段 3]

## 用户问题
[用户 query]

## 回答要求
- 基于参考资料回答，不要编造
- 如果有多条信息冲突，选择最可靠的来源
- 在回答中标注信息来源（如"根据资料[1]"）
```

##  三、RAG 的检索策略：从"简单搜索"到"智能检索"

###  （一）基础检索：向量相似度搜索

最基础的 RAG 检索：把 query 转成向量，在向量数据库中找最相似的 Top-K。

**流程**：

```
用户 query → Embedding → 向量数据库 ANN 搜索 → Top-K 片段
```

**局限性**：

> -   如果 query 和文档的表述方式不同，可能检索不到（语义鸿沟）
> -   只考虑语义相似度，不考虑关键词匹配（可能漏掉含有关键词但语义不近的文档）
> -   对多条件查询支持不好（"价格在 100-200 元之间的红色产品"）

###  （二）混合检索：向量 + 关键词

**核心思想**：向量检索擅长语义匹配，关键词检索（BM25）擅长精确匹配，两者结合取长补短。

```
query ──┬──→ 向量检索 → 结果 A
        └──→ 关键词检索（BM25）→ 结果 B
                    ↓
             融合排序（RRF）→ 最终结果
```

**RRF（Reciprocal Rank Fusion）**：

> 把两种检索的结果列表合并，重新排序。在两种列表中都排名靠前的文档，最终排名更高。

**适用场景**：

-   需要同时匹配语义和关键词（如产品名称、型号、专业术语）
-   用户对精确匹配有要求（如法律条文、药品名称）

###  （三）多路召回：从多个角度检索

**核心思想**：一个 query 可能涉及多个维度，从多个角度分别检索，再合并结果。

<table><thead><tr><th style="text-align:left;">召回路径</th><th style="text-align:left;">方法</th><th style="text-align:left;">用途</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>语义召回</strong></td><td style="text-align:left;">向量相似度</td><td style="text-align:left;">找语义相关的文档</td></tr><tr><td style="text-align:left;"><strong>关键词召回</strong></td><td style="text-align:left;">BM25 / 倒排索引</td><td style="text-align:left;">找含有关键词的文档</td></tr><tr><td style="text-align:left;"><strong>图谱召回</strong></td><td style="text-align:left;">知识图谱</td><td style="text-align:left;">找实体关联的文档</td></tr><tr><td style="text-align:left;"><strong>结构化召回</strong></td><td style="text-align:left;">SQL / 属性过滤</td><td style="text-align:left;">按条件筛选（价格、时间等）</td></tr></tbody></table>

**示例**：

> 用户问："2023 年发布的、价格在 5000 元以下的拍照手机推荐"
> 
> -   结构化召回：筛选 2023 年发布、价格 < 5000 的手机
> -   语义召回：找和"拍照好"相关的评测
> -   关键词召回：确保包含具体型号名称
> -   合并结果，生成推荐

###  （四）查询重写：让 query 更容易被理解

**问题**：用户的 query 可能表述不清、太简短、或者和文档的表述方式不同。

**解决方案**：在检索前，先用大模型"改写" query。

<table><thead><tr><th style="text-align:left;">改写策略</th><th style="text-align:left;">示例</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>扩展</strong></td><td style="text-align:left;">"手机" → "手机 智能手机 移动电话 手持设备"</td></tr><tr><td style="text-align:left;"><strong>澄清</strong></td><td style="text-align:left;">"这个怎么用？" → "产品 X 的使用方法是什么？"（结合上下文）</td></tr><tr><td style="text-align:left;"><strong>分解</strong></td><td style="text-align:left;">"怎么退货和换货？" → "退货流程" + "换货流程"（两个问题分别检索）</td></tr><tr><td style="text-align:left;"><strong>同义词替换</strong></td><td style="text-align:left;">"笔记本电脑" → "笔记本 手提电脑 laptop"</td></tr></tbody></table>

**HyDE（Hypothetical Document Embeddings）**：

> 让大模型先根据 query 生成一个"理想的回答文档"，然后用这个理想文档的向量去检索。
> 
> 例如：用户问"量子计算的原理"
> 
> -   先生成一段关于量子计算原理的"理想回答"
> -   用这段理想回答的向量去检索真实文档
> -   这样检索到的文档和理想回答语义接近，往往更相关

##  四、RAG 的高级优化技巧

###  （一）重排序（Re-ranking）

**问题**：向量检索返回的 Top-K 不一定是最相关的。因为向量相似度是"粗略筛选"，精确度有限。

**解决方案**：用更精确的模型对 Top-K 结果重新排序。

```
用户 query → 向量检索 → Top-100 候选
                                ↓
                    重排序模型（Cross-Encoder）
                                ↓
                         精确排序 → Top-5
```

**Cross-Encoder 的直觉**：

> 向量检索（Bi-Encoder）像"看照片相亲"——快速、批量，但只看外表。
> 
> 重排序（Cross-Encoder）像"面对面交流"——慢、逐个进行，但能深入理解两者是否真正匹配。

**常用重排序模型**：

<table><thead><tr><th style="text-align:left;">模型</th><th style="text-align:left;">特点</th></tr></thead><tbody><tr><td style="text-align:left;"><strong>Cohere Rerank</strong></td><td style="text-align:left;">商业 API，效果优秀</td></tr><tr><td style="text-align:left;"><strong>BGE Reranker</strong></td><td style="text-align:left;">开源，中文效果好</td></tr><tr><td style="text-align:left;"><strong>bce-reranker</strong></td><td style="text-align:left;">网易开源，轻量高效</td></tr></tbody></table>

**AI PM 关注点**：

> 重排序是提升 RAG 效果的"性价比之王"——增加少量计算，检索准确率提升 10-20%。
> 
> -   数据量 < 10 万：可以不加重排序
> -   数据量 > 10 万：强烈建议加重排序

###  （二）查询路由：不同问题走不同路径

**核心思想**：不是所有问题都需要走 RAG。先判断问题类型，再决定检索策略。

```
用户 query
    ↓
查询分类器
    ├── 闲聊/通用知识 → 直接用大模型（不走 RAG）
    ├── 需要实时数据 → 调用 API / 查数据库
    ├── 需要文档知识 → 走 RAG（向量检索）
    └── 需要精确计算 → 调用计算器 / 代码执行
```

**好处**：

-   减少不必要的检索，降低成本和延迟
-   不同类型的问题用最适合的方式处理

###  （三）迭代检索：多轮检索 refine

**核心思想**：第一次检索可能不够精准，用检索结果进一步 refine query，再做第二轮检索。

```
query → 第一轮检索 → 分析结果 → 生成子问题 → 第二轮检索 → 合并结果
```

**适用场景**：

-   复杂的多条件查询
-   需要跨文档关联信息
-   初始 query 比较模糊

###  （四）上下文压缩：把检索结果精炼后送给大模型

**问题**：检索到的 Top-K 片段可能很长，全部塞进 Prompt 会：

-   超过上下文限制
-   引入噪声（不相关的信息干扰模型判断）
-   增加 Token 成本

**解决方案**：

##  六、RAG 的典型应用场景

###  （一）企业知识库问答

**场景**：企业内部文档（产品手册、技术文档、规章制度）的问答。

**特点**：

-   文档格式多样（PDF、Word、网页）
-   需要权限控制（不同员工能看到不同内容）
-   答案需要可溯源

**方案**：

-   文档加载 + 切分 + Embedding
-   向量数据库 + 权限过滤
-   RAG + 引用来源标注

###  （二）智能客服

**场景**：替代人工客服，回答用户关于产品/服务的问题。

**特点**：

-   需要接入实时数据（订单状态、物流信息）
-   回答需要准确，不能 hallucinate
-   可能需要执行操作（退款、换货）

**方案**：

-   RAG（产品知识）+ Function Calling（查订单/操作）
-   话术库 + 标准答案匹配
-   人工兜底机制

###  （三）法律/医疗助手

**场景**：辅助专业人士检索法规、判例、医学文献。

**特点**：

-   对准确性要求极高
-   需要引用具体条文
-   责任重大，不能出错

**方案**：

-   高质量领域数据（法规库、医学数据库）
-   多路召回（向量+关键词+结构化筛选）
-   重排序精排
-   人工审核机制

###  （四）代码助手

**场景**：基于代码库回答技术问题、生成代码。

**特点**：

-   需要理解代码结构和依赖关系
-   代码更新频繁
-   需要精确的上下文（相关函数、类定义）

**方案**：

-   代码切片（按函数/类切分）
-   代码 Embedding（CodeBERT、CodeT5）
-   结合 AST（抽象语法树）理解代码结构

##  十、小结

###  核心要点

1.  **RAG 是解决大模型幻觉和知识截止的首选方案**：超过 80% 的企业级大模型应用采用 RAG。
    
2.  **RAG = 检索 + 生成**：先查资料，再写答案。让大模型从"闭卷考试"变成"开卷考试"。
    
3.  **文档切分是 RAG 的基础**：Chunk Size 300-800 Token，Overlap 50-200 Token 是经验值。
    
4.  **混合检索 + 重排序是效果提升的关键**：向量检索负责语义，BM25 负责关键词，重排序负责精确度。
    
5.  **RAG 不是万能的**：语气风格、复杂推理能力还是需要微调来补充。RAG + 微调是最佳组合。
    
6.  **评估 RAG 要看两个维度**：检索效果（找得准不准）和生成效果（答得对不对）。
    

###  给 AI PM 的一句话

> **RAG 是大模型产品落地的"基础设施"——它让模型从"靠记忆答题"变成"查资料答题"。作为 PM，你不需要懂 ANN 算法的细节，但你需要懂：怎么切分文档、怎么评估检索效果、怎么设计生成 Prompt、以及这一切的性价比。RAG 做好了，大模型产品就成功了一大半。**
